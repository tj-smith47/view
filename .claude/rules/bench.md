# Benchmark conventions

## Every cell declares the human moment it stands for

A bench cell either names the moment a person lives through, under a config
they would actually run, at a threshold they can perceive -- or it is a
diagnostic that decomposes such a cell and can never carry a claim. There is
no third kind of number worth gating on, and a page that leads with the
flattering segment instead of the moment is measuring what was easy to
measure.

Every `[[budget]]` row in `crates/view-bench/budgets.toml` therefore
declares its meaning, and `view_harness::budgets::parse` refuses one that
does not:

```toml
[[budget]]
spec_row = "Launch -> the settled screen, real config"
scenario = "startup"
metric   = "settled_ratio_p50"
max      = 1.0
kind     = "felt"            # felt | diagnostic | resource
felt     = "launch -> the screen you can start working in (tree, tabline, statusline settled), paired with nvim on the same host in the same run"
config   = "real"            # real (a plugin config a person runs) | fixture

[[budget]]
spec_row = "Embedded engine startup cost"
scenario = "startup"
metric   = "server_delta_ms"
max      = 5.0
kind     = "diagnostic"
decomposes = "startup.settled_ratio_p50"
config   = "real"
```

- `felt` carries the moment in a person's words and is refused on any other
  kind, where it would read as a claim the row is not entitled to make.
- `diagnostic` carries `decomposes`, naming a felt row the file declares.
  A dangling target is a load error: a segment that explains nothing has no
  reason to be measured.
- `resource` (memory, footprint) carries no speed language anywhere.

## A felt bound is seated on the config it claims

`kind = "felt"` with `config = "real"` requires a `MATRIX` seat on the
`user` fixture -- the login-shaped config generated by `task user-fixture` --
paired against bare nvim. `bin/bench.rs`'s
`every_felt_bound_is_seated_on_the_config_it_claims` fails the build
otherwise: the `startup` row shipped declaring a real config while seated on
the plugin-free fixture, so the felt statement in the file described a
measurement nobody had taken.

The only exemptions are rows with no bare-nvim counterpart to pair against
(view's own picker, the engine-wedge banner), each listed in
`view_harness::budgets::UNPAIRED_FELT` with its grounds. A felt row that is
neither `real` nor listed is refused at load, and an entry left behind after
its row is renamed fails `every_unpaired_felt_exemption_names_a_shipped_row`.

## A diagnostic is never cited as a win

`scripts/check-budget-drift.sh` (in `task ci`, via `task audit`) fails when:

- a `[[budget]]` number stops appearing in the spec row it names;
- a diagnostic or resource row's spec text does not say which it is;
- `README.md` or `docs/performance.md` names any metric identifier.

That last rule is the strict form, and it is the one with no false
positives: the user-facing pages state moments in words ("the key reaches
nvim in under a tenth of a millisecond"), so an identifier on either page is
a number quoted outside the vocabulary that decides what it may claim.
Identifiers, statistics, classes, headroom and re-seating live in
`docs/benchmarking.md`, which nothing checks because nobody reads it for a
claim.

## A moment nobody has measured says so

A felt row whose real-config leg has not been recorded is committed as an
empty baseline cell with a `[withdrawn.<scenario>.<fixture>]` reason beside
it: the gate then reports it (`GATE COVERAGE FAIL`) instead of passing over
it quietly, and `docs/performance.md` says "not yet recorded" in words.
Filling such a row from the plugin-free fixture's number is the exact
substitution this whole vocabulary exists to refuse.
