- [x] **flood row cannot record on macOS** (RESOLVED 00b7b53: wall-clock window + unbounded non-interactive producer; both classes recorded, ~1200/1350 gaps): `flood/minimal` refuses on mbp with `only 31 samples collected with a 1000-sample warmup`. The floor is `min_gap_samples` = the protocol's sample count, met on Linux (3M lines drain in ~12.6s with ~1020 observed frame changes) but not on macOS, where the same flood drains in ~845ms with ~12 observed frame changes. Not a view painting defect: bare nvim, measured through the same pty in the same run, shows 11 gaps against view's 12. The producer is NOT the cause and an earlier claim that it was ("BSD seq emits the lines ~15x faster") is false — running the scenario's own command, `seq -f 'L%.0f' 1 3000000 > /dev/null` takes 0.38s on Linux (uutils 0.8.0) and 0.49s on macOS (BSD seq, M1 Max), i.e. macOS is 1.3x SLOWER. Producer time is ~0.4-0.5s on both hosts and cannot explain 845ms vs 12.6s; the difference lives in the consumer/pty path and is currently unattributed. So the cell's constants are Linux-shaped, but do not size them from a producer-speed story. RESOLVED (not a user call, and previously mis-routed as one): the remedy is a fixed wall-clock drain window. The other two candidates fail on inspection rather than on preference. Sizing `FLOOD_LINES` per platform is a hand-tuned constant duplicating data the run itself can derive, it drifts silently on any hardware change, and it equalizes SAMPLE COUNTS without equalizing the pressure regime the row exists to measure. Making the gap floor per-platform is worse: a p99 computed over ~12 observations is not a p99 at all — the top sample IS the reported value — so it would keep the metric's name while silently swapping in a far noisier statistic, which is the exact silent-failure class this project is organized against. The wall-clock window matches spec 3.1's own framing, which defines this row by a property ("UI thread never blocks; coalesced paint stays inside the staleness budget") and never by a line count, so no spec amendment is required; `FLOOD_LINES` is a harness choice. Sustained pressure is a duration concept, and a duration-bounded window makes sample counts comparable across hosts by construction with no per-platform constant to maintain. It does require the producer to become unbounded (a repeating or endless generator) rather than a fixed line count — that is the real cost of the option and it is worth paying. OPEN, and answerable only by step 1 below, not by choosing differently: whether the window is SUFFICIENT. If the attribution shows the two hosts deliver fundamentally different byte chunking into the pty, the window equalizes measurement duration while the STIMULUS still differs, and the row would gate two different things under one name; that case needs a companion pin (chunk size and/or `$SHELL`) alongside the window. Do not pick the remedy's final shape before the attribution lands. The work must (1) attribute the drain difference, testing the host `$SHELL` difference recorded above as a candidate, (2) then pin `$SHELL` so the shell stops being a host input to a measured number, and (3) then re-record both classes, in that order — pinning before attributing destroys the evidence. `dev-macos.toml` now carries the `[flood.minimal]` cell, so a full-matrix macOS run gates the row rather than failing on it. **RESOLVED 2026-07-26.** Step 1 (attribute), evidence in `.claude/measurements/2026-07-26-flood-shell-attribution.md` (two independent paths, both hosts): `$SHELL` reaches the drain enormously via zsh's ZLE on Linux (nozle restores speed), but the ZLE penalty is Linux-zsh-specific (macOS zsh is fast, macOS bash 3.2 is slow-interactive), so interactive shells are a cross-host minefield and the correct `$SHELL` pin is to run the producer NON-interactively (`sh -c`, fast on both). ORIGINAL: view has no mechanism enforcing a production-line ceiling, and no `.claude/scripts/` directory to host one. Port the mechanism from anodizer (`/opt/repos/anodizer/.claude/scripts/audit-god-files.sh`, wired into `task lint`), which exists because the ad-hoc census it replaced was silently wrong. The rule it enforces: a file is oversized when its **production** code exceeds 1000 lines; test code never counts, and a pure `tests.rs` of any size is never a god file. Four properties are what make it trustworthy and must survive the port. (1) **Test detection is structural, not filename-based**: Cargo `tests/` + `benches/`, `#![cfg(test)]`, plus a transitive closure over `#[cfg(test)] mod NAME;` declarations resolved through real Rust module rules; `any(test, …)` is deliberately NOT treated as test-only. (2) **String and comment elision before brace counting** — the first cut under-counted (fail-open) because a `//` inside a `"https://…"` literal ate the rest of the line, reporting one file as 8 production lines instead of 21. (3) **Named exemption and debt registers, both ratchets**: each entry pins a number that may only fall, and a stale pin — file shrank, or was split, or is no longer over the ceiling — *fails* the audit and must be removed, so neither register can become a parking spot. (4) **Cross-check against an independent implementation** before trusting the counter; anodizer's was validated over all 818 files with zero disagreements. The naive form to avoid is `awk '/^#\[cfg\(.*test/{exit}'`, which matches `#[cfg(feature = "test-helpers")]` and truncates the count — that is exactly how a 1305-line file stayed off anodizer's target list while the split program was reported complete. Cost after optimization is ~2.9s (7.5s before; ~2500 subprocess spawns collapsed into a single awk pass for mod declarations, one `grep -rl`, and pre-indexed pin arrays), which is affordable inside `task lint`.
