# P5.5 Implementation Plan — Session DVR

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** visual scrub/replay of what the screen showed during a session,
branch a fresh session from any recorded point, and export a replay file
(spec:621, §9 invented capability, v0.1 CORE — ruled 2026-08-05, spec:903,
no "post-v0.1" framing anywhere in this plan).

**Binding correction to the charter (spec:621's own wording is wrong and
this plan does not repeat it):** spec:621 describes DVR as built "over the
same keystream+frame recording the oracle uses." No such recorder exists.
`view-oracle`'s only recording mechanism is `PtySession::record_raw_output`
(`crates/view-oracle/src/pty.rs`), which is output-only (no keystream/input
log at all), capped at `RAW_RECORD_LIMIT = 256 * 1024` bytes, and scoped by
its own doc comment to startup-assertion traffic in test fixtures — not
fit for reuse, extension, or renaming into a session-long recorder. This
plan builds the recorder from scratch, as a new, independent mechanism in
`view-core`, and budgets its cost as a first-class perf-contract line item
rather than assuming it is free because "something like it already
exists."

**Why this is invention, not tuning:** nvim's own TUI has no scrub/replay
concept at all — the terminal only ever shows the current frame, and undo
history is buffer-text-only (no screen history, no branch-from-a-past-frame
concept). This plan creates a new measured quantity (recorded session
depth, replay fidelity) where today there is none, on the same "possible
only because the UI and the engine are separate processes" premise every
other P5.5 capability rests on (spec:613-615).

**Architecture:** a bounded, `view-core`-resident `SessionRecorder`
(pure struct, `VecDeque`-backed exactly like `ToastHistory`
(`crates/view-core/src/native/toast.rs:81-120`), fed by a new sibling call
at `runtime.rs`'s existing `dispatch()` entry point, in the same position
and on the same terms as the established `vlog::log_msg(&msg)` call
(non-consuming `&Msg` read, before `update()` consumes the message,
zero-cost when disabled). Two parallel bounded logs: a keystream log
(every `Msg::Key` that reached `update()`; `Key` derives `Clone`, not
`Copy` — it owns a `notation: String` — so each recorded entry costs one
`String` clone, budgeted, not free; § "The hot-path cost bound") and a
frame log (every decoded `Vec<UiEvent>` redraw batch,
the same typed structure `view-engine::ui_events::decode_redraw`
(`crates/view-engine/src/ui_events.rs:19`) already produces and
`view-oracle::raster` already knows how to turn back into a picture — see
"As-built interfaces" below). Scrub renders on-demand by replaying frames
0..=N through the existing `view_surface::render` pipeline into a
side-buffer `Surface`, never by holding N materialized `Surface` snapshots.
Branch spawns a fresh local `Engine` and replays the keystream 0..=branch
point through ordinary `RpcCall::Input`, because "nvim owns all buffer
text" leaves no other mechanism available — view has no buffer-state copy
to clone, only the keystrokes it forwarded. Export serializes the paired
keystream+frame log to a file.

**Tech stack:** no new dependency. Recording reuses `view-engine`'s
existing typed `UiEvent` decode; export serializes with the workspace's
existing msgpack tooling (`rmpv`, already a `view-engine` dependency) or
a plain length-prefixed binary format — Task 5 decides between the two
with a stated default (below).

## Global Constraints

Hard rules, embedded verbatim. Every task states which rule bounds it.

- **nvim owns all buffer text. No view subsystem holds authoritative text
  state. Buffer mutation happens only through `Effect::Rpc`.** Binds
  hardest here: the recorder never stores buffer text, only the two
  things view itself already produces and forwards — outbound keystrokes
  and inbound decoded redraw batches. Branch-from-point replays keystrokes
  through ordinary `RpcCall::Input` against a fresh engine; it never
  reconstructs or injects buffer content directly.
- **The paint loop never awaits RPC. The RPC reader thread never blocks.**
  Binds hardest here: recording a frame is an in-process append to a
  `VecDeque` already sized and owned by `Model`, on the same thread that
  already decodes the redraw batch — no new thread, no new channel, no
  blocking. Scrub rendering (replaying frames 0..=N through
  `view_surface::render`) runs only while the DVR overlay is open, off the
  hot per-keystroke path entirely (§ "The hot-path cost bound" below).
- **No unwrap/expect/panic in lib crates.** Ring-buffer eviction, export
  I/O, and branch-engine spawn failure all return `Result`/are silently
  bounded; no new panic path.
- **Dependency direction: core ← surface ← {native, ai}; only view-engine
  speaks RPC; only view-tui touches the terminal.** `SessionRecorder` and
  its ring buffers live in `view-core`, pure. Branch's fresh-engine spawn
  and keystream replay live in `view-engine`/`view` (the RPC- and
  process-owning layers), never in `view-core`. Export/scrub-render UI
  lives behind the existing overlay/`LayerKind` boundary in `view-tui`.
- **Performance is a contract.** Recording runs on the same per-message
  path supervision's heartbeat and remote's `expire_stale` already share;
  its cost is budgeted explicitly (§ "The hot-path cost bound").
- Use `task` targets, never raw cargo/git, for build/fmt/lint/test/commit.
  Commit only via `task commit -- -m "<msg>"`.
- Comments are WHY-only; doc comments render for users and carry a WHAT
  summary. No session-narrative markers.
- Non-conventional commit prefixes are parenthesised scopes: `feat(dvr):`,
  `test(oracle):` — never `dvr:`.
- **Never weaken an existing budget, the 5 µs tap bar, or the 1.15
  calibration floor.** DVR gets a new budget row (Task 6); no existing
  row's `max` or `ratio` changes.

## The hot-path cost bound

**Round-1 fix note:** the original draft of this section claimed `observe`
paid zero clone cost ("an already-owned `Vec<UiEvent>` moved into the ring,
no clone" and "a `Key`... small `Copy` struct"). Both claims are wrong and,
worse, type-impossible: `observe` is called as a non-consuming `&Msg` read
at the same site `vlog::log_msg(&msg)` already uses
(`crates/view/src/runtime.rs:840`, inside `dispatch()` at line 834),
deliberately *before* `update(model, msg)` at `crates/view-core/src/
update.rs:29` consumes the owned `msg` — so `observe` only ever sees a
shared borrow. A function taking `&Msg` cannot move a `Vec<UiEvent>` or a
`String` out of that borrow; the only way to get an owned copy into the
ring is to clone. Verified against `crates/view-core/src/msg.rs:31`
(`Msg::Redraw(Vec<UiEvent>)`) and `crates/view-core/src/msg.rs:360` (`Key`
derives `Clone`, not `Copy` — it owns a `notation: String`).

**Three options were evaluated for closing this gap:**

1. **Accept the clone, state its cost (chosen).** `observe` clones `Key`'s
   `notation` `String` (a short keystroke notation, e.g. `"<C-w>"`,
   typically a small allocation) per `Msg::Key`, and clones the decoded
   `Vec<UiEvent>` per redraw batch. This is the only option that keeps
   `observe`'s call site and signature identical to `vlog::log_msg`'s
   established non-consuming-read shape — no other hot-path tap in the
   codebase is restructured to hand off ownership, and DVR does not get to
   be the exception.
2. **Restructure the hook to receive ownership at the real drop site
   (rejected).** `msg` is genuinely owned and consumable exactly once, at
   `dispatch()`'s call to `update(model, msg)`
   (`crates/view/src/runtime.rs:834`) — the *only* place ownership could be
   handed to a recorder without cloning. Doing so would require either (a)
   cloning `msg` before the call anyway (no cost win over option 1, and a
   larger clone since it copies the whole `Msg`, not just the two arms DVR
   cares about), or (b) rewriting `update`/`apply_ui_event`'s entire
   match-arm ownership model (`crates/view-core/src/update.rs:271`, `:1000`)
   to thread a recorder callback through every arm so DVR can intercept the
   moved value before the match consumes it — a disproportionate, invasive
   rewrite of the core dispatch path to save a clone that option 1 already
   bounds and states honestly. Rejected.
3. **Cheap summary checkpoints, not every redraw (rejected as the
   default).** Recording a periodic digest (e.g. cell-count/dirty-region
   summary) instead of the full `Vec<UiEvent>` per batch would cut the
   clone cost, but breaks Task 3's own falsifiable check (a sentinel-cell
   test requiring exact, full frame-by-frame replay fidelity) and Task 7's
   oracle cross-check against independent rendering — both need the real
   decoded events, not a lossy summary. Rejected as the primary mechanism;
   not revisited unless a future profiling pass shows option 1's clone
   cost is unacceptable even at opt-in defaults (§ below).

**Falsifiable latency pin:** with `[dvr] enabled = true`, `observe`'s added
cost for a `Msg::Key` dispatch immediately followed by a typical
single-cell-update `Msg::Redraw` batch (one `UiEvent::GridLine` covering a
single character write — the modal case for a keystroke-driven session, not
a worst case) stays under the existing **5 µs tap bar** already invoked by
this plan's Global Constraints section. Task 6's bench row measures this
directly (enabled vs. disabled delta on `echo.minimal`) and gates it
against both the 5 µs tap bar and the existing 1.15 calibration floor,
whichever is tighter.

**Falsifiable latency pin — heavy/full-screen redraw (round-3 fix, closes
important 1: the 5 µs pin above only covers a single-`GridLine` batch, not
a full-screen repaint's clone cost).** `observe`'s `Msg::Redraw` arm clones
the *entire* decoded `Vec<UiEvent>` per batch (§ above) — a full-screen
repaint (window resize, `:e` on a new buffer, scroll-triggered repaint of
a 100k-line file) produces a batch with orders of magnitude more
`UiEvent`s than the single-cell modal case the 5 µs pin bounds, so that
pin alone does not bound DVR's added cost on the class of redraw this
codebase already tracks separately as "heavy" (`crates/view-bench/
budgets.toml`'s existing `echo`/`scroll` `fixture = "heavy"` rows, and the
`scenario = "scroll"` rows measuring the 100k-line-file case specifically)
and "scroll" (`spec_row = "Sustained scroll, 100k-line file, tier full"`).
This plan follows that same fixture-class convention rather than inventing
a new one: a new bench row, `dvr.heavy_redraw_overhead_us`, measures
`observe`'s enabled-vs-disabled delta on the existing `scroll` scenario's
100k-line fixture (the codebase's own heaviest already-instrumented
redraw-batch case), the same paired-campaign shape Task 6's
`recording_overhead` row and supervision's Task 6 p99-over-real-traffic
framing already use — a measurement across real dispatch traffic, not a
synthetic single-call microbenchmark, following the same principle that
motivates measuring heartbeat liveness over real traffic rather than an
isolated call.

This row cannot be armed with a bound in this plan — no measurement of it
exists yet — so it follows the arming convention `budgets.toml` already
uses for a brand-new metric (round-4 fix: not the `[[shortfall]]` state,
which is reserved for an *existing* spec-mandated budget currently missed
— `budgets.toml`'s own header, `crates/view-bench/budgets.toml:14-15`,
"A metric with no entry here has no spec budget. That is a real state, not
an oversight," and `view-harness/src/budgets.rs:8-52`'s module doc, which
defines `[[shortfall]]` as accepted-and-gated debt against an already-
budgeted metric that regressed, not a staging area for a metric that has
never had a budget). `dvr.heavy_redraw_overhead_us` starts with **no
entry at all** — the correct unarmed state for a metric this plan
introduces — and gains its first real `[[budget]]` `max` row only once
Task 6's paired A/B campaign on the `scroll` fixture actually measures it;
no number is invented here.

**Stated ceiling for the documentation-warning trigger:** if the recorded
`dvr.heavy_redraw_overhead_us` value exceeds **200 µs** (roughly two
orders of magnitude under `echo.heavy`'s own existing `view_p99_ms` 8 ms
bar and its recorded ~10.3 ms shortfall on dev-macos, keeping DVR's own
tax a small fraction of the existing heavy-fixture budget rather than
comparable to it), Task 6's registry entry (and any user-facing feature
documentation the introspector/help surface generates for `dvr`) must
carry an explicit performance warning that enabling DVR adds measurable
redraw latency on large or complex screens — the single-character 5 µs pin
alone must not be read as bounding the opt-in feature's full cost.

Both recorder appends remain unconditional `VecDeque` operations against a
pre-sized ring (capacity fixed at construction, no reallocation once
warm), gated by a single `bool` read (`recorder.enabled`) so a disabled
recorder still costs one branch and nothing else — that half of the
original claim was correct and is unchanged.

## Open design questions — resolved in this plan

Per `invention-research.md`'s DVR sheet, three forks were flagged open.
Resolved here, each with a stated default and an override:

1. **Always-on vs. opt-in recording.** Resolved (revised in the round-1 fix
   — see "The hot-path cost bound"): **opt-in by default**
   (`[dvr] enabled = false`, overridable to on). The original "always-on"
   default was justified partly on a "recording is free, no clone" claim
   that round-1 review showed is type-impossible under `observe(&Msg)`'s
   borrow signature — recording provably clones a `String` per keystroke
   and a `Vec<UiEvent>` per redraw batch, so "on by construction, no cost
   to the common case that never opens the scrub overlay" is no longer
   true. A user who wants DVR pays a real, bounded, budgeted cost (§ above)
   to have it available; a user who does not is unaffected. This makes DVR
   the first native feature in this plan set to use an opt-IN switch
   rather than the established opt-OUT `off_switch` convention
   (`registry.rs`) — a deliberate, reasoned exception, not silent drift:
   DVR's per-message cost is categorically different from every other
   feature's `off_switch`, which gates *behavior* behind a cheap check,
   where DVR's `observe` does real allocation work even to be recorded at
   all. Task 6's registry entry documents this exception explicitly rather
   than silently reusing `off_switch` semantics unchanged.
2. **Recording location.** Resolved: `view-core`, as a new
   `native::dvr::SessionRecorder` pure struct owned by `Model`, ring-buffer
   shaped identically to `ToastHistory` (`toast.rs:81-120`) — `capacity`,
   `entries: VecDeque<_>`, `new`/`with_capacity`/`push`/`entries()`. Two
   separate ring buffers (keystream, frames) rather than one combined
   struct, because their per-entry size and retention needs differ by
   roughly two orders of magnitude (a `Key` is tens of bytes; a redraw
   batch's `Vec<UiEvent>` is not) — a single shared capacity would either
   starve frames or waste keystream space.
3. **Branch-from-point mechanism.** Resolved: **replay-driven forking**.
   A branch always spawns a fresh **local** engine, even when the
   originating session is remote (P3's SSH-spawned `Engine`) — decided as
   v0.1 CORE scope-narrowing (not "post-v0.1" language: it is simply the
   only mechanism the architecture supports without inventing a
   buffer-state clone the "nvim owns all buffer text" rule forbids
   outright). The new engine replays the recorded keystream from session
   start through the branch point via ordinary `RpcCall::Input`, then
   accepts live input from there. A remote-originated branch producing a
   local child is a real, user-visible behavior difference and is
   surfaced in the branch UI's own copy (Task 4), not hidden.
4. **Frame storage shape** (not flagged in the research sheet as a fork,
   but resolved here since it drives Task 1's type): store the already-
   decoded `Vec<UiEvent>` per redraw batch (not raw msgpack `Value`, not a
   rasterized `Buffer`/`Surface` snapshot). `view-oracle::raster` already
   demonstrates the reusable pattern this plan copies:
   `raster::screen_text`/`screen_rows` (`crates/view-oracle/src/raster.rs`)
   render a `Surface`+`Grid` pair to text with no `view-tui` dependency —
   confirming decoded events are sufficient to reconstruct a picture
   without the terminal-painting layer. Scrub reconstructs a frame
   on-demand by replaying batches `0..=N` through `view_surface::render`
   into a throwaway `Surface`/`Grid`, never by materializing N screens up
   front.

### Task 1: `SessionRecorder` — the bounded keystream+frame ring buffers

**Files:** Create `crates/view-core/src/native/dvr.rs`; edit `mod.rs`,
`model.rs`.

**Rule bound:** paint loop never awaits RPC (observe is a pure, hot-path
append); no view subsystem holds authoritative buffer text (only
keystrokes and decoded redraw batches are stored, never buffer content
itself).

**Design:** `SessionRecorder { enabled: bool, keys: VecDeque<RecordedKey>,
frames: VecDeque<RecordedFrame>, key_capacity: usize, frame_capacity:
usize, header: SessionHeader }`. `RecordedKey { notation: String, at:
Duration }` (session-relative timestamp, not wall clock — makes
export/replay host-independent). `RecordedFrame { events: Vec<UiEvent>,
at: Duration }`. `observe(&mut self, msg: &Msg)` pattern-matches exactly
two arms: `Msg::Key(key) if self.enabled => self.keys.push_back(...)`
(clones `key.notation` — § "The hot-path cost bound") and the existing
redraw-batch message variant (cite exact name at implementation — the same
one `vlog::log_msg` already matches for its `Redraw` arm) `if self.enabled
=> self.frames.push_back(...)` (clones the decoded `Vec<UiEvent>` — same
section); every other variant falls through as a no-op, same shape as
`ToastHistory::push`'s eviction. `Default` capacities: 10,000 keys
(generous — a `Key`-sized entry is cheap) and 2,000 frames (redraw batches
are heavier; 2,000 frames covers a substantial session at typical
keystroke-to-redraw ratios without unbounded growth). Both configurable
via `[dvr] key_capacity`/`frame_capacity`, both clamped to a minimum of 1
exactly like `ToastHistory::with_capacity`.

**Session-start header (round-1 fix, closes blocker: branch cannot
reproduce origin state without it).** `view file.txt` never sends a
`Msg::Key`/`Msg::Redraw` naming `file.txt` — it bakes the file into
`EngineConfig.extra_args` at spawn time, before the message loop even
starts (`fn engine_config(cli: &Cli) -> EngineConfig`,
`crates/view/src/main.rs:152`, consumed in `main()` before
`Model::with_term_size(...)` construction). A recorder that only observes
`Msg`s has no way to know what file(s) the session opened with, so a
branch replaying only the keystream would spawn a fresh engine with no
open buffer — it cannot reproduce the origin session's state. Fix:
`SessionRecorder` also captures a `SessionHeader { nvim_bin: PathBuf,
extra_args: Vec<OsString>, env: Vec<(OsString, OsString)>,
stdin_relay_active: bool }` — the exact subset of `EngineConfig`'s public
state needed to respawn an equivalent engine (mirrors `EngineConfig`'s own
field shape field-for-field; `view` constructs the header from the same
already-built `EngineConfig` value it passes to `Engine::spawn`, not by
re-deriving it independently, so there is one source of truth). Captured
once, at `SessionRecorder::new`, from a new `SessionRecorder::with_header(
enabled: bool, header: SessionHeader) -> Self` constructor called from
`main.rs` immediately after `engine_config(&cli)` is built. `EngineConfig`
is `#[non_exhaustive]` and not `Clone` (it holds a private `stdin_relay:
Option<OwnedFd>` on unix, `crates/view-engine/src/process.rs:29`), so
`SessionHeader` is a deliberately narrower, independently `Clone`-able
struct built from `EngineConfig`'s public fields at the one call site that
already has both the `Cli` and the constructed `EngineConfig` in scope —
it does not attempt to clone or wrap `EngineConfig` itself.

**Round-3 fix — `view -` (piped-stdin) sessions, closes the important:**
`stdin_relay` is private, but `EngineConfig::stdin_relay_requested(&self)
-> bool` (`crates/view-engine/src/process.rs:201-204`) already exposes
whether it is armed, populated by `main.rs`'s `maybe_relay_stdin` for the
`view -` passthrough form (`crates/view/src/main.rs:181-190`). Capturing
the piped content itself into the header was evaluated and rejected: the
relay is a live fd handed to nvim at spawn time with no existing tee
point, and unlike `extra_args`/`env` it is not bounded in size or in when
it finishes being read (an interactive terminal fd or a slow producer both
count as `view -`), so any size cap would silently truncate the replay
input rather than bound it honestly — a wrong buffer state produced
silently, which is worse than the alternative below and inconsistent with
this same task's own disk-staleness design (§ Task 4) choosing refuse-
with-override over silent divergence. Chosen instead: `SessionHeader`
captures only the boolean `stdin_relay_active` (via the existing public
`stdin_relay_requested()`, no private-field access needed), and Task 4's
branch path refuses to branch a session recorded with it set, with a
stated user-visible error (§ Task 4 below) — a deliberate scope
narrowing, not a silent drop, and falsifiable (Task 4's own check).

**Interfaces:**

### Task 3: Scrub — on-demand frame reconstruction and overlay

needed here).

### Task 4: Branch — replay-driven fork to a fresh local engine

**Files:** `crates/view-engine/src/process.rs`,
`crates/view-core/src/msg.rs` (`Msg::DvrBranch`, `Msg::DvrBranchReady`),
`crates/view-core/src/update.rs`, `crates/view/src/runtime.rs`.

**Rule bound:** nvim owns all buffer text (branch never clones engine
state — it re-derives it by replaying keystrokes against a fresh engine,
the only mechanism the architecture permits).

**Design:** `Msg::DvrBranch { at_frame: usize }` fired from the scrub
overlay. `update()` returns an `Effect` (not a direct RPC call — the
executor already owns spawning async work) that: (1) resolves `at_frame`
to the corresponding keystream index (the recorder's frame and key logs
share the same session-relative `Duration` timeline, so "branch at frame
N" maps to "replay every key with `at <= frames[N].at`"); (2) spawns a
new **local** `Engine` from the recorder's captured `SessionHeader` (Task
1) via the existing `Engine::spawn`/`EngineConfig` path (Task 1 of the
supervision plan already establishes this exact reuse for `restart()` —
branch follows the same precedent) — this is what makes the branched
engine open the same file(s) the origin session did, closing the "branch
of `view file.txt` opens no buffer" gap the original draft left open; (3)
replays the resolved key subsequence through `RpcCall::Input` against the
new engine, in order, before accepting any live input; (4) on completion,
emits `Msg::DvrBranchReady { handle }`, which `update()` routes to a new
window/session swap (exact swap mechanism — new terminal tab vs. replacing
the current session — deferred to implementation-time UX decision, scoped
to "opens a usable second session," not blocking this plan's architecture).
A remote-originated branch producing a local child is stated in the
branch confirmation prompt's copy: `"Branch will run locally, even though
this session is remote — nvim owns no state view can clone."`

**Piped-stdin refusal (round-3 fix, closes the important — a session
started as `view -` cannot be branched correctly).** `SessionHeader`
captures whether the origin session relayed piped stdin
(`stdin_relay_active`, § Task 1) but not the piped content itself — a
branch that respawned nvim with a bare `-` passthrough argument and
nothing behind it would either hang waiting for stdin that never arrives
or open an empty buffer, a silent divergence from the origin session with
no signal to the user. Fix: before `update()` emits the spawn effect for
`Msg::DvrBranch`, it checks `model.dvr.header().stdin_relay_active`; if
set, no engine is spawned at all — the same `PromptState`/toast surface
Task 4's disk-staleness divergence prompt already uses instead reports
`"This session was started with piped stdin (view -) — branching is not
supported because the piped content was never captured. Export the
session instead (Task 5)."` This is a deliberate scope narrowing (§ Task
1's round-3 fix states the rationale for rejecting capture-with-a-cap),
not a silent drop: it is stated here with rationale and has its own
falsifiable check below.

**Disk-staleness detection (round-1 fix, closes blocker: branch-time state
may not match record-time state on disk).** A recorded session's
`SessionHeader.extra_args` names file paths that may have changed on disk
between record-start and branch-time (edited outside view, reverted,
deleted) — replaying the keystream against a freshly re-read file could
silently diverge from what the user watched in scrub. Fix: at
record-start, `SessionRecorder::with_header` computes a content hash (a
local FNV-1a implementation, mirroring `theme_cache::fnv1a`'s existing
precedent — `crates/view/src/theme_cache.rs:163-177` — reimplemented here
because the original is private to the `view` crate and this code lives in
`view-core`) over every file-shaped path in `extra_args`, stored on
`SessionHeader` as `open_target_hashes: Vec<(PathBuf, u64)>`. At
`spawn_branch` time, the same hash is recomputed over the same paths and
compared. On mismatch, branch **refuses with an override**, not a silent
warn-and-proceed: the existing branch-confirmation `PromptState` modal
(the same one carrying the local-child copy above) gains a divergence
variant — `"file.txt has changed on disk since this session was recorded
— branch anyway? [y/N]"` — and only proceeds past the mismatch on explicit
confirmation. Refuse-by-default is chosen over silent proceed because a
branch is, by definition, a deliberate act to reproduce a specific
past state; silently replaying keystrokes against changed content produces
a buffer state the user did not ask for and has no signal it happened,
whereas a blocking prompt costs one keypress and is skippable by a user
who understands the risk.

**Interfaces:**

### Task 5: Export — serialize the paired keystream+frame log

**Files:** `crates/view-core/src/native/dvr.rs` (export/import),
`crates/view-core/src/msg.rs` (`Msg::DvrExport`).

**Rule bound:** no unwrap/expect/panic in lib crates (file I/O and
serialization both return `Result`).

**Design — format decision (open question, resolved here):** msgpack via
`rmpv`, not a bespoke binary format. Rationale: `rmpv` is already a
`view-engine` dependency (the RPC wire format itself), so exporting
`RecordedKey`/`RecordedFrame` (which directly embed `UiEvent`, already
msgpack-shaped from `decode_redraw`) costs no new dependency and produces
a replay file whose frame section is, structurally, the same shape as the
original RPC traffic — inspectable with the same tooling a user might
already reach for. A plain custom binary format was the runner-up,
rejected for adding a second serialization convention to a codebase that
already standardized on msgpack at this exact boundary. Export writes a
small header (`format_version: u32`, session start timestamp) followed by
the key log then the frame log, each length-prefixed.

**Interfaces:**
