# P5.5 Implementation Plan — Native Image Viewing

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** kitty graphics protocol on the `full` capability tier, half-block
cell fallback below it, painted as a native overlay; extends to picker
preview and tree hover; nvim keeps the buffer, view supersedes only the
paint (spec:621, §9 invented capability, v0.1 CORE — ruled 2026-08-05,
spec:898, no "post-v0.1" framing anywhere in this plan).

**Why this is invention, not tuning:** nvim's own TUI has no image-
rendering concept at all — every terminal-nvim image plugin (image.nvim,
etc.) shells out to a separate kitty-graphics-aware process or degrades
to ASCII art, because nvim's own paint path has no channel for anything
outside `ext_linegrid` cell text. view's separate `view-tui` paint layer,
already the sole terminal-touching crate, is what makes a genuine
graphics-protocol overlay possible without nvim's cooperation — the same
"possible only because the UI and the engine are separate processes"
premise every P5.5 capability rests on (spec:611-613).

**Dependency on the shared open-dispatch mechanism:** this plan does not
define its own classifier, message, or dispatch fan-out. `P5.5-media`
(`.claude/plans/2026-08-09-p5_5-media.md`, § "The shared open-dispatch
mechanism") owns
`open_dispatch::classify()`, `OpenKind` (including the `OpenKind::Image`
variant), `Msg::OpenPath`, and `update()`'s single fan-out match — that
plan's Task 2 stubs the `OpenKind::Image` arm specifically so this plan
can implement it without either plan blocking on the other's full
completion. This plan's Task 1 is that arm's real implementation; it must
not introduce a second classifier or a second `Msg::OpenPath`-shaped
message anywhere in `view-core` — if implementation-time drift is found
(two competing definitions), P5.5-media's is authoritative and this
plan's must be deleted in favor of it.

**Correcting a stale `HANDOFF.md` claim (image plan foundation):**
`HANDOFF.md:215-217` claims `Rows.lines: Vec<String>` cannot express
intra-row styling and needs a reshape, framed as an open blocker. Direct
inspection of `crates/view-surface/src/overlay.rs` at HEAD shows this
already landed — `Rows.lines` is `Vec<Vec<Span>>`, confirmed by
`git log --oneline --all --grep` finding commit `035543e "reshape
statusline overlay rows to per-span styling"`. This plan does not cite or
depend on the stale claim. The real, still-open limitation this plan
must design around is different and deeper: `Span { text: String, role:
StyleRole }` (`crates/view-core/src/native/views.rs:103`) carries a
`StyleRole` — a closed, finite, **themed** enum (`Plain`, `Mode`, `File`,
`GitBranch`, `DiagnosticError`, `Match`, ...), resolved to a concrete
color only by a painter via `StyleRole::chrome_group` — not an arbitrary
RGB value. An image's pixels need literal per-cell truecolor with no
themed meaning at all; `Span`/`StyleRole` cannot express that by
construction, not merely by missing a reshape.

**Architecture:** image overlays bypass the `Rows`/`Span`/`StyleRole`
styled-text pipeline entirely. A new `LayerKind::Image(ImageView)` variant
carries either a raw kitty-graphics APC payload (full tier, protocol
probe passed) or a `Vec<Vec<(u8, u8, u8)>>` grid of literal per-cell
truecolor pairs (half-block fallback — each terminal cell rendered as an
upper/lower half-block character with independently set foreground/
background RGB, doubling vertical resolution over a plain solid-color
cell). A dedicated `paint_image` function in `view-tui` writes true-color
escapes (or the kitty APC sequence) directly, called from a new
`composite_into()` arm — the same, single dispatch site every other
`LayerKind` variant already routes through, extended by one arm rather
than by a second painting path. Capability detection adds a genuine
kitty-graphics protocol probe (a new APC query, not merely inferred from
`Tier::Full`) to `tiers.rs`'s existing single startup probe batch,
producing a new `TermCaps.kitty_graphics: bool` field; `Tier::Full` gates
whether the probe/encode path is attempted at all, but the probe result
is the actual truecolor-vs-kitty-graphics decision, since some full-tier
terminals (by the existing sync/truecolor/kitty-kbd definition) strip APC
sequences even while passing every other probe. Picker preview reuses the
existing async `PreviewBuffer`/`PickerPreviewReply` machinery
(`docs/picker-preview-wire-capture.md`); tree hover is genuinely new (no
existing preview mechanism in `tree.rs` at all).

**Tech stack:** no new dependency for kitty-graphics encoding — the
protocol is a plain APC escape sequence (`\x1b_G...\x1b\\`) with a base64
image payload; base64 encoding needs a small, already-common dependency
if the workspace does not already carry one (confirmed at implementation
time via `Cargo.lock`; if absent, `base64` is the minimal, single-purpose
addition, not a larger image-processing crate). Decoding source image
formats (PNG/JPEG at minimum) needs a decode dependency — Task 2 states
and justifies the specific crate choice, since this is the one place this
plan takes on new dependency surface.

## Global Constraints

- **nvim owns all buffer text. No view subsystem holds authoritative text
  state. Buffer mutation happens only through `Effect::Rpc`.** Binds
  directly: view never reads image bytes through nvim, never asks nvim to
  decode or hold image state. `open_dispatch::classify()` (owned by
  P5.5-media) routes an image path to this plan's overlay before nvim is
  ever asked to open it as a buffer — nvim keeps the buffer for every
  file it *does* open; images are the one case where nvim's buffer
  concept is bypassed entirely, by design, matching the goal's own
  framing ("view supersedes only the paint").
- **The paint loop never awaits RPC. The RPC reader thread never blocks.**
  Binds hardest here: image decode (Task 2) and encode (Task 3) are CPU-
  bound, not RPC-bound, but are still too heavy to run inline on the
  paint loop's own turn for a large source image — Task 2 states the
  decode/encode happens once, at overlay-open time, off the per-frame
  paint path, with the result cached on the overlay's own state, so
  scrolling/resizing an already-open image overlay never re-decodes.
- **No unwrap/expect/panic in lib crates.** Decode failure (corrupt/
  unsupported image), encode failure, and probe-inconclusive all return
  `Result`/degrade to a stated fallback (Task 4's half-block path, or a
  plain "cannot preview this image" message reusing the same toast route
  Task 4 of the media plan already established); no new panic path.
- **Dependency direction: core ← surface ← {native, ai}; only view-engine
  speaks RPC; only view-tui touches the terminal.** The image encoder
  (kitty APC construction, half-block RGB grid construction) lives
  entirely in `view-tui`, behind the `composite_into()` boundary — never
  in `view-core`, which only carries the decoded pixel data as a plain
  `Vec<Vec<(u8,u8,u8)>>` (or equivalent) with zero terminal-protocol
  awareness. This is the concrete instance of "only view-tui touches the
  terminal" this plan is built to prove.
- **Performance is a contract.** Decode/encode cost is stated and bounded
  (Task 2/3); the capability probe adds one query to `tiers.rs`'s
  existing single-shot startup batch, not a new probe round-trip (Task
  5) — the paint loop's own per-frame budget is untouched, since an open
  image overlay's steady-state paint is a cached-payload write, not a
  re-encode.
- Use `task` targets, never raw cargo/git, for build/fmt/lint/test/commit.
  Commit only via `task commit -- -m "<msg>"`.
- Comments are WHY-only; doc comments render for users and carry a WHAT
  summary. No session-narrative markers.
- Non-conventional commit prefixes are parenthesised scopes:
  `feat(image):` — never `image:`.

## Open design questions — resolved in this plan

1. **Styled-text pipeline vs. a bypass.** Resolved: bypass entirely (see
   "Architecture" above) — `StyleRole`'s closed, themed vocabulary cannot
   express arbitrary per-pixel truecolor, and widening `StyleRole` itself
   to carry an escape hatch for "just this literal RGB" would leak a
   graphics-only concern into a type every other native feature's
   styled text also uses, the same kind of small drift this codebase's
   platform-engineering discipline exists to prevent. A new, narrow
   `LayerKind::Image` variant is the smaller, more correct surface.
2. **Capability detection: infer from `Tier::Full` or probe directly.**
   Resolved: **probe directly**, gated by `Tier::Full`. Rationale:
   `Tier::Full`'s existing definition (sync + truecolor + kitty keyboard
   protocol) says nothing about kitty *graphics* — some multiplexers/SSH
   hops pass every existing probe but strip APC sequences, so a terminal
   correctly classified `Full` today could still fail a real graphics
   probe. `Tier::Full` remains the gate on whether the attempt happens at
   all (never probe graphics on a `Basic`/`Standard` terminal, since the
   spec's own tier table already scopes kitty graphics to `full`); the
   new probe is the gate on which encoding is actually used.
3. **Half-block fallback resolution.** Resolved: upper/lower half-block
   characters (`▀`/`▄`) with independently set foreground/background
   truecolor per cell — doubling effective vertical resolution over a
   naive solid-color-per-cell rendering, at zero protocol cost (plain
   SGR truecolor escapes, already known-supported on every `Standard`-
   tier terminal per the existing tier table's "truecolor ANSI" line).
   Rejected: quadrant block characters (finer resolution, but no single
   Unicode block character expresses four independently colored
   quadrants — would require multiple escape codes per cell, more
   complex, marginal visual gain for a fallback path that is by
   definition the degraded case).
4. **Preview vs. full overlay: one code path or two.** Resolved: one
   encode path (`encode_image_layer`, Task 3), two call sites (Task 6
   picker preview, Task 7 tree hover) — both produce a `LayerKind::Image`
   at a different rect/z-order, never a second encoder. This mirrors how
   `Rows`/`overlay.rs` already serves picker, tree, statusline, prompt,
   and palette from one shared shape rather than five bespoke ones.

### Task 2: `native::image::decode` — pixel decode, no protocol awareness

**Files:** Create `crates/view-core/src/native/image.rs`; edit workspace
`Cargo.toml`.

**Rule bound:** no unwrap/expect/panic in lib crates (decode of an
arbitrary, possibly-corrupt file is exactly the kind of external input
this rule exists for); dependency direction (this module knows pixels,
never kitty-APC or half-block escapes — those are `view-tui`'s job,
Task 3).

**Design:** dependency choice — the `image` crate (the de facto standard
Rust image-decode crate, pure decode, no rendering/terminal awareness of
its own, satisfying "only view-tui touches the terminal" by construction
since this crate never touches a terminal at all) with a minimal feature
set enabled (PNG, JPEG, GIF-first-frame — the formats spec:621's charter
implies as baseline; WebP/others are an additive follow-up, not a v0.1
CORE gap, since the charter's own wording does not enumerate a format
list and PNG/JPEG covers the overwhelming majority of real files a
migration-audience user would open). `decode(path: &Path) -> Result<
DecodedImage, ImageError>` reads the file, decodes, and downsamples/
converts to a plain `Vec<Vec<(u8, u8, u8)>>` at a bounded maximum
resolution (Task 3's encoder further resamples to the actual terminal
cell grid at render time; decode's own cap exists only to bound memory
for a pathologically large source image, not to do the real resampling
work twice).

**Interfaces:**

```rust
pub struct DecodedImage {
    pub width: u32,
    pub height: u32,
    pub pixels: Vec<Vec<(u8, u8, u8)>>, // row-major, no alpha -- flattened
                                         // against a neutral background at
                                         // decode time, since terminal
                                         // cells have no alpha channel
}

#[derive(Debug)]
pub enum ImageError {
    Io(std::io::Error),
    UnsupportedFormat,
    Decode(String),
}

pub fn decode(path: &std::path::Path) -> Result<DecodedImage, ImageError>;
```

**Falsifiable check:** unit tests decode a known-good fixture PNG and
assert exact width/height and a handful of known pixel values (a
generated test fixture with a solid-color corner, asserted exactly);
a corrupt-bytes fixture asserts `Err(ImageError::Decode(_))`, never a
panic (the specific falsifiable claim this task's rule bound exists for).

- [ ] **Step 1:** `DecodedImage`, `ImageError`, `decode()`, dependency

- [ ] **Step 2:** Known-fixture pixel-value test.
- [ ] **Step 3:** Corrupt-input no-panic test.

### Task 3: `view-tui::image` — kitty-graphics and half-block encoders,
`paint_image`

**Files:** Create `crates/view-tui/src/image.rs`; edit `paint.rs`,
`view-surface/src/lib.rs`.

**Rule bound:** only view-tui touches the terminal (the entire reason
this task exists as a separate crate boundary from Task 2's pure decode).

**Design:** `LayerKind::Image(ImageView { pixels: Arc<DecodedImage> })`
(shared, not cloned per-frame — Task 1's decode result is reference-
counted into the layer so repaint on an unrelated screen change never
re-touches the pixel buffer). `paint_image(term_caps: &TermCaps, view:
&ImageView, rect: Rect) -> Vec<u8>` (raw bytes to write) branches on
`term_caps.kitty_graphics`: `true` → `encode_kitty(view, rect)` builds
the APC payload (`\x1b_Gf=100,a=T,...;<base64 RGB data>\x1b\\`, chunked
per the protocol's own size-per-chunk limit); `false` → `encode_halfblock
(view, rect)` resamples `pixels` to `rect.height * 2` rows (half-block
doubling) by `rect.width` columns via nearest-neighbor (simple, fast,
adequate for a terminal-cell-resolution target where sub-pixel accuracy
is moot) and emits `▀` per cell with SGR truecolor foreground/background
set from the two source rows it represents. `composite_into()` gains one
new arm calling `paint_image` and writing its returned bytes directly —
the same "match arm produces bytes, caller writes them" shape every
other `LayerKind` arm already follows.

**Interfaces:**

```rust
pub fn paint_image(caps: &view_core::model::TermCaps, view: &ImageView, rect: Rect) -> Vec<u8>;
fn encode_kitty(view: &ImageView, rect: Rect) -> Vec<u8>;
fn encode_halfblock(view: &ImageView, rect: Rect) -> Vec<u8>;
```

**Falsifiable check:** `encode_halfblock` unit test against a 2x2 known-
color `DecodedImage` and a 1x1-cell `rect` asserts the emitted byte
sequence contains the exact expected SGR truecolor codes for both source
rows' colors (proving the half-block path is byte-exact, not merely
"produces some output"). `encode_kitty` unit test asserts the APC
envelope's control-data segment (`f=100,a=T,...`) is well-formed and the
base64 payload round-trips (decode the base64, compare to the source
RGB bytes) — protocol conformance beyond this (a real kitty terminal
actually rendering it) is out of this task's falsifiable scope and
covered by Task 8's acceptance script instead.

- [ ] **Step 1:** `ImageView`, `LayerKind::Image`.
- [ ] **Step 2:** `encode_halfblock`, byte-exact unit test.
- [ ] **Step 3:** `encode_kitty`, envelope/payload round-trip unit test.
- [ ] **Step 4:** `paint_image`, `composite_into()` arm.
- [ ] **Step 5:** `task ci`. Commit: `feat(image): kitty-graphics and
  half-block encoders behind the composite_into() boundary`.

### Task 5: Kitty-graphics capability probe, `TermCaps.kitty_graphics`

**Files:** `crates/view-tui/src/tiers.rs`, `crates/view-core/src/
model.rs`.

**Rule bound:** performance is a contract (the probe joins the existing
single startup batch — `tiers.rs`'s `detect()` — rather than adding a
second round trip).

**Design:** a new APC query byte sequence (the kitty-graphics protocol's
own documented capability-check idiom: send a minimal 1x1 transmit-and-
query request, expect a structured OK/error reply) added alongside the
existing `QUERY_SYNC`/`QUERY_KITTY`/`QUERY_DA1_FENCE` constants in
`tiers.rs`, sent in the same batched write `detect()` already performs,
parsed by the same `scan_csi_replies`-adjacent reply-scanning logic
(extended, not duplicated, for the new reply shape) within the existing
`PROBE_DEADLINE` (50ms) — no new deadline, no new probe round trip.
`TermCaps` gains `kitty_graphics: bool`; `from_probe` sets it from the
new reply; `caps_for_override(tier)` (the manual `--tier` override path)
sets it `true` only for `Tier::Full`, since an explicit override forgoes
the real protocol probe entirely, and `Tier::Full` is the closest
available signal in that path.

**Interfaces:**

```rust
// crates/view-core/src/model.rs
pub struct TermCaps { pub sync: bool, pub truecolor: bool, pub kitty_kbd: bool, pub kitty_graphics: bool }
```

**Falsifiable check:** a scripted-reply unit test (using `tiers.rs`'s
existing `ReplySource` trait, already built for exactly this kind of
test) feeds a synthetic terminal reply containing the new probe's OK
response and asserts `TermCaps.kitty_graphics == true`; a reply omitting
it (or containing only the pre-existing three probes' replies) asserts
`false` — proving the new field is driven by the new probe's actual
reply, not defaulted `true` for every `Tier::Full` terminal regardless of
protocol support (the exact failure mode this design decision exists to
avoid).

- [ ] **Step 1:** New APC probe constant, added to `detect()`'s existing
  batched write.
- [ ] **Step 2:** Reply parsing extension, `TermCaps.kitty_graphics`,
  `from_probe`/`caps_for_override` wiring.
- [ ] **Step 3:** Scripted-reply falsifiable tests (present/absent).
- [ ] **Step 4:** `task ci`. Commit: `feat(image): kitty-graphics
  protocol probe joins the existing startup batch`.

### Task 7: Tree hover — new mechanism (no existing precedent)

**Files:** `crates/view-core/src/native/tree.rs`.

**Rule bound:** dependency direction (hover state is pure `view-core`,

nothing (this task does not build a generic tree-hover-preview-for-text

consistent with never de-scoping a named feature while also never
