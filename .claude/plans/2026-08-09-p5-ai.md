**Goal:** first-class AI — an ACP client speaking to any conforming agent, a
native panel, context providers, and diff review with buffer-truth safety
(spec §10, §10.1, §10.2; charter "an ACP client speaking to any conforming
agent, a native panel, context providers, and diff review with buffer-truth
safety").

**Architecture:** `view-ai` is the only crate that speaks ACP (JSON-RPC over
stdio to an agent subprocess), the only crate that owns a tokio runtime, and
the only crate that ever `.await`s anything in this workspace — mirroring
"only view-engine speaks [nvim] RPC" with an ACP-shaped twin: "only view-ai
speaks ACP." Every ACP wire type stays inside view-ai; view-core gains a
closed, rmpv/acp-crate-free vocabulary (`AiEvent`/`AiCommand`) exactly on
`RpcCall`'s own precedent ("core stays rmpv-free and an unencodable call is
unrepresentable"), so `Msg::Ai(AiEvent)` and `Effect::Ai(AiCommand)` are the
only things that cross the crate boundary, carried over a plain,
tokio-free channel the bin crate `view` wires at startup. The agent panel is
a `Surface`-native overlay (`OverlayKind::Ai`) that reads and renders
`AiEvent` history the same way every other native overlay reads its own pure
state — no Lua, no screen-scraping. Diff review is nvim-buffer-truth safety
machinery: agent-proposed edits arrive as ACP `oldText`/`newText` pairs,
view-ai (or view-core's diff engine, see Task 16) computes hunks, and only
`Effect::Rpc(RpcCall::BufSetText { .. })` ever touches buffer text — nvim
remains the sole owner, no exception, including for files with no open
window (Task 17's hidden-buffer path).

**Tech Stack:** `view-ai` gains its first real dependencies this phase:
`tokio` (async runtime, confined here per the spec decision log), an ACP
client crate or a hand-rolled JSON-RPC-over-stdio transport (Task 3 records
both options and the choice), `serde`/`serde_json` (ACP is JSON-RPC, not
msgpack — a new wire format this workspace has not carried before), and
`serde`/`toml` for `[ai]` config parsing (Task 5). Every one of these lands
with its `scripts/audit-deps.sh` row in the same commit as Task 1, before
any of them is used, per this plan's own early-task requirement. The bin
crate `view` gains a `view-ai` dependency (it has none today). Two further
third-party crates land inside `view-ai`, each in its own task's commit
with its own `scripts/audit-deps.sh` confinement row: an fs-watch crate for
Task 19 (`notify` — the workspace's not-yet-used, most-maintained option),
and an HTTP client for Task 7's checksummed adapter download. `notify`
belongs to `view-ai`, not the bin, because the watcher's lifetime is tied
to the session and the trust state `view-ai` owns; the HTTP client is
named at implementation time (the least-heavy maintained option the

## Global Constraints

Hard rules, embedded verbatim per planning-protocol step 8. Every task's
requirements implicitly include this section.

- nvim owns all buffer text. No view subsystem holds authoritative text
  state. Buffer mutation happens only through `Effect::Rpc`. **This phase's
  hardest test of that rule:** an agent process, not a view subsystem,
  proposes the edit — the rule holds exactly the same regardless of the
  edit's origin. No code path in `view-ai` or the diff-review overlay may
  write to a buffer any other way, including the hidden-buffer path (Task
  17) and the out-of-band conflict UI (Task 19). The client-side `fs/*`
  handlers (Task 18) are held to the identical rule: a loaded buffer's
  content, never disk, answers an agent's read, and a write to a loaded
  buffer lands only via `Effect::Rpc`.
- The paint loop never awaits RPC. The RPC reader thread never blocks. This
  phase extends the rule to ACP traffic: the paint loop and the runtime
  executor never await anything `view-ai` does, and `AiSession::send`
  (Task 3) is non-blocking by construction — it queues onto a channel a
  tokio task drains, never a synchronous call into the agent process.
- No unwrap/expect/panic in lib crates (workspace lints enforce; do not
  weaken them). Test modules may open with
  `#![allow(clippy::unwrap_used, clippy::expect_used)]`.
- Dependency direction: core ← surface ← {native, ai}; only view-engine
  speaks RPC; only view-tui touches the terminal. This phase adds: **only
  view-ai speaks ACP** (the JSON-RPC-over-stdio protocol to agent
  processes) and **only view-ai owns a tokio runtime** — no other crate may
  depend on tokio, async-std, or smol, per the spec decision log
  ("Runtime model, amended at P1 exit"). `scripts/audit-deps.sh` enforces
  the matrix; any new crate or edge lands with its audit row in the same
  commit.
- Performance is a contract: any change touching key dispatch, grid apply,
  or paint states its latency consequence in the commit description. Tasks
  that touch none of the three (config parsing, adapter provisioning,
  registry/doctor rows, oracle coverage, the wire-capture docs) commit
  without a latency statement; every task that touches key dispatch, grid
  apply, or paint carries the statement in its own commit step.
- `serde`/`toml` and now `serde_json`/`tokio` stay allowlisted per crate:
  `scripts/audit-deps.sh` confines them to the crates that genuinely need
  them (`check_absent` on every pure layer; `view-core` stays free of all
  four). `serde_json` has no row in the script today at all, so Task 1
  creates one rather than asserting a confinement nothing enforces: a
  `check_absent` line on every pure layer plus a `check_transitive_reach`
  allow-list, on the same two-mechanism shape `serde`/`toml` already carry.
  This phase widens the allowlist for `view-ai` exactly once, in Task 1,
  before any later task needs it — and widening a `check_absent` loop is
  never sufficient on its own: `check_transitive_reach` enumerates every
  workspace member that reaches a crate in the *resolved* graph and fails
  for any member not on its allow-list, so a crate newly declaring `serde`
  or `toml` must be added to both. Task 1's exact diff does both.
- Every third-party crate this phase adds lands with a `check_absent`
  confinement loop naming the crates that must *not* declare it, in the
  same commit that adds it: `notify` (Task 19) and Task 7's HTTP client
  are confined to `view-ai`; `similar` (Task 16) is confined to
  `view-core`. A crate with no row passes `task audit` silently — the
  deny-list is presence-based, so an unrowed dependency is an unenforced
  one, not a permitted one.
- Use `task` targets, never raw cargo/git, for build/fmt/lint/test/commit.
  Commit only via `task commit -- -m "<msg>"`.
- Production files stay under 1000 production LOC (`task loc`); split
  before a file approaches the ceiling. Three files are on course to hit
  it, and all three are split up front rather than after the ceiling
  trips:
  - the diff-review hunk engine — `native/diff/hunk.rs` (old/new pair to
    hunks, stale detection) vs. `native/diff/rebase.rs` (live rebase
    against buffer-change events);
  - the ACP session/transport layer — `acp/wire.rs` (codec, framing,
    JSON-RPC envelope) vs. `acp/session.rs` (lifecycle and method

  - **the agent panel**, which has more inbound tasks than either of the

    scale sits alongside `crates/view-core/src/native/supervision.rs`,
    1265 lines with fewer responsibilities. It is created as a module

- Comments are WHY-only; doc comments render for users and carry a WHAT

**ACP protocol version pin: v1 (`protocolVersion: 1`).** ACP currently has
two coexisting surfaces: v1 (stable, the version the maintainers say to
ship in production) and v2 (draft, published 2026-07-20, explicitly not yet
default-safe). This plan targets **v1 only**. The reason is not caution for
its own sake: v1 represents a file edit as a whole-file `oldText`/`newText`
pair; v2 replaces it with a `changes`-operation list plus an optional
`git_patch`, and the ACP docs state there is **no mechanical mapping from
v2 diffs back to `oldText`/`newText`**. Diff review's hunk-by-hunk
accept/reject machinery (Task 16) is built against the v1 shape; a v1 pin
is what keeps that machinery meaningful. v2 is a recorded future-migration
note (capability negotiation, per §1.9 of the research package, is the
mechanism a later phase would use to add it without a version branch at
every call site), never a Task in this plan. Every ACP call site, wire
capture, and test fixture in this plan targets v1 verbatim method/field
names; a v2 method or field appearing anywhere in this plan's task text
would be a plan defect.

**Pin re-verified 2026-08-18 against live docs (the charter's MANDATORY
planning-time step, discharged here rather than deferred to Task 2).** The
charter requires the ACP surface be re-verified against current docs at
plan time because "the protocol is young and churns"; this plan was
authored 2026-08-09 and the re-verification was run 2026-08-18 via the
Context7 MCP server against `/agentclientprotocol/agent-client-protocol`
plus direct fetches of `agentclientprotocol.com/protocol/schema` and
`agentclientprotocol.com/announcements/acp-v2-draft`. All three
load-bearing claims above hold unchanged:

1. **v1 is still the stable, production surface.** The v2 draft
   announcement (published 2026-07-20, unchanged) tells implementers to
   "support both versions side by side" because "v1-only peers will remain
   common for some time."
2. **v2 is still draft and still not default-safe.** Verbatim from the
   same announcement: "v2 is a Draft... various pieces can, and will,
   change before stabilization," and "gate your implementation behind the
   version negotiation **AND** feature flags. Don't ship it by default in
   production until we are closer to stabilization." The docs repo's own
   v2 pages still sit under a `draft/` path.
3. **v2 diffs still do not map mechanically back to `oldText`/`newText`.**
   v2 replaces the v1 `{ path, oldText, newText }` diff with a
   `changes` list of file-level operations (add/delete/modify/move/copy,
   plus binary and non-text cases) and an *optional* `patch` object
   (`{ format: "git_patch", text }`). The `changes` list is the
   authoritative field and clients "must be capable of handling diffs
   where the patch is omitted or null" — so a v2 diff carries neither the
   before-text nor, in general, any patch text at all, and reconstructing
   the v1 pair would require reading the file and applying a patch that
   may not have been sent. The v2 migration page states the direction
   plainly: migrating clients "requires moving away from the old
   text-based diff mapping."

Nothing in the re-verification changes the pin. Task 2 remains the
implementer-side capture of the exact v1 enum strings and field spellings
(a different obligation: this paragraph pins the *version choice*, Task 2

## Design questions resolved (planning protocol step 6, applied ahead of
## implementation rather than left open)

The research package (`p5-research.md` §4) raised six open questions.
Resolved here, decisions binding on every task below:

1. **Where does the agent panel sit in the focus-stack model?**
   `OverlayKind::Ai(AiPanelState)`, following `OverlayKind::Tree`'s shape:
   anchored (not centered), non-modal, coexists with an active engine
   buffer, pushed like `Tree`/`Picker` with the same beneath-a-blocked-
   prompt fallback. Adopted as researched: the spec's own language ("agent
   as a peer subsystem," "toggled via a real nvim mapping like every native
   feature") describes a persistent sidebar, not a modal, and `Tree` is
   already the working precedent for exactly that shape. See Task 8.
2. **Does `[ai]` get a `FeatureDesc` registry entry, or a parallel
   mechanism?** A parallel mechanism: a small `AiStatus` struct
   (`crates/view-core/src/native/ai_registry.rs` or a peer module — Task 9
   names the exact path) distinct from `FeatureDesc`. Adopted as
   researched: `FeatureDesc::id`'s doc comment hard-codes "the `[native]`
   table key," and `[ai]` is a sibling top-level table per spec §11, not a
   `[native]` key — forcing it into `FeatureDesc` would make that doc
   comment a lie the day this ships. P6's doctor charter already expects
   "feature/supersession states" and "agent sessions" as *separate* doctor
   rows, which is two mechanisms by the charter's own design, not one.
3. **Where does `[ai]` table parsing live?** `view-ai` gets its own
   `serde`/`toml` dependency and owns `[ai]` parsing itself, mirroring
   `view-native`'s `[native]` precedent exactly (`ViewFile` struct,
   deny-unknown-key resolution, example-config drift tests) rather than
   splitting the work between the bin crate and a pure `view-core` type.
   **Diverges from the research package's stated preference** ("the second
   option [bin-crate parsing] costs less audit-deps.sh churn"). The
   tie-break the research flagged (churn) does not hold once the tree is
   read: `scripts/audit-deps.sh` lines 68–76 give the *architectural*
   reason `view-native` owns `[native]` parsing rather than the bin —
   "parsing it in the bin instead would put the schema and its error
   messages where neither `view-native`'s tests nor the oracle can reach
   them." That reasoning is not native-specific; it applies to `[ai]`
   verbatim, since `[ai]` is equally a shipping user surface (spec §11).
   Bin-crate parsing would repeat the exact anti-pattern the comment
   argues against, to save two `check_absent`/`check_transitive_reach`
   lines this plan is already touching in Task 1 for `tokio`. The literal
   audit-deps.sh churn is not equal once that's weighed, so the tie-break
   does not apply. `view-core` stays free of `serde`/`toml` either way — no
   task in this plan gives it either.
4. **Exact `PermissionOption`/`RequestPermissionOutcome` wire enum
   strings.** Pinned from `schema.json` at implementation time, never
   guessed — Task 2 is the wire-capture task that does this before any
   later task consumes the enum, per planning-protocol item 1 ("wire facts
   are captured, never recalled").
5. **`nvim_buf_attach` change-event plumbing: reuse `Msg::BufferChanged` or
   add new vocabulary?** New vocabulary — resolved, not left open. Reading
   `Msg::BufferChanged`'s as-built payload
   (`crates/view-core/src/msg.rs:270-273`: `{ name: String, modified: bool
   }`) settles this: it is sourced from a narrow autocmd bridge trigger
   group (`BufEnter`/`BufFilePost`/`BufWritePost`/`BufModifiedSet`) built
   for the statusline's file segment, and it structurally cannot carry a
   `nvim_buf_attach` change event's line-range/changedtick payload — there
   is no field for `firstline`/`lastline`/`linedata`/`changedtick`, and
   widening it to carry them would turn a statusline-only signal into an
   overloaded one two unrelated consumers must now both interpret
   correctly. Task 15 adds `Msg::BufTextChanged` (a new, `#[non_exhaustive]`
   variant carrying nvim's own change-event shape verbatim) and
   `RpcCall::BufAttach`/`BufDetach`, on the same "P4 extends the
   vocabulary, never the loop" precedent the charter already names.
6. **Undojoin batching granularity: one undo step per hunk, or per whole
   accept action?** One undo step per accepted hunk. Adopted as researched:
   this is what a user's `u` keypress should feel like stepping backward
   through, and it is the finer-grained of the two readings of "one undo
   step per accept" — the plan's task-level spec (Task 14) states this as
   the literal acceptance criterion so it cannot drift to whole-diff
   granularity during implementation. A multi-hunk "accept all" action
   issues one `Effect::Rpc(RpcCall::BufSetText { undojoin: true, .. })` per
   hunk in sequence, each undojoined onto the previous, so `u` after an
   accept-all still steps hunk by hunk.

   **Corrected 2026-08-21.** The answer above is what was researched and it
   is not what the engine can do: `:undojoin` merges into the previous
   entry by construction, so a chain of joined calls is one entry and
   per-hunk stepping is not representable with it at all. The as-built
   contract is one undo entry per review -- the first accept opens it,
   every later accept joins it, and a single `u` retracts the whole
   review. Spec §10.1 carries the same correction.

    /// the process (spec decision log). `emit` forwards a decoded `Msg`
    /// into the caller's loop channel; it runs on a tokio task thread,
    /// never the paint thread, and must never block, which a plain
    /// unbounded channel send satisfies.

    `TrustStore::set_trusted` and feeds the outcome back into the loop as

**How the trust fact reaches `update()`, and why it is not a function
call.** The gate fires inside `Msg::FeatureInvoke`'s dispatch arm
(`crates/view-core/src/update/mod.rs:199`) and pushes an overlay via
`Model::push_overlay` (`crates/view-core/src/model.rs:388`) — both in
`view-core`. `TrustStore` lives in `view-ai`, and
`scripts/audit-deps.sh:19-21` forbids `view-core` from depending on
`view-ai` (Global Constraints restate the direction). So `update()` can
never call into the trust store, directly or transitively. It does not need
to: **trust is plain data on the `Model`**, exactly like every other fact
the bin resolves and the core reasons over.

- `crates/view/src/main.rs` loads the `TrustStore` at startup and seeds
  `model.ai_trusted` for the session's `cwd` before the loop begins, the
  same way it already seeds terminal capabilities and cwd.
- `update()` reads that `bool` and nothing else.
- The user's answer leaves the core as `Effect::AiTrustSet { project_root,
  trusted }`. The bin's effect executor (`crates/view/src/runtime.rs`, the
  same place `Effect::ClipboardRead` and `Effect::Osc52Copy` are executed)
  is the only code that touches `TrustStore::set_trusted`.
- The executor feeds the persisted result back as `Msg::AiTrustResolved {
  trusted }`, which `update()` folds into `model.ai_trusted`. A store write
  that fails surfaces as `trusted: false` plus a toast, never a silent
  in-memory trust the next process start would forget.

No `view-ai` type is named anywhere in `view-core`: the crossing is one
`bool` out and one `bool` back, on the closed-vocabulary shape this plan
already uses for the ACP boundary.

**Consumer call-site first.** Two placements for the trust gate considered:

```rust

    /// (`$XDG_STATE_HOME/view/trusted-projects.toml`, or the platform's
    /// own state-directory equivalent). Keyed by the project root's

    /// the same directory must trust or distrust together.

/// Canonicalizing containment check: resolves both `root` and `candidate`
/// (symlinks and `..` components included) before comparing, so a
/// trusted-root escape via a symlink planted inside the project or a
/// literal `../` in an agent-supplied path is caught the same way -- a
/// prefix comparison over un-resolved paths would miss both. `Ok(false)`
/// (never an `Err`) is the answer for "resolves outside `root`"; `Err`
/// is reserved for a candidate that cannot be resolved at all (e.g. a
/// dangling symlink), which callers treat as refused all the same.
/// Free function, not a `TrustStore` method: no store state is needed,
/// and both the read and the write side of an agent's file access run
/// this on every request, whether or not a `TrustStore` instance happens
/// to be in scope. A client that advertises safe file access must not let
/// a read reach further than a write may.
pub fn path_is_contained(root: &Path, candidate: &Path) -> Result<bool, TrustError>;

unconditionally. Diff review's own hold follows the identical pair: it
increments once on `AiEvent::DiffProposed`'s hidden-buffer open and
releases once when its last hunk resolves (a hunk still `Fresh`/`Stale`
when the panel closes leaves that hold in place, exactly as before).

two of Task 18's own opens) stack safely on the same path: the buffer
survives until every holder has released, whichever order they finish in.

/// Increments `path`'s in-flight refcount (creating the buffer first if
/// this is the first holder) and returns whether this call was the
/// creator. Never deletes anything -- deletion is `release_hidden`'s
/// job alone, once every holder has released.
pub fn load_hidden(path: &Path) -> Result<(BufferHandle, Created), EngineError>;
/// Decrements `path`'s in-flight refcount; deletes the hidden buffer
/// (`nvim_buf_delete`) iff the decrement brings the count to zero. Every
/// `load_hidden` call has exactly one paired `release_hidden` call,
/// whether it created the buffer or reused an existing hold.
pub fn release_hidden(path: &Path) -> Result<(), EngineError>;
```

### Task 18: ACP `fs/*` handlers — client answers agent-initiated file reads/writes through nvim

**Why this task exists.** Task 4 advertises `clientCapabilities.fs.{read
TextFile,writeTextFile}`; until something answers the corresponding
Agent→Client JSON-RPC requests, that advertisement is a lie an agent can
act on. This task is the handler, and the only task that flips both flags
to `true` — same commit, not a step ahead.

**Opening contract (fix round 3): reads and writes share one trust
boundary and one hidden-buffer safety mechanism, by design.** A client
advertising "safe" file access must not let a read reach further than a
write may — `fs/read_text_file` gets the **identical**
`trust::path_is_contained` gate `fs/write_text_file` already had,
refused before either handler touches a buffer, no exception and no
config-driven relaxation in v0.1 (decision + rationale below). And
because both handlers can open the *same* never-opened path concurrently
(nothing in ACP or in `view-ai`'s async handling serializes two
overlapping tool-loop calls), the hidden-buffer path they share is
refcounted, not merely gated on "did I create it" — a second bullet below
replaces round 2's `Created`-gated unload with Task 17's `release_hidden`.

`session.trusted_project_root()` is a value `AiSession` was handed at spawn
by the bin crate, which is the only place a `TrustStore` is ever read
(Task 6). `view-ai` reads its own `trust.rs` free function here, never the
core's `Model`, and `view-core` still names nothing from `view-ai` — the
two halves of the trust boundary sit on their own sides of the crossing.

**The crossing, restated (fix round 2's blocker).** `view-ai` can never
name a `view-engine` type (`check_absent view-ai view-engine`, Task 1) and
the `EngineRequest`/`ReplyToken`/`ReplyValue` pattern (`msg.rs:499`, `:530`,
`:589`) is the *opposite* direction — it lets nvim block on a client-side answer
(clipboard), not the other way around. The only legal crossing between
`view-ai`'s async world and the sync engine is the closed `AiEvent`/
`AiCommand` vocabulary, and the request-reply shape it needs is already
there: Task 3 lands all four variants as part of the closed vocabulary, so
this task adds handlers and plumbing, never an enum arm.
`AiEvent::FsReadRequested`/`FsWriteRequested` cross view-ai → core and
`AiCommand::FsReadReply`/`FsWriteReply` cross core → view-ai, each
carrying a `request_id` `view-ai` alone correlates against
a `oneshot` channel it alone owns (`AiSession`'s `PendingFsReplies` map,
Task 3). The sync side never touches that map or any tokio type — it only
ever sees `RpcCall::AiFsRead`/`AiFsWrite` and their `Msg::AiFsReadReply`/
`AiFsWriteReply` replies, the same "fire an `Effect::Rpc`, the reader
thread decodes the completion into a plain `Msg`" shape `RpcCall::
PreviewBuffer` (`msg.rs:1031`) and `Msg::PickerPreviewReply`
(`msg.rs:318`) already establish.

**Read-path trust boundary, decided (fix round 3, Important 1).** As
designed through round 2, `handle_read_text_file` had no containment
check at all — an agent could read `~/.ssh/id_ed25519` or `/etc/passwd`
through a capability view itself advertises as safe. Fixed by giving
reads the same gate writes already had (see call-site below); the
remaining question is whether any relaxation should exist — e.g. an
`[ai]` config key naming additional readable roots outside the project
(a monorepo's sibling package, a shared vendored dependency). **Decision:
none in v0.1.** No charter or spec item names a cross-root read
requirement, and the config-derivability rule (Hard Rule 10) cuts against
inventing a knob nothing yet needs — a hand-written extra-roots list is
exactly the kind of user-supplied config that drifts and silently
broadens the trust boundary it was meant to bound. The single trusted
project root (Task 6) is the only readable root in v0.1; recorded as a
deferred candidate in Non-goals below (an `[ai] additional_read_roots`
key, default empty, would be the natural v0.2+ shape if a real need
surfaces) rather than silently absent from consideration.

**Consumer call-site first:**

```rust
// crates/view-ai/src/acp/fs.rs -- runs on view-ai's own tokio task,
// answering an Agent->Client JSON-RPC request. Crosses back into the sync
// engine ONLY through the closed AiEvent/AiCommand vocabulary: no
// view-engine type appears anywhere in this file, and the
// EngineRequest/ReplyToken/ReplyValue pattern is never reused here, since
// that mechanism blocks nvim on the client rather than view-ai on nvim.
pub async fn handle_read_text_file(req: ReadTextFileParams, session: &AiSession)
    -> Result<ReadTextFileResponse, AcpError> {
    // containment is the first action in both handlers, before a request id
    // is allocated or any event is emitted, so a refused path never reaches
    // a buffer branch and no file content can leave in the error reply
    let root = session.trusted_project_root();
    if !trust::path_is_contained(&root, &req.path).unwrap_or(false) {
        return Err(AcpError::path_outside_trust_boundary(&req.path));
    }
    let (request_id, rx) = session.register_fs_reply();
    session.emit(AiEvent::FsReadRequested { request_id, path: req.path.clone() });
    let result = rx.await.map_err(|_| AcpError::session_ended())?;
    result.map(|content| ReadTextFileResponse { content }).map_err(AcpError::from)
}
pub async fn handle_write_text_file(req: WriteTextFileParams, session: &AiSession)
    -> Result<(), AcpError> {
    let root = session.trusted_project_root();
    if !trust::path_is_contained(&root, &req.path).unwrap_or(false) {
        return Err(AcpError::path_outside_trust_boundary(&req.path));
    }
    let (request_id, rx) = session.register_fs_reply();
    session.emit(AiEvent::FsWriteRequested { request_id, path: req.path, content: req.content });
    rx.await.map_err(|_| AcpError::session_ended())?.map_err(AcpError::from)
}
```

Both handlers run the identical `path_is_contained` gate as their very
first action, before `register_fs_reply` or `emit` run — the read
branch's refusal never allocates a `request_id`, never touches
`PendingFsReplies`, and never emits `AiEvent::FsReadRequested`, so no
buffer branch executes and no file content is ever read off of `path` in
the first place ("no content leaves" is true by construction, not merely
by the reply carrying no `content` field).

**Interfaces:**

```rust
// crates/view-core/src/msg.rs -- the sync-side mirror of the
// AiEvent/AiCommand fs pair; core's update() translates one into the other
// with no I/O of its own, exactly like every other RpcCall arm
RpcCall::AiFsRead { request_id: u64, path: String },
RpcCall::AiFsWrite { request_id: u64, path: String, content: String },

/// The reader thread's decoded answer to RpcCall::AiFsRead/AiFsWrite,
/// following PickerPreviewReply's own "reply decodes on the reader
/// thread and routes back as a plain Msg" contract -- never a blocking
/// completion, never routed through ReplyToken/ReplyValue.
Msg::AiFsReadReply { request_id: u64, result: Result<String, FsError> },
Msg::AiFsWriteReply { request_id: u64, result: Result<(), FsError> },
```

**The round trip, numbered** (read side; write is symmetric, substituting
`AiFsWrite*`/`BufSetText` for `AiFsRead*`/`nvim_buf_get_lines`):

0. Both handlers run `trust::path_is_contained(root, path)` as their
   first action (call-site above); a refusal returns a JSON-RPC error
   directly from the `async fn` and the round trip below never starts —
   no `request_id` allocated, no `AiEvent` emitted, no buffer touched.
   Stated as step 0, not folded into step 1, because it is the one point
   in this sequence that runs entirely inside `view-ai` with no crossing
   at all — nothing here needs the round trip's non-blocking machinery.
1. Agent sends `fs/read_text_file` over ACP; `acp/fs.rs::handle_read_text_file`
   decodes it on `view-ai`'s tokio task.
2. The handler allocates `request_id`, registers a `oneshot::Receiver` in
   `AiSession`'s `PendingFsReplies` map (Task 3), and calls the same
   `emit(AiEvent::FsReadRequested { request_id, path })` every other
   `AiEvent` already goes through — `emit` takes the `AiEvent` and wraps it
   in `Msg::Ai` itself, so the handler names no other `Msg` arm. No new
   plumbing, no new thread.
3. Core's `update()` (pure, sync, running on the paint/key-dispatch thread)
   matches `Msg::Ai(AiEvent::FsReadRequested { .. })` and emits
   `Effect::Rpc(RpcCall::AiFsRead { request_id, path })` — fire-and-forget,
   exactly like `RpcCall::PreviewBuffer`; `update()` returns immediately,
   satisfying "the paint loop never awaits RPC."
4. The effect executor hands the call to `view-engine`; `handle.rs`'s call
   site resolves `path` exactly as `PreviewBuffer` already does — a loaded
   buffer wins (`nvim_buf_get_lines`), otherwise Task 17's `load_hidden`,
   which increments `path`'s in-flight refcount (round 3, Important 2 —
   replaces round 2's bare `Created::Yes`/`No` unload gate; see the
   lifecycle section below for why) — issued on the RPC writer/reader
   pair, never the paint thread. This is itself 1-2 further async nvim
   RPC round trips (`nvim_create_buf`+read, if the path had no open
   window), each with its own reply Waiter (`EngineHandle`'s existing
   `Waiter` map, `crates/view-engine/src/handle.rs`) — never a single
   atomic operation, which is exactly why step 4 and step 5 below are not
   safe to treat as one indivisible unit against a second, overlapping
   call for the same path.
5. The reader thread decodes the completion, calls Task 17's
   `release_hidden(path)` (decrementing the refcount; the buffer is
   deleted only if this call's release brought the count to zero — never
   unconditionally, per the lifecycle section), and produces
   `Msg::AiFsReadReply { request_id, result }`, routed back into
   the ordinary loop channel — the RPC reader thread never blocks per
   Global Constraints.
6. Core's `update()` receives `Msg::AiFsReadReply` and emits
   `Effect::Ai(AiCommand::FsReadReply { request_id, result })` — the
   existing `Effect::Ai` executor path (Task 3) forwards it to
   `AiSession::send`, non-blocking by the same contract every other
   `AiCommand` already has.
7. `AiSession`'s internal tokio task receives it, removes `request_id`
   from `PendingFsReplies`, and fires the stored `oneshot::Sender`.
8. `handle_read_text_file`'s `rx.await` (step 1's call site — holding
   nothing the panel's render path needs; no lock shared with
   `AiPanelState`) resolves; the transport writes the JSON-RPC response
   back to the agent.

**Latency consequence.** Non-blocking at both boundaries by construction,
not convention: the paint loop never awaits the reply — steps 3 and 6 are
plain `Effect` emissions from `update()`, which returns immediately every
time, while the effect executor and the RPC reader thread do the actual
I/O off that thread. `view-ai`'s async handler (step 8) awaits only its
own `oneshot::Receiver`, holding no lock the panel's render path
(`AiPanelState`, Task 8) or the engine's executor needs, so a slow agent
never stalls a redraw. The one place latency is visible is where ACP
already expects it: the agent's own JSON-RPC call blocks on `view-ai`'s
tokio side until step 8 — same as every other Agent→Client request in
this protocol, and no new category on key dispatch, grid apply, or paint.

**Hidden-buffer lifecycle for standalone fs callers (round 2 Important 1,
refcounted in round 3 to close Important 2).** Task 17's diff-review
cleanup fires only when its last hunk resolves; a plain
`fs/read_text_file`/`fs/write_text_file` call has no diff-review state to
tie into, so this task defines its own. Round 2's answer — unload
immediately if `load_hidden` reported `Created::Yes` for this call, never
touch a `Created::No` buffer — was gated on a false assumption: that one
call's "create-or-reuse, act, delete-if-I-created-it" sequence runs as an
indivisible unit no other call can interleave with. Step 4 above shows
that's false: `load_hidden` and the eventual cleanup are separated by 1-2
independently-tracked async nvim RPC round trips (each own `Waiter` map
entry in `EngineHandle`), not one atomic operation — so a **second**
`fs/read_text_file`/`fs/write_text_file` for the *same never-opened path*,
arriving while the first is still mid-flight (nothing in ACP or
`view-ai`'s async dispatch prevents an agent's tool loop from issuing two
overlapping calls), can call `load_hidden` for that path before the
first call's cleanup runs. Under round 2's design this is a real bug: if
call A saw `Created::Yes` and call B (arriving concurrently) saw
`Created::No` because A's buffer already existed by the time B's
`load_hidden` ran, A's completion unconditionally deletes the buffer
(it created it) while B may still be reading from or writing to it —
B then either errors against a buffer that no longer exists or, worse,
silently operates on a stale handle.

**Fixed by making Task 17's hidden-buffer lifecycle a refcount, not a
boolean.** `load_hidden` increments an in-process, per-path counter on
every call (returning `Created::Yes`/`No` unchanged, now purely
diagnostic — "did I create it," not "am I allowed to delete it"); a new
paired function, `release_hidden(path)`, decrements that counter and
deletes the buffer only when the decrement brings it to zero. Diff review
(Task 17) and Task 18's standalone handlers call the identical pair —
diff review's own hidden-buffer open increments on `AiEvent::DiffProposed`
and releases when its last hunk resolves; Task 18's step 4/5 increments
on `load_hidden`, releases in step 5 after the RPC completes. Two
concurrent standalone calls for the same path, or a standalone call
overlapping a diff review's hold, safely stack: the buffer is deleted
only once every holder has released, in whatever order they finish —
proving the race by construction rather than by an unverifiable claim
that the two calls never overlap.

### Task 21: Real-agent conformance script + streaming/session budgets (exit gate)

**Files:**
- Create: `scripts/ai-conformance.sh` (or the equivalent location the
  tree's existing `scripts/compat-*`/conformance scripts establish as
  convention — verified at implementation time)
- Modify: `crates/view-bench/budgets.toml`,
  `crates/view-bench/baselines/dev-linux.toml`,
  `.claude/specs/2026-07-17-view-design.md` (two new §3.1 budget rows —
  see below; this is a spec amendment, not an incidental edit)

**Why this is the phase's own capstone task, last by design:** every prior
task is exercised individually by its own unit/engine-seam tests; this task
is the one place the charter's exit-gate language ("a real agent, not a
mock, exercised end to end") gets checked, and it is the natural place to
also pin the "budgets hold with an active AI session" measurement, since
the script's own run is what puts a session in the state the budgets must
be measured under.

**Conformance script covers, against a real ACP-speaking agent binary
(pinned per Task 7's adapter table, not a hand-rolled mock):**
1. session init (`initialize` → `authenticate` if required → `session/new`)
2. a prompt whose response streams via `session/update` and renders
   incrementally in the panel (Task 11)
3. a tool-call status update rendering as non-terminal → terminal per
   ACP's own status vocabulary
4. a diff proposal, accepted through Task 16's UI end to end (buffer state
   asserted, per Task 20's oracle-style assertion, not just "no crash")
5. a second diff proposal, rejected — buffer state unchanged
6. `session/cancel` mid-turn — asserts the ACP cancellation contract's both
   halves (Task 13): a pending permission (if any) resolves `Cancelled`,
   the original prompt's promise resolves `stopReason: "cancelled"`
7. a deliberately crashed agent subprocess — panel surfaces the crash
   locally (Task 13's non-toast persistent slot), paint loop never stalls,
   verified by a frame continuing to render within the budget window
   immediately after the crash
8. a permission-overlap scenario against the real agent (Task 12,
   Important 2): the agent issues a second `session/request_permission`
   before the first is answered; the second request receives, within a
   bounded wait, exactly the reply shape Task 2's Step 5 pinned as
   conformant, and `pending_permission`'s first slot/prompt is unaffected
   — the real-agent counterpart to Task 12's own stub-agent unit test,
   proving a real reference agent tolerates the pinned reply shape rather
   than hanging or erroring out its whole session

**Latency consequence / budgets:** two new budget rows record that key-
dispatch and paint-apply latency (the existing budget categories) hold
their current thresholds when measured with an active AI session present
(panel open, a turn in flight) versus the existing session-absent
baseline — this is the exit gate's explicit performance requirement (the
mandate that "AI presence never degrades editor responsiveness" cannot be
asserted from Tasks 1–20's unit-level tests alone; only a budget row
measured under a live session proves it).

**A new budget row is a spec amendment, not a file edit.**
`scripts/check-budget-drift.sh` fails CI unless every `[[budget]]` entry's
`spec_row` string appears verbatim in `.claude/specs/2026-07-17-view-design.md`
and its `max` appears as a number in that same spec row. The spec is the
pinned source and the budget file is the machine-readable restatement, so
the two new rows cannot land in `budgets.toml` alone: §3.1 gains two rows in
the same commit. Spec wins on conflict, which is why this is decided here
rather than left to implementation.

The schema is `spec_row`/`scenario`/`metric`/`max`, plus an optional
`classes` (`crates/view-bench/budgets.toml:47-52`) — there is no `name`
field. The two entries take this shape, with `max` transcribed from the
recording run's own recorded baselines:

```toml
# crates/view-bench/budgets.toml
[[budget]]
spec_row = "view input path, AI session active: key event read from the terminal -> RPC bytes written"
scenario = "ai_session_active"
metric = "key_to_rpc_p99_us"
max = 0.0                        # transcribed from the recorded baseline
classes = ["controlled-linux"]

[[budget]]
spec_row = "view output path, agent response streaming: redraw event parsed -> terminal write"
scenario = "ai_streaming"
metric = "p99_ms"
max = 0.0                        # transcribed from the recorded baseline
```

`classes = ["controlled-linux"]` on the input-path row mirrors the scope its
session-absent counterpart already carries: the budget table is loaded only
on a controlled class, so a row pointed at `dev-linux` could never fire. The
recording run still happens on the dev-linux matrix — that is where the
baseline comes from; the gate that reads it is the controlled one.

"Never hand-typed" and "the drift gate needs the number in the spec" are not
in tension once the order is fixed: **measure, then transcribe once into two
places in one commit.** The threshold is never invented, and it is never
written into `budgets.toml` without the same value going into the spec row
the same entry names.

The corresponding §3.1 rows follow the table's existing `| Metric | Budget |
Measured how |` shape, each Budget cell carrying the measured number so the
drift check can find it, and each stating plainly that it exists to hold the
"AI presence never degrades editor responsiveness" mandate to a measurement
rather than an assertion.

**Falsifiable check:** running the conformance script against a
deliberately broken build (e.g., Task 13's cancel contract half-reverted)
fails at the specific assertion for that half, not a generic timeout —
proving each of the 8 steps above is independently falsifiable, not one
big "did it not crash" check.

- [ ] **Step 1:** Write the script against Task 7's pinned adapter,

- [ ] **Step 3:** Record the two new budget baselines on the dev-linux

- [ ] **Step 4: Amend spec §3.1 and `budgets.toml` together.** Add the two

## Non-goals (v0.1 scope line — recorded, not dropped)

These are explicit exclusions from the spec's v0.1 scope line (§10), each
recorded here as a deferred candidate for a later phase, never silently
absent from consideration:

- **Inline ghost-text completions.** The agent panel (Task 8) and diff
  review (Task 16) are the only v0.1 AI-editing surfaces; an inline,
  cursor-adjacent suggestion UI is a distinct interaction model the spec
  places outside v0.1. Candidate for a post-P5 phase, not this plan.
- **Multi-agent orchestration.** `AiConfig`/`AgentSpec` (Task 5) name one
  agent per session; running multiple agents concurrently, or one agent
  supervising another, is out of scope for this plan's `AiSession` shape
  (Task 3), which is deliberately singular.
- **Embedded model serving.** view launches an external ACP-speaking agent
  subprocess (Task 4); it never hosts or serves a model itself. This
  boundary is structural (only `view-ai` speaks ACP to a subprocess it
  spawned) and is not expected to change.
- **Cross-root `fs/*` reads.** Task 18's read-path trust decision (fix
  round 3, Important 1): `fs/read_text_file`/`fs/write_text_file` are
  bounded to the single trusted project root (Task 6) with no
  relaxation, config or otherwise, in v0.1 — no charter/spec item names a
  cross-root read requirement, and inventing an unused config knob
  contradicts the config-derivability rule. If a real need surfaces (a
  monorepo sibling package, a shared vendored dependency), the natural
  v0.2+ shape is an `[ai] additional_read_roots` key (default empty
  `Vec<PathBuf>`, each entry canonicalized and `path_is_contained`-checked
  the same as the project root) — recorded here so the option is not
  silently absent from consideration, not designed further until needed.
