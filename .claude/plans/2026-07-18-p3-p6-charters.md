# P3-P6 Phase Charters

Boundary-level charters, deliberately free of signatures and task decomposition.
Each phase gets its full task-level plan (P0/P1 format: bite-sized TDD tasks,
complete code, no placeholders) authored at its boundary, against the real
interfaces the previous phase produced. Spec of record:
`.claude/specs/2026-07-17-view-design.md`; on conflict the spec wins.

Charters exist so scope, exit gates, and cross-phase dependencies are fixed
now while signature-level detail waits until it can be true. A charter item
is a commitment; dropping one at planning time requires user approval.

## Planning protocol (binding on every future plan, regardless of author)

Mechanical steps, each checkable. A plan that skipped one is defective even
if it looks complete.

0. **Coverage walk first.** Enumerate the charter's deliverables and every
   MUST in the phase's spec anchors into a checklist inside the plan; every
   item maps to at least one task or to a user-approved deferral recorded
   in the plan. A plan whose tasks are all well-formed can still silently
   drop a chartered deliverable; this step is the net for that class.
1. **Wire facts are captured, never recalled.** Implementer-side capture is
   the rule: briefs direct the implementer to capture live (`nvim
   --api-info` dump, live attach, current docs fetch) and pin what they
   observe. The only alternative is a capture artifact committed at
   planning time (the command plus its verbatim output, as a file in the
   repo); a prose citation of a capture is never sufficient — prose is
   fabricatable and unfalsifiable. A plan-authored fixture with neither is
   the defect class that produced a protocol-breaking bug in P1.
2. **Consumer call-sites first.** Every new API, config field, or CLI surface
   appears in the plan as its consumer's call-site before its implementation.
   Two genuinely different shapes considered; the runner-up appears as a
   call-site beside the winner, never as a one-line strawman.
3. **Interfaces from the tree, not the plan chain.** Signatures consumed from
   earlier phases are read from the as-built source at authoring time; citing
   a previous plan's text for a signature is banned (plans drift, code
   doesn't lie).
4. **Task = independently checkable unit.** Every task states its falsifiable
   check (command + expected observation) before its steps; TDD steps carry
   complete code; no placeholders (writing-plans standard).
5. **Adversarial review before execution.** Every full plan gets a
   fresh-context adversarial review (most capable model available, handed
   the spec, the charter, and this protocol verbatim) before its first
   task dispatches. The review checks every task against every repo hard
   rule by name, not only against the spec. Findings are fixed in the
   plan, then the changed sections are re-reviewed; findings are never
   carried as notes.
6. **Plan-sync welded to fix rounds.** A conflict between plan text and
   observed reality halts the task: reality wins after verification
   against the tree or a live capture, the plan is updated, and downstream
   briefs are re-extracted before the task proceeds. User approval is
   required only when the deviation changes scope or a consumer-facing
   surface; otherwise the plan owner approves and records it. Coding
   around a wrong plan without syncing it is the drift class that hid two
   P1 defects.
7. **Exit checklist is authored with the plan** and includes: task ci, the
   phase's spec-budget measurements, known-bugs drain, dogfood note, and
   authoring of the next phase's plan under this same protocol. Each
   checklist item closes with an evidence citation (the command run and
   its observed output), never a bare checkmark.
8. **Hard rules travel in the plan.** Every plan's Global Constraints
   section embeds the repo hard-rule list verbatim (CLAUDE.md hard rules
   plus the crate dependency matrix). A plan whose text blesses a
   hard-rule violation is defective even if every task is well-formed;
   this closes the P1 class where plan text mandated a blocking request on
   the input path.

## P3 — Oracle + compat suite + bench harness + CI gates (the moat)

**Goal:** the compounding evidence assets: a differential oracle proving view
renders what nvim renders, a compat suite over real plugin configurations, and
the real §3.4 latency protocol wired into CI as enforced budgets.

**Spec anchors:** §13 (testing & the oracle), §3 (performance mandate,
§3.1 budgets, §3.4 protocol), §17 note: P3 sits deliberately before features.

**Deliverables**
- Differential oracle: same input script driven into view and into a
  reference nvim with a UI attached over RPC using the identical
  ext-option set (§13.2 — a bare `--headless` nvim renders no grid and is
  not a valid reference). Equivalence is the full §13.2 relation: exact
  RPC state parity (buffer text, cursor, mode, registers, marks) plus
  masked grid parity, under the quiesce protocol (timers drained or
  disabled, controlled clock). Divergence = failure with a minimized
  repro. Grows a corpus per §13; corpus entries carry inputs, engine pin,
  and ext-option set (§15's manifest rule) so the corpus survives
  engine-pin bumps.
- Compat suite: real-world plugin/config fixtures run under the oracle.
  The §13.3 named set is the floor (lualine, noice, nvim-notify,
  nvim-tree/neo-tree, dressing, fidget, telescope, treesitter, cmp,
  mini.nvim, which-key, plus the cold-bootstrap and daily-config
  scenarios); planning time may add, never subtract. The §13.3 published
  compat-evidence page (row schema + staleness rule) ships with the suite.
- Fuzz harness per §13.6: keystroke-storm scripts run through the oracle,
  divergence minimized to a repro.
- Bench harness v1: formalizes the §3.4 measurement protocol, replacing the
  v0 pairing-file mechanism; budgets from §3.1 become CI gates that fail the
  build, not informational prints. Includes the §3.3 `perf-audit` task
  target.
- Consolidation (carried finding): the pty scaffolding duplicated between
  view-bench and view-oracle becomes one shared test-support crate before a
  third copy appears. Audit matrix gains the new crate's row.
- CI: oracle + bench additions run in the matrix; nvim install pinned to the
  engine-pin version (spec §16) so the matrix tests the contract.

**Interface contracts at the boundary**
- Consumes: P2's headless driver (a P2 exit criterion), which must
  provide: scripted Msg-level and pty-level input injection; deterministic
  Surface/frame capture; a clock/timer seam the harness controls (no
  free-running `Instant::now` in any loop timer path); and RPC access to
  the embedded engine for §13.2 state-parity probes. Absence of any one of
  the four is a P2 exit-gate failure.
- Produces: oracle corpus format + runner CLI that P4-P6 extend per feature.

**Exit gates:** task ci green including oracle + compat + bench in CI;
compat matrix green, or each red row filed with a user-approved deferral;
every §3.1 budget row measurable without P4+ features measured and gated
(picker rows gate at P4 — record the split in the plan); latency gap
attribution re-measured after P2's loop redesign (the 4ms tick + 4ms
silence-timeout components must be gone); known-bugs drained; dogfood
note; P4 plan authored.

**Risks / open questions for planning time**
- Oracle flakiness vs real nvim timing: needs a settle-signal design (the v0
  harness's fixed sleeps are explicitly not acceptable here).
- Windows leg: which oracle tests are pty-portable; ConPTY work stays P6.

## P4 — Native features + theming

**Goal:** the visible product surface: picker, file tree, statusline, toasts,
command palette, theming — native-wins with per-feature opt-out.

**Spec anchors:** §9 (native features v0.1), §5.5 (supersession), §7
(surface & rendering), decision log (nucleo; native-wins default).

**Deliverables**
- Fuzzy picker on nucleo (files, buffers, live-grep, more per §9 —
  live-grep is spec-committed v0.1 scope, not optional).
- File tree, native statusline, command palette.
- Messages ownership: the full §9 kind-aware ext_messages routing table —
  modal native prompt overlays for confirm/return_prompt/inputlist (they
  take focus and reply via RPC; the engine is blocked on the reply, so a
  timeout toast here would hang first-run plugin bootstraps), sticky emsg
  toasts, statusline-routed showmode/showcmd/ruler, transient toasts with
  history. Owning ext_messages forces `cmdheight=0`; align with the
  ext_messages rendering P2 ships as-built.
- Clipboard provider per §5.1: g:clipboard injection so `"+y` works — a
  first-five-minutes bug if missing, and daily-driving starts this phase.
- CLI surface per §5.6: `--clean`, engine passthrough args
  (`+42` / `-c` / `-R` / `-o` / `-O` / `-p` / `-u`), `ls | view -` via
  stdin_fd, `--appname`. `--clean` is the §12 triage tool; daily-driving
  needs it.
- Theming: nvim highlight namespaces + view-native surfaces unified
  (§7/§9). Includes §7's cold-start theme cache (keyed by config path) and
  the ColorScheme re-derive bridge, whether or not P2's startup shell
  stubbed them.
- Supersession honesty machinery: every native feature that supersedes a
  plugin UI reports it — first-run toast, a registry entry in the
  doctor-facing schema (id, enabled, supersession record, off-switch key),
  and an exact per-feature off switch. §13.3's three-states assertion
  (native on / opt-out / plugin) lands in the oracle per UI-owning plugin.
  Config split: P4 owns the `[native]` per-feature keys (minimal file +
  flag read — enough for the three states and the off switch); P6 owns the
  full §11 surface (precedence chain, `VIEW_*` env, derived-defaults
  audit).

**Interface contracts at the boundary**
- Consumes: P2's Surface/tier system and Elm Msg/Effect shapes; P2's
  engine-request dispatch seam (`Msg::EngineRequest` + `Effect::Reply` —
  modal prompt replies and the clipboard provider both answer
  engine-blocked requests through it, so P4 extends the vocabulary, never
  the loop); P3's oracle runner (every feature ships with oracle coverage
  of its three states).
- Produces: the feature registry the config surface (P6) and doctor expose.

**Exit gates:** every shipped feature oracle-covered in all three states,
plus §9's non-interference test per feature (feature open causes no engine
state drift); budgets hold with features enabled (features may not eat the
latency win);
known-bugs drained; dogfood note (real daily-driving expected to start here);
P5 plan authored.

**Risks / open questions for planning time**
- Feature-by-feature scope inside §9 is a planning-time cut with user input.
- Theming across engine-owned vs native-owned regions: exact §7 boundary.

## P5 — AI: ACP client, agent panel, context providers, diff review

**Goal:** first-class AI: an ACP client speaking to any conforming agent, a
native panel, context providers, and diff review with buffer-truth safety.

**Spec anchors:** §10 (AI integration), §10.1 (out-of-band writes), decision
log (ACP over bespoke), risks (ACP churn: version-pinned adapter behind a
view-ai trait).

**Deliverables**
- ACP client in view-ai behind a view-owned trait (adapter version-pinned).
- Agent panel (native Surface consumer), context providers, and the
  per-project trust prompt before first agent launch (§10.2).
- Diff review flow where agent edits route through Effect::Rpc (nvim owns
  buffer text, always). The safety machinery is the deliverable, not the
  happy path: live hunk rebase via `nvim_buf_attach` change events, stale
  hunks re-diffed and never force-applied, one undo step per accept
  (undojoin), and the hidden-buffer path for files not loaded in a window.
- ACP adapter auto-provisioning mechanism per §16 (pinned version,
  checksummed download); packaging and checksum distribution land in P6.
- Out-of-band write handling per §10.1: routed-where-possible,
  detected-always (fs watch, checktime, conflict UI).

**Interface contracts at the boundary**
- Consumes: P2 Msg/Effect runtime, P4 panel/toast surfaces.
- Produces: the agent-session lifecycle the doctor (P6) inspects (session
  id, agent identity, state, last activity, pending edit count).
- Runtime model is settled (spec decision log, "Runtime model (amended at
  P1 exit)"): sync event loop + std threads; async exists only inside
  view-ai, bridged by channels at the crate boundary. The view-ai
  dependency-matrix row gains tokio; no other crate may. Re-opening this
  requires a spec amendment, not a planning-time choice.

**Exit gates:** ACP conformance against at least one real agent, verified
against the current ACP spec (MANDATORY planning-time step: re-verify ACP
via context7/current docs — the protocol is young and churns). Conformance
minimum script: session init, streamed response rendering, tool-call
status display, an edit proposal driven through diff review to both accept
and reject, cancel/interrupt, and agent crash surfacing as a panel-local
error that never stalls paint. Budgets hold during streaming and with a
session active; diff-review path oracle-covered; known-bugs drained;
dogfood note; P6 plan authored.

## P6 — Polish, multigrid, doctor, Windows tier-1 (= v0.1)

**Goal:** ship shape: multigrid + panes, the config surface, doctor,
docs, tier goldens, Windows promoted to tier-1.

**Spec anchors:** §11 (config), §14 (platforms), §15 (strangler roadmap
direction), §16 (release & distribution), risks (multigrid instability:
single-grid is the shipped mode until P6; upstream PR #32691 tracked).

**Deliverables**
- ext_multigrid attach + native panes, oracle-covered before panes ship;
  single_grid knob lifespan re-evaluated at the engine-pin bump.
- Config surface per §11 (derived defaults, overrides only — no field the
  tool can compute may be required).
- view doctor: engine pin, feature/supersession states, agent sessions,
  platform capabilities, resolved config path, the bare-nvim repro
  invocation (§12), tmux allow-passthrough guidance, and
  multigrid-shaped-failure recognition (§5.4).
- Docs + tier goldens; release/distribution per §16 (bundled pinned engine
  pair + override), released via anodizer. Includes ACP adapter packaging
  and checksum distribution (mechanism built in P5).
- Windows tier-1: ConPTY-gated, validated on real Windows via winserver
  (evidence, not CI-hope); the unix-gated test cluster gets Windows-shaped
  equivalents where the behavior exists there.

**Exit gates (= v0.1 gates):** full oracle + compat + bench suite green on
all three tier-1 platforms; §3.1 budgets gated in CI on all three; docs
complete; distribution artifacts verified by installing from the built
artifact in a clean environment on each tier-1 platform (real Windows via
winserver, real macOS via mbp — evidence, not CI-hope), `view doctor`
clean, `cosign verify-blob` passing, bundled engine matching the pin;
known-bugs drained; dogfood note; post-v0.1 direction reviewed against
§15.

**Risks / open questions for planning time**
- Multigrid upstream state at the time (PR #32691) decides how much §15
  machinery lands in P6 vs after v0.1.
- anodizer integration specifics (signing, release pipeline) verified
  against anodizer's then-current feature set.
