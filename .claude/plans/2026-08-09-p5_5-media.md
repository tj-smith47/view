# P5.5 Implementation Plan — Media Playback Handoff

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `view file.mp4` (or any audio/video file, however opened — CLI
arg, tree select, picker accept) hands the full terminal to a detected
system `mpv` and resumes view on exit (spec:620, §9 invented capability,
ruled 2026-08-07, v0.1 CORE per the same 2026-08-05 ruling covering the
other five — spec:896 — no "post-v0.1" framing anywhere in this plan).

**Why this is invention, not tuning:** no terminal editor treats "open a
media file" as a first-class, dispatch-routed action at all — nvim
(and every plugin ecosystem around it) either fails to open a binary file
or degrades to a hex/binary-detection warning. view's separate-process
architecture, plus this plan's shared open-dispatch (below), makes
"select a video in the tree and it plays" a genuinely new capability, not
a wrapper around an existing nvim behavior.

**2026-08-08 ruling this plan encodes (verbatim requirement):** ONE shared
open-dispatch — every open path (CLI arg, tree select, picker accept)
runs the same type detection and routes to buffer / image overlay / media
handoff. Selecting a video in the tree must play it. This plan defines
that dispatch once (§ below); the image plan (P5.5-image) references this
section for the routing mechanism and owns only the image-overlay branch
of it.

**A materially larger starting gap than the charter implies:** the
charter's "seamless... handoff" line reads as though only media routing
is missing. Direct inspection of the current tree shows the gap is
bigger: picker-accept (opening a selected candidate on `<CR>`) does not
exist today, for **any** file type, not only media. Confirmed via
`update.rs`'s `Msg::Key` dispatch — the `OverlayKind::Picker(p)` arm
unconditionally routes every notation, including `<CR>`, through
`PickerState::edit_query(&notation)`, whose own implementation treats any
notation that is not a single printable character or `<BS>` as a no-op
edit (`<CR>` bumps the query generation and does nothing else).
`PickerState::selected_path()` exists but is used only internally by
`refresh_preview()`, never to open a selection. The only existing
`RpcCall::OpenFile` emission site in the entire file is inside the tree's
`<CR>` handler. **This plan's dispatch task therefore builds picker-accept
for the first time** (for every file type, text included), not merely
"reroutes an existing path for media" — the CLI-arg and tree-select paths
already reach nvim/a buffer today and only need routing through the new
dispatch function, but picker-accept needs to be built before it can be
routed through anything.

**Architecture:** a new, pure `view-core` classifier
(`open_dispatch::classify(path) -> OpenKind`) examining a path's
extension against a small static table (`video`/`audio` → `OpenKind::
Media`, known image extensions → `OpenKind::Image` — deferred to the
image plan's own task, referenced not duplicated here — everything else
→ `OpenKind::Buffer`). A single new `Msg::OpenPath { path, source }`
message, emitted from all three entry points (CLI startup, tree `<CR>`,
new picker `<CR>` accept), replacing the tree's ad hoc direct
`RpcCall::OpenFile` emission and the CLI's untyped passthrough. `update()`
routes `Msg::OpenPath` through `classify()` and fans out to exactly one of:
the existing `RpcCall::OpenFile` (buffer path, unchanged from today's tree
behavior), a new `Effect::OpenImageOverlay` (image plan's task, this plan
only reserves the enum arm), or a new blocking `Flow::MediaHandoff`
intercepted by the main loop outside the ordinary `Executor` (§ "The
blocking-handoff Flow variant" below). mpv detection is `Command::new
("mpv").spawn()` returning `ErrorKind::NotFound` — no new dependency, no
config surface, satisfying the config-derivability rule by having nothing
to derive. Terminal suspend/resume reuses `TerminalGuard::restore_now()`
and `enter_raw_mode()`/`finish_entering_alt_screen()` verbatim — no new
terminal-control code, only sequencing around the existing guard.

**Tech stack:** no new dependency anywhere in this plan. `mpv` itself is
an external system binary, detected, never bundled (matching the browser-
pane precedent already ruled at spec:833 for the workspace-arc CDP
integration: "browser is detected, never bundled").

## Global Constraints

- **nvim owns all buffer text. No view subsystem holds authoritative text
  state. Buffer mutation happens only through `Effect::Rpc`.** Binds the
  buffer-path branch of dispatch (unchanged `RpcCall::OpenFile`); media
  and image branches never touch a buffer at all — they bypass nvim
  entirely for the file's content, which is exactly why they need a
  dispatch layer above the buffer-open path rather than inside it.
- **The paint loop never awaits RPC. The RPC reader thread never blocks.**
  Classification (`classify()`) and dispatch routing are synchronous, pure,
  and cheap (an extension lookup) — no RPC involved. The media handoff's
  blocking wait on `mpv`'s exit is addressed as its own, explicitly
  justified exception below (§ "The blocking-handoff Flow variant"), not
  as a violation of this rule: it blocks only the main UI thread's own
  dispatch loop, on a local child process the user explicitly invoked by
  opening a media file — never the RPC reader/writer threads, which stay
  live and unaffected throughout, and never an RPC wait of any kind.
- **No unwrap/expect/panic in lib crates.** mpv-not-found, mpv nonzero
  exit, and terminal guard re-entry failure all return `Result`/degrade
  to a stated error path (Task 5); no new panic path.
- **Dependency direction: core ← surface ← {native, ai}; only view-engine
  speaks RPC; only view-tui touches the terminal.** `classify()`/`Msg::
  OpenPath`/dispatch routing live in `view-core`, pure, RPC- and
  terminal-unaware. The actual `mpv` spawn and `TerminalGuard` suspend/
  resume sequencing live in `view` (the binary crate, which already owns
  `terminal.rs`'s `Term`/`TerminalGuard` and is the only place permitted
  to touch the terminal) — never in `view-core`.
- **Performance is a contract.** `classify()` runs once per open (CLI
  startup, tree select, picker accept — never per-keystroke, never per-
  paint), so it carries no hot-path budget row; stated explicitly rather
  than assumed (Task 6).
- Use `task` targets, never raw cargo/git, for build/fmt/lint/test/commit.
  Commit only via `task commit -- -m "<msg>"`.
- Comments are WHY-only; doc comments render for users and carry a WHAT
  summary. No session-narrative markers.
- Non-conventional commit prefixes are parenthesised scopes:
  `feat(media):`, `feat(dispatch):` — never `media:`.

## The shared open-dispatch mechanism (owned here; referenced, not
redefined, by P5.5-image)

This section is the single definition of the 2026-08-08 ruling's "one
shared open-dispatch." Any other P5.5 plan needing to route an opened
path (today: only P5.5-image) cites this section by name rather than
declaring its own classifier or its own `Msg::OpenPath` variant.

```rust
// crates/view-core/src/native/open_dispatch.rs — pure, no I/O, no RPC.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum OpenKind {
    Buffer,
    Image,
    Media,
}

/// Extension-table classification. A conservative default (`Buffer`) for
/// any extension not on the image or media lists, matching nvim's own
/// behavior for a file type it does not recognize -- an unrecognized
/// extension must never silently hand the terminal to an external
/// process the user did not ask for.
pub fn classify(path: &std::path::Path) -> OpenKind;
```

```rust
// crates/view-core/src/msg.rs — the one message every open entry point
// (CLI startup, tree <CR>, picker <CR> accept) emits.
Msg::OpenPath { path: std::path::PathBuf, source: OpenSource }

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum OpenSource { Cli, Tree, Picker }
```

`update()`'s `Msg::OpenPath` arm is the single fan-out point:

```rust
match open_dispatch::classify(&path) {
    OpenKind::Buffer => /* existing RpcCall::OpenFile, unchanged behavior */,
    OpenKind::Image  => /* Effect::OpenImageOverlay{path} -- P5.5-image's
                            task owns everything past this arm; this plan
                            only reserves it so dispatch has exactly one
                            fan-out site, never two competing ones */,
    OpenKind::Media  => /* Flow::MediaHandoff, the blocking-handoff variant below */,
}
```

`OpenSource` is carried for exactly one reason: a picker-accepted or
tree-selected path already has a resolved, on-disk `PathBuf` (no
resolution needed), while a CLI passthrough arg may still need the
existing relative-path/CWD handling `main.rs` already performs before
this dispatch point — `source` lets `update()`'s arm apply source-specific
normalization without three separate message variants. It is not used to
change which `OpenKind` branch fires; classification is by extension
alone, identically regardless of source, which is precisely what "one
shared open-dispatch" requires — a video opened via `view file.mp4`, tree
select, or picker accept must all reach the same `OpenKind::Media` branch.

## The blocking-handoff `Flow` variant

`Effect`'s doc comment (`msg.rs:511-513`) states "the executor never
blocks; every effect crosses a channel or is fired and forgotten." A
media handoff that blocks on `mpv`'s exit cannot be an ordinary `Effect`
run through `Executor::run` — `mpv` must own the real terminal file
descriptor, which is incompatible with being backgrounded behind a
channel. This plan resolves the tension by keeping the handoff **out of**
`Effect` entirely: `update()`'s `Msg::OpenPath` arm returns a new,
payload-free `Flow::MediaHandoff` variant (`runtime.rs:289`'s `Flow` enum
currently has `Continue`, `Quit(i32)`, `EngineLost`, all `#[derive(...,
Copy, ...)]` — a payload-bearing addition would force dropping `Copy`
tree-wide at every `Flow` call site, so the target path is stashed on
`Model` instead, the same shape `Quit(i32)`'s scalar payload is the
exception to, not the rule). The top-level loop in `runtime.rs`'s `run()`
intercepts `Flow::MediaHandoff` **outside** the ordinary per-message
`dispatch()`/`Executor` path — the same place it already special-cases
`Quit`/`EngineLost` — and runs the suspend → block → resume sequence on
the main/UI thread only, by design: `TerminalGuard::restore_now()`,
`Command::new("mpv").arg(path).status()` (a deliberate, singular blocking
call — `Command::status` is Rust's own name for "wait for exit," used
here exactly as a user's own `Ctrl-Z`/`:!` shell-out already blocks the
same thread today), then `TerminalGuard::enter_raw_mode()` +
`finish_entering_alt_screen()` + `model.dirty = true` (forces a full
repaint on resume, since the terminal's contents were entirely owned by
mpv while it ran). This is a stated, justified architectural exception,
not an accidental rule violation: the RPC reader/writer threads
(`view-engine`'s own threads) are untouched throughout — the embedded
nvim engine keeps running, keeps its own liveness, and is exactly where
it was when the user resumes — and the "await RPC" rule's actual target
(never let the *paint* loop block on the *engine*) is not what is
happening here at all. The engine is never awaited; a local child
process the user explicitly asked to take over the terminal is.

## Open design questions — resolved in this plan

1. **Doctor sequencing** (spec's own charter text says "doctor-guided when
   absent," and the §15 phase table sequences doctor's implementation in
   P6, strictly after P5.5 — spec:872). **Resolved by sequencing, not
   de-scoping: the doctor-guided contract stands for v0.1 — P6 is the
   phase that closes v0.1 itself (the phase table marks it "← v0.1"), so
   doctor integration lands before v0.1 ships, not after it.** This plan
   ships the plain-error detection path now, at P5.5; P6 completes the
   doctor-guided contract on top of the same detection function, within
   the same v0.1 release, not as a post-v0.1 deferral. Confirmed via
   direct inspection that no `doctor` subcommand exists anywhere in the
   tree today (`main.rs`'s `Cli` has no `doctor` variant; every "doctor"
   hit in the codebase is a doc-comment reference to a not-yet-built
   feature) — this plan cannot integrate with something that does not
   exist, and inventing a partial doctor subsystem here would be scope
   creep this plan does not own. The forward-compatible seam already
   exists and this plan uses it for free: `registry.rs`'s
   `FeatureDesc.id` doc comment states verbatim that the id "is... the
   doctor row name," so registering media as a `FeatureDesc` entry (Task
   6) gives P6's doctor a row to report against with zero additional
   work in this plan — the plain error message this plan ships (Task 5)
   and P6's eventual doctor check both read from the same detection
   function (`mpv_available()`, Task 5), so there is exactly one place
   the check lives, not two that could drift.
2. **Media type table.** Resolved: a small static extension list (`mp4`,
   `mkv`, `mov`, `webm`, `avi` for video; `mp3`, `wav`, `flac`, `ogg`,
   `m4a` for audio) rather than content-sniffing (magic bytes). Rationale:
   extension-based classification is what every comparable dispatcher
   (the shell's own `xdg-open`, `mpv` itself) already uses as its primary
   signal, it is config-derivable with zero user input needed (satisfying
   the config-derivability rule directly — there is nothing to derive
   *from*, so the sane default is simply shipped as the whole answer), and
   content-sniffing would require reading file bytes on every open
   (including plain-text opens, to rule out the media branch), a cost
   this plan's "classify once per open, cheap" performance framing
   explicitly rules out.
3. **mpv argument shape / audio-only files.** Resolved: `mpv <path>`
   with no special-cased flags — `mpv` already handles audio-only files
   correctly in a terminal (falls back to a text-based progress display,
   no video output attempted), so `OpenKind::Media` does not need an
   `is_audio` sub-branch; the same handoff invocation covers both.

### Task 1: Picker accept — build the missing `<CR>`-opens-a-file path

**Files:** `crates/view-core/src/native/picker.rs`,
`crates/view-core/src/update.rs`.

**Rule bound:** nvim owns all buffer text (accept never reads file
content itself; it only resolves a path and emits `Msg::OpenPath`, which
the dispatch arm — Task 2 — routes to the buffer-open `RpcCall` exactly
as today's tree accept already does).

**Design:** `update.rs`'s `OverlayKind::Picker(p)` arm in the `Msg::Key`
match gains a `<CR>` special case, mirroring the tree arm's existing
`<Esc>`-closes-picker special case immediately above it in the same
match — checked *before* falling through to `edit_query`, not inside it
(`edit_query` stays a pure query-text editor, unaware of accept, exactly
as `PickerState`'s own module boundary already separates "editing the
query" from "acting on a selection," the same separation `refresh_preview`
already respects by reading `selected_path()` without mutating the
picker). On `<CR>`, `PickerState::selected_path()` is read (returns
`Option<String>`, an owned path string, not a borrowed `&Path` — the
picker call site converts via `PathBuf::from(path)` before constructing
`Msg::OpenPath`, whose own `path` field is a `PathBuf`); `Some(path)`
emits `Msg::OpenPath { path: PathBuf::from(path), source: OpenSource::
Picker }` and closes the picker overlay (matching the tree's existing
close-on-open behavior); `None` (empty result list) is a no-op, matching
`edit_query`'s existing treatment of "nothing useful to do here."

**Interfaces:** (no new type; a new match arm ahead of the existing
`edit_query` fallthrough, and one new call site for `selected_path()`.)

**Falsifiable check:** integration test opens the picker, populates one
result, dispatches `<CR>`, and asserts `update()` returned an effect
sequence containing `Msg::OpenPath` with the expected path and
`OpenSource::Picker` — proving accept is now live, where today the same
test (run against the current tree, kept as a regression fixture in this
task) asserts `<CR>` produces no path-opening effect at all.

- [ ] **Step 1:** `<CR>` special case ahead of `edit_query` in the
  `OverlayKind::Picker` match arm.
- [ ] **Step 2:** Empty-results no-op case.
- [ ] **Step 3:** Regression fixture proving today's no-op behavior
  (kept as a comment-documented "this was the gap" test, converted to
  assert the new behavior).
- [ ] **Step 4:** `task ci`. Commit: `feat(dispatch): picker <CR> now
  opens the selected candidate, for every file type`.

### Task 3: `Flow::MediaHandoff` and the suspend/spawn/resume sequence

**Files:** `crates/view/src/runtime.rs`, `crates/view-core/src/model.rs`
(handoff target field), `crates/view-core/src/update.rs` (media arm).

**Rule bound:** the paint loop never awaits RPC (this task's entire
design is the stated exception, justified in § "The blocking-handoff
`Flow` variant" above — cite it, do not re-litigate it in code comments;
a one-line WHY pointer in the implementation is enough, the full
justification belongs in this plan and, later, in `runtime.rs`'s own
module doc for `Flow::MediaHandoff`).

**Landing-order dependency on P1 supervision.** This task's design (below)
requires two methods on `HeartbeatWatch` — `pause()`/`resume()` — that
supervision's plan does not currently define; supervision's plan, as
drafted, only exposes `observe(&self, connection_closed: bool) ->
Liveness` and `record_ack(&mut self, generation: u64)`. This is not a
citation of an existing interface (unlike the remote plan's precedent) —
it is a **required addition** to supervision's Task 1 surface, flagged
here because media's design cannot be made correct without it (§ below).
Round 3 pins down what that addition must guarantee, not just its
signature: `pause()` must stop the prober from advancing `sent_generation`
without ever decrementing it, and `resume()` must reset only `sent_at` —
`sent_generation` and `acked_generation` are left exactly where pause
found them (§ "the blocking window's interaction with liveness
supervision" below states the invariant and why resetting either counter
to a baseline is unsafe). **Task 3 does not begin implementation until
supervision's Task 1 (`HeartbeatWatch` itself) has landed in the tree AND
been extended with `pause()`/`resume()` per the signatures and the
monotonic-forward semantics in § below** — coordinate the addition with
whoever implements supervision's Task 1; this plan does not have write
access to the supervision plan file to add it there directly. Tasks 1-2
and 4-7 of this plan consume no supervision interface and are not gated
on it.

**Design — the blocking window's interaction with liveness supervision
(round-1 closed two of three problems; round 3 fixes the third — a stale
reply from a probe already in flight at `pause()`-time must not be able to
mask a real subsequent hang).** The original draft specified suspend →
block → resume with no treatment of supervision's `HeartbeatWatch`.
Tracing the real mechanism shows why that is unsafe: `HeartbeatWatch`'s
`sent_generation`/`sent_at` are written by an **independent prober
thread** that ticks every `HEARTBEAT_PROBE_INTERVAL` (2s) regardless of
what the main thread is doing, while `acked_generation` (and therefore
`Liveness`'s verdict) only advances when the main loop's own dispatch
processes a `Msg::HeartbeatReply` — which cannot happen while the main
thread is blocked inside `Command::status()`. Three independent problems
follow from this; pausing the prober outright (below) fully closes the
first two, and the third needs `resume()`'s own semantics pinned down
precisely rather than left as "a fresh baseline":

1. **False `Wedged` verdict on resume.** With the prober still ticking
   during the block, `sent_at` keeps advancing past `acked_generation`'s
   frozen value; the very first `observe()` call after resume sees an
   unacked probe older than `HEARTBEAT_WEDGE_THRESHOLD` (10s) — for any
   handoff longer than 10 seconds, this is certain, not probabilistic —
   and reports `Wedged` even though the engine was never actually
   unresponsive, it was simply never asked anything while mpv owned the
   terminal.
2. **Unbounded reply backlog on the message channel.** Every probe the
   prober thread sends during the block eventually produces a
   `Msg::HeartbeatReply` written to `msg_tx` (a bounded
   `mpsc::sync_channel(MSG_CHANNEL_CAPACITY)`,
   `crates/view/src/main.rs:349`) by the RPC reader thread — a thread the
   architecture requires to never block. For a short handoff this is
   harmless (a handful of queued replies, drained on the very next
   dispatch loop pass); for an arbitrarily long one (a feature-length
   film) it is not: once the channel fills, the reader thread's send
   blocks (`sync_channel`'s documented behavior, and the exact
   full-channel semantics this tree already has a regression test for —
   `re_enqueueing_replayed_keys_onto_a_full_bounded_channel_with_no_
   consumer_blocks_forever`), which is a direct violation of "the RPC
   reader thread never blocks" for a scenario this plan itself introduces.
3. **Late replies from the probes already in flight when `pause()` fires
   (round-3 fix — round-1's text claimed this could not happen; round-4
   fix — round-3's text undercounted it as one).** The promoted
   supervision plan's prober is a fixed-interval timer with no ack-gating:
   it calls `request_heartbeat` every `HEARTBEAT_PROBE_INTERVAL` tick
   regardless of whether earlier probes are still unacked
   (`.claude/plans/2026-08-09-p5_5-supervision.md:372-375`), and the plan
   itself notes at least 4 probes land inside `HEARTBEAT_WEDGE_THRESHOLD`
   before a verdict can flip (`:461-463`) — so up to
   `⌈HEARTBEAT_WEDGE_THRESHOLD / HEARTBEAT_PROBE_INTERVAL⌉` ≈ 4-5 probes
   can be outstanding, unacked, at the moment `pause()` fires, not just
   one. `pause()`'s `AtomicBool` is checked at the top of the prober
   thread's `tick()`, so it stops the *next* tick from firing, but every
   probe a prior tick already dispatched is unaffected: the embedded nvim
   process is never suspended or signaled during the handoff (§ "engine
   outbox" below), so it keeps servicing RPC and will eventually reply to
   each of them, and each `Msg::HeartbeatReply` lands on `msg_tx`
   independently, whether mid-block or after `resume()` has already run —
   pausing at an arbitrary point in a fixed 2s cadence with no ack-gating
   makes some in-flight backlog the common case, not a rare race. This is
   still not a channel-capacity hazard: `pause()` stops every probe after
   that already-outstanding handful, so at most ~4-5 small RPC replies are
   ever outstanding — comfortably inside `MSG_CHANNEL_CAPACITY`, and the
   bounded-channel-fill risk problem 2 describes remains fully closed by
   pausing, `crates/view-engine/src/damage.rs`'s bounded-channel behavior
   included. The hazard is what `record_ack` does with *each reply's
   generation* if it lands after `resume()`.

Problems 1 and 2 are fixed exactly as round-1 described: pausing removes
the traffic that would otherwise cause them. Problem 3 requires `resume()`
itself to guarantee something round-1 never proved, so the mechanism is
tightened here:

**The fix, chosen: `resume()` is monotonic-forward, never a baseline
reset.** `update()`'s `OpenKind::Media` arm, in addition to setting
`model.pending_handoff = Some(path)`, calls `model.heartbeat.pause()`
before returning the `Flow::MediaHandoff` signal, exactly as round-1
specified: `pause()` sets a shared `AtomicBool` the prober thread's
`tick()` checks before issuing each probe, so no *new* probe is sent once
paused. What changes is `resume()`: `sent_generation` is one counter for
the whole lifetime of the `HeartbeatWatch` — `pause()` stops the prober
from advancing it (no new ticks means no new bump) but never rewinds it,
and `resume()` does not touch it either. `resume()` resets only `sent_at`
to "now" (this alone closes problem 1: without it, the frozen `sent_at`
would still read as overdue the instant `observe()` is next called) and
leaves `acked_generation` untouched. The prober's first post-resume tick
simply continues the same counter, one past whatever generation was last
sent before the pause.

**Invariant:** any stale ack that arrives after `resume()` carries a
generation from before the pause, and every post-resume tick uses a
strictly greater generation (the counter never rewound), so the stale
generation is always less than every post-resume `sent_generation`.
Supervision's own `record_ack` already folds acks via `max(current,
incoming)` specifically so a stale reply can never clobber a newer verdict
(promoted plan: `.claude/plans/2026-08-09-p5_5-supervision.md:516-522`'s
`HeartbeatWatch::record_ack` doc, composing here with the same plan's
`Waiter::Heartbeat { generation }` generation-tagged design that motivates
it, `:399-408`) — combined with a `resume()` that never
lowers `sent_generation`, that max-fold can raise `acked_generation` to at
most the stale pre-pause value, never as high as a post-resume
`sent_generation`. A late stale ack is therefore folded in harmlessly and
leaves exactly the gap `observe()` needs to still report a genuinely stuck
post-resume probe as `Wedged` once `HEARTBEAT_WEDGE_THRESHOLD` elapses —
the stale ack cannot manufacture a false `Alive` verdict for a real
subsequent hang. This is why the reset is deliberately narrow: resetting
`sent_generation` or `acked_generation` downward — which round-1's "fresh,
mutually consistent baseline" language did not rule out — is exactly what
would let a stale ack's generation exceed a newly-lowered post-resume
counter and mask a real subsequent hang as permanently `Alive`, a failure
mode strictly worse than problem 1's false `Wedged` (that one is loud and
self-correcting on the next ack; this one is silent and permanent). Option
(b) — an explicit epoch/session discriminator carried alongside
`generation`, so pre-pause replies are identifiable and dropped outright
rather than relying on generation ordering — was considered and rejected:
it duplicates state `record_ack`'s existing max-fold already makes
unnecessary once `resume()` stops resetting the counter, adding a second
field with the same job the first already does under the monotonic-
forward invariant.

**Design — engine outbox during the block.** With the prober paused
(above) after the already-outstanding probes (~4-5, § problem 3 above)
drain, the engine produces no further traffic while nothing is reading it
back on the view side except through the same reader thread that already
never blocks under normal operation — no new outbox, buffer, or channel is
introduced. The embedded nvim process itself keeps running throughout
(never suspended, never signaled) but has nothing to say: no input is
being forwarded to it during the handoff (the main dispatch loop is
blocked, not calling `Executor::run`), so `Msg::Redraw` traffic has no
trigger either. The only traffic that could exist during the block is
heartbeat probe/reply pairs — bounded by that same ~4-5, per problem 3,
not unbounded — and pausing the prober removes every probe after that
handful at its source, rather than requiring a new bound on where a
continuing stream of them would buffer.

**Design — resize during playback.** `mpv` owning the terminal does not
stop `SIGWINCH` from being delivered to the view process, but the reason
the resize is not lost is a specific mechanism, not a general claim about
signal delivery: `crates/view-tui/src/input.rs`'s pollable input handle
registers a `SIGWINCH` self-pipe via `signal_hook::low_level::pipe::
register(signal_hook::consts::SIGWINCH, winch_write)` — a kernel pipe
buffer that retains the byte the signal handler writes regardless of
whether anything is reading the pipe's other end at the moment the signal
arrives. While `mpv` owns the terminal and the main loop is blocked inside
`Command::status()`, nothing is polling that self-pipe, but the kernel
still buffers the write; the pipe is not a channel the blocked loop must
be actively draining to avoid losing the signal, only one it must
eventually read. `run()`'s existing top-of-loop check, `term_size.take()`
(`crates/view/src/runtime.rs:1116`), is the very next read of that pipe —
it runs on every pass through the loop, including the first pass after
`Flow::MediaHandoff`'s resume sequence completes and control returns to
the top of `run()` — so a resize that happened mid-block is observed on
that first post-resume pass exactly as it would be during any other idle
period; no new interception is needed.

**Design — resume repaints from the engine's current grid, never a stale
one.** Setting `model.dirty = true` alone is insufficient: any redraw
damage the engine sent immediately before the handoff began (or, per
above, during a brief window before `pause()` takes effect) may still be
sitting undrained in the pump. Painting from `model`'s current state
without first applying that damage would repaint a frame from
*before* the handoff, not the engine's actual current grid. The resume
arm therefore reuses the loop's own existing residue-drain idiom — the
same one-shot `pump.take_damage()` drain `run()`'s own per-pass loop
already performs after its inner message queue empties
(`crates/view/src/runtime.rs:1056-1230`) — calling it once, explicitly, in
the handoff arm immediately after `enter_raw_mode()`/
`finish_entering_alt_screen()` and before setting `model.dirty = true`, so
any backlogged damage is applied to `model` before the forced full
repaint paints it.

**Design — suspend/spawn/resume sequence (unchanged from the original
draft, restated for completeness).** `runtime.rs`'s `run()` gains a new
match arm alongside its existing `Quit`/`EngineLost` handling: on
`Flow::MediaHandoff`, take `model.pending_handoff` (clearing it), call
`model.heartbeat.pause()`, `term.guard.restore_now()`,
`Command::new("mpv").arg(&path).status()`, then unconditionally (success
or failure both resume view — a failed playback is not a reason to strand
the user in a bare terminal) `term.guard.enter_raw_mode()` +
`finish_entering_alt_screen()`, `model.heartbeat.resume()`,
`pump.take_damage()` (residue drain, § above), `model.dirty = true`, and
continue the ordinary loop. `mpv`'s exit status is not itself an error
path for view — only spawn failure (mpv not found) is (Task 5).
