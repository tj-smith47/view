**Architecture:** P6 adds no new subsystem. It finishes three seams that
already exist and builds one new command:

- **The grid seam becomes plural.** Today `Model` owns one `Grid` fed by
  `ext_linegrid` events. Under `ext_multigrid` nvim emits the same
  `grid_*` events per grid id plus a window-placement vocabulary
  (`win_pos`, `win_float_pos`, `win_hide`, `win_close`, `grid_destroy`,
  `win_viewport`). view composites those grids itself, which is what
  "native panes" means at v0.1: the window separators, the inactive-pane
  treatment and the float chrome become view-owned surfaces instead of
  cells nvim drew. Arbitrary non-engine content in a pane is the v0.2
  workspace arc (spec §15.1), not this phase.
- **The config seam gains a precedence chain.** `ViewConfig` already
  parses `[native]`/`[supervision]`, and `view-ai` parses `[ai]`. P6 adds
  `[ui]` and `[engine]`, and — the part spec §11 actually names — one
  resolver that answers every key as flags > env (`VIEW_*`) > file >
  derived default, carrying the provenance of each answer so `doctor` can
  print where a value came from.
- **The engine seam gains its bundled layout.** §16's "tested pair"
  contract is unimplemented today: `EngineConfig::default` names `nvim` on
  `PATH`, and `view-engine`'s env module *clears* `$VIMRUNTIME`. P6
  resolves a bundled engine beside the executable, exports its runtime,
  fronts its bin directory for child processes, and reports drift.
- **`view doctor` is the new command**, and it is a report model with two
  fill paths (a standalone probe for the triage flow, a live-session fill
  for the rows only a running session knows), never two doctors.

## Global Constraints

Hard rules, embedded verbatim per planning-protocol step 8. Every task's
requirements implicitly include this section.

- **nvim owns all buffer text.** No view subsystem holds authoritative text
  state; buffer mutation happens only through `Effect::Rpc`. This phase
  writes no buffer text at all. Its nearest approach is `[ui] theme`
  naming a colorscheme (T6), which is an `Effect::Rpc` telling nvim to run
  its own `:colorscheme` and then deriving view's chrome from the
  highlight table nvim reports — view never holds a second palette that
  nvim does not know about.
- **The paint loop never awaits RPC. The RPC reader thread never blocks.**
  Multigrid multiplies the number of grids a frame composites; it must not
  add a single request to the paint path. Window placement is read from
  redraw events only, never from `nvim_win_get_config` on the paint path
  (that call belongs to migration-integrity's float-claimant detector,
  which runs off an autocmd, not off a frame).
- **`view-core` stays pure.** No I/O, no env access, no clock. The
  multigrid model, the doctor report model and the config key registry are
  plain data; every probe, env read and file read happens in `view-native`,
  `view-tui`, `view-engine` or the bin.
- **No unwrap/expect/panic in lib crates** (workspace lints enforce; do not
  weaken them). Test modules may open with
  `#![allow(clippy::unwrap_used, clippy::expect_used)]`.
- **Dependency direction: core ← surface ← {native, ai}**; only
  `view-engine` speaks RPC; only `view-tui` touches the terminal; only
  `view-ai` speaks ACP and owns a tokio runtime. `view-native` and
  `view-ai` are mutually forbidden, both directions — so the doctor's
  adapter and agent rows arrive as plain scalars the bin passes in, never
  as a `view-ai` type a `view-native` signature names. `scripts/audit-deps.sh`
  enforces the matrix; any new crate or edge lands with its audit row in
  the same commit.
- **Wire strings come from capture docs, never from recall.** Two capture
  tasks precede every task that consumes one: T1 (multigrid redraw event
  names, argument shapes and ordering) before T8–T12; T2 (ConPTY harness
  behavior) before T20–T22. A task may not embed an event name, a field
  spelling or a reply grammar that no capture doc in `docs/` records. A
  prose citation of a capture is never sufficient.
- **Performance is a contract.** Any change touching key dispatch, grid
  apply, or paint states its latency consequence and the §3.1 budget row
  that covers it, in the commit description. Multigrid touches grid apply
  and paint in every task from T8 to T12, so each of those carries the
  statement; capture docs, config plumbing, docs and matrices commit
  without one.
- **Budget rows: max is inherited, never derived from the recording it
  bounds.** A new row's `max` is the bar the spec already states for the
  same quantity on its sibling class (the memory row's 150.0 is the same
  150.0 on every platform; only the metric name changes). A bound computed
  from the first measurement cannot fail by construction — that is the
  defect that withdrew the input-path row's 232 µs, the first-paint
  `cold_ms` bar and the remote row's 6.0. `scripts/check-budget-drift.sh`
  fails CI unless each entry's `spec_row` appears verbatim in the spec with
  its `max` as a number in that row, so every new row lands with its spec
  amendment in the same commit. A first recording that misses an inherited
  bar is a `[[shortfall]]` with an honest `why`, not a relaxed `max`.
- **Budgets attest on controlled classes only.** The gh legs are regression
  tripwires; cold absolutes and tail statistics never gate on a shared
  host. A Windows class's label follows its own null-pair calibration, not
  a name chosen in advance: `--gate` refuses when the measured floor is not
  met, and a host that cannot hold the floor records with measured noise
  floors instead of gating.
- **Production files stay under the 1000-line ceiling**
  (`scripts/audit-god-files.sh`, `task loc`; the exemption list is empty
  and neither pin may be raised). Three areas are on course to trip it and
  are split up front rather than after the ceiling fires: the multigrid
  model (`view-core/src/grid.rs` is the existing single-grid file — the
  registry lands beside it as `grid/registry.rs`, not inside it), the
  paint compositor (`view-tui/src/paint.rs` is already large — pane
  composition lands as `paint/panes.rs`), and the doctor report
  (`view-native/src/doctor/` as a module directory from the start:
  `mod.rs` for the report model, `rows.rs` for the row producers,
  `render.rs` for the text rendering).
- **Comments are WHY-only**; doc comments render for users and carry a WHAT
  summary. No session-narrative markers of any kind, no caller refs, no
  deferred-work pointers (`scripts/check-style.sh`, `task style`). Every
  comment inside a code block below is written as source-ready text.
- **`task` targets only** — never raw cargo or git. `task ci` before every
  commit; commit only via `task commit -- -m "<msg>"`. Gates run in the
  FOREGROUND with a generous timeout when a subagent runs them.
- **Non-conventional commit prefixes are parenthesised scopes**:
  `feat(engine):`, `test(tui):` — never `engine:`.

## Design questions resolved (decided here, not handed to the implementer)

Decisions binding on every task below. Each is a question the tree or the
spec leaves genuinely open, answered here so no implementer invents an
answer mid-task.

1. **What "native panes" means at v0.1.** view composites nvim's own
   window grids and owns the chrome between them (separators, the active
   or inactive treatment, float borders). It does not host non-engine
   content in a pane — that is the v0.2 pane compositor (spec §15.1),
   which this phase's grid registry is deliberately shaped to accept later
   (a pane's content is an enum with exactly one variant today) without
   building a second variant now.

2. **Multigrid is the default attach mode at P6, and the flip is gated on
   measurement.** Spec §11 shows `single_grid = false`, and the §19 risk
   row says single-grid is the shipped mode *until* P6. The flip changes
   what every existing budget row measures, so T11 does not land the flip
   until the paired bench matrix has been re-recorded on a controlled
   class with the new mode and holds. A regression past a bar is a blocker
   for the flip, not a shortfall to accept.

3. **`view doctor` is a subcommand, matched before clap parses.** `Cli`
   uses `trailing_var_arg` passthrough, whose whole contract (stated in
   the binary's own `after_help`) is that the first token which is not one
   of view's flags starts nvim's argument list. A clap subcommand inside
   that shape is ambiguous; a first-token match is not. `view doctor` is
   the command; `view ./doctor` or `view -- doctor` opens a file of that
   name, and the help text says so.

4. **One doctor, two fill paths.** `view-native::doctor` builds a
   `DoctorReport` from plain data. The standalone CLI fills it by probing
   (config resolution, a headless engine spawn for the version handshake,
   the terminal capability register, adapter and node readiness). The
   in-session path fills the same struct from the live `Model` — real
   supersession claims, real `AiStatus`, the real attach mode. Rows that
   the standalone path can only predict are labelled as predicted, never
   printed as observed. Two renderers would be two truths.

5. **The in-session doctor reuses the notification history overlay.** It
   writes the rendered report into the history and opens it, inheriting
   the scroll and copy-the-path affordances migration-integrity's T18
   adds. A dedicated overlay kind for a page of text that already has a
   scrollable home is surface for its own sake.

6. **`VIEW_*` env names are derived from the key path, not hand-listed.**
   One key registry drives file parsing, env lookup, flag mapping and the
   doctor's provenance row; the env name is `VIEW_<TABLE>_<KEY>`
   uppercased from the same row. The namespace already carries
   non-config members (`VIEW_LOG` and the harness's own `VIEW_*` names),
   so the resolver claims only names the registry generates and ignores
   every other `VIEW_*`, with a test proving `VIEW_LOG` is never read as
   config.

6a. **The registry spans every live table, and a row without a flag is a
   stated state.** P5's recorded deferral is the *full* §11 surface, so
   the registry carries a row for every key the shipped example ships —
   `[ui]` (2), `[engine]` (3), `[native]` (5), `[supervision]` (1) and
   `[ai]` (2), thirteen rows — each with its env name and its derived
   default. `VIEW_NATIVE_PICKER=false` and `VIEW_SUPERVISION_AUTO_RESTART=false`
   therefore work, because a precedence chain that covers two tables of
   five is not the surface the spec states. **Flags are the narrow set,
   deliberately:** only the keys decision 8 argues for get one
   (`--tier`, `--theme`, `--nvim-bin`, `--appname`, `--single-grid`).
   `[native]`'s per-feature switches already have `--clean` as their
   whole-table triage flag and a `--picker=false`-shaped flag per feature
   is surface nobody asked for; the registry's `flag` field is
   `Option<&'static str>` and `None` is a legitimate, tested state rather
   than a gap.

6b. **`[ai]`'s two keys are registered in `view-native` and resolved in
   `view-ai`, cross-checked in the bin.** `view-native` and `view-ai` are
   mutually forbidden in both directions, so neither can call the other's
   resolver. The registry is *metadata about keys* — table, key, env
   name, derived-default text — which `view-native` can carry for a table
   another crate parses without naming one of its types (it already
   carries `SIBLING_READ_TABLES` for exactly this shape). `view-ai` gains
   the env layer for its own two keys, and the cross-check lives in the
   bin, the only crate that may name both:

   ```rust
   // crates/view/tests/config_registry.rs
   // the two crates cannot see each other, so the one place that can see
   // both is where the registry and the resolver are held to each other
   for row in view_native::config::keys().iter().filter(|k| k.table == "ai") {
       let name = view_native::config::env_name(row);
       assert!(view_ai::AiConfig::env_names().contains(&name.as_str()));
   }
   ```

   The runner-up was resolving `[ai]` inside `view-native` from the raw
   `toml::Value` so one resolver answers every key. It is rejected for the
   reason the `loaded_tables` doc comment already gives about two loaders
   over one file: `view-ai` would still parse `[ai]` for its typed config,
   and two crates resolving the same key is two answers a user has to pick
   between. One parser per table, one cross-check, no shared answer.

7. **`[ui] theme` names an nvim colorscheme, and "auto" is the absence of
   a choice, not a variant.** Both `[ui]` keys encode "derived" the same
   way — `Option<T>` where `None` is what the string `"auto"` parses to
   and what an absent key yields, so one shape covers tier and theme and
   there is no second spelling of the same idea. `auto` (the derived
   default) keeps today's behavior: view derives its chrome from whatever
   colorscheme the user's config ended on. A named value issues nvim's own
   `:colorscheme <name>` after the user's config has sourced, and the
   chrome derives from the result exactly as before — one palette, nvim's.
   A colorscheme nvim cannot find surfaces as a notice and leaves the
   derived theme untouched, because a config typo must not cost the user
   their colors.

8. **The keys a user reaches for mid-session get a CLI flag.** Spec §11's
   own sentence is "CLI flags mirror config (`--tier`, `--nvim-bin`)",
   which names the shape rather than demanding one flag per key; decision
   6a states where the line falls. P6 adds `--theme` and `--single-grid`
   to the four flags that exist. `--single-grid` is load-bearing rather
   than symmetric: `doctor` recognizes multigrid-shaped failures and
   suggests the knob (spec §5.1's `ext_multigrid` note), and suggesting a
   knob reachable only by editing a file is a worse triage flow than the
   one `--clean` already sets the bar for.

9. **Windows tier-1 does not require a Windows tap channel.** The
   tap-based cells split three ways, and the plan states each rather than
   averaging them into one claim:
   - `input_path`, `ai_session_active` and `ai_streaming` carry budget
     rows the spec already scopes to `controlled-linux`, so no
     Windows-class bar exists for them.
   - `echo_path` carries no budget row at all — it is a
     `DIAGNOSTIC_MATRIX` decomposition, never selected by `--all` and
     refused under `--record`/`--gate`, so it can never gate anywhere.
   - `output_path` carries a row with **no `classes` key today**, which
     means every class — including a Windows class that cannot measure
     the cell at all, because the tap channel is unix-only. That is a bar
     bound to a platform it can never be evaluated on, and T18 scopes the
     row to the classes that measure it in the same commit as the
     register row that claims it. `echo_speculated` is already scoped to
     `controlled-linux`.

   The cells that *do* carry platform-general bars — `echo`, `scroll`,
   `first_paint`, `flood`, `picker`, `memory` — must all measure on
   Windows, which is why T19 exists: `memory` has no Windows metric
   defined in spec §3.4 today, and a tier-1 platform with an unmeasurable
   memory budget is a hole in the promotion, not a detail.

## Config derivation audit (spec §11, and the standing user rule)

Nothing view can compute may be required. Every key **the shipped example
ships** — not only the ones P6 adds — because P5's deferral is the full
§11 surface and a chain covering two tables of five is not that surface.
Thirteen rows, thirteen registry entries, no required key:

| Key | Flag | Env | Derivable from | Derived default | Required? |
|---|---|---|---|---|---|
| `[ui] tier` | `--tier` | `VIEW_UI_TIER` | the terminal capability probe (migration-integrity T4/T5) | absent (`"auto"`) → the probed tier | never |
| `[ui] theme` | `--theme` | `VIEW_UI_THEME` | nvim's highlight table after the user's config sources | absent (`"auto"`) → derived from the engine's own colorscheme | never |
| `[engine] nvim_bin` | `--nvim-bin` | `VIEW_ENGINE_NVIM_BIN` | the bundled layout beside the executable (T3), else `nvim` on `PATH` | `bundled` | never |
| `[engine] appname` | `--appname` | `VIEW_ENGINE_APPNAME` | the process's own `NVIM_APPNAME`, else unset | inherit the environment | never |
| `[engine] single_grid` | `--single-grid` | `VIEW_ENGINE_SINGLE_GRID` | the pinned engine's own multigrid support, from the version handshake | `false` while the pinned engine supports multigrid | never |
| `[native] picker` | none | `VIEW_NATIVE_PICKER` | the feature registry's own row | `true` | never |
| `[native] tree` | none | `VIEW_NATIVE_TREE` | the feature registry's own row | `true` | never |
| `[native] statusline` | none | `VIEW_NATIVE_STATUSLINE` | the feature registry's own row | `true` | never |
| `[native] notifications` | none | `VIEW_NATIVE_NOTIFICATIONS` | the feature registry's own row | `true` | never |
| `[native] palette` | none | `VIEW_NATIVE_PALETTE` | the feature registry's own row | `true` | never |
| `[supervision] auto_restart` | none | `VIEW_SUPERVISION_AUTO_RESTART` | nothing to derive from; the default is the policy | `true` | never |
| `[ai] enabled` | none | `VIEW_AI_ENABLED` | nothing to derive from; the default is the policy | `true` | never |
| `[ai] agent` | none | `VIEW_AI_AGENT` | the one adapter this build can provision | `"claude-code"` | never |

The eight rows with no flag are a stated policy (decision 6a), not an
omission: `--clean` is `[native]`'s whole-table triage flag, and the
registry's `flag` field is an `Option` whose `None` arm is tested.
`[ai]`'s two rows are registered here and resolved in `view-ai`
(decision 6b), cross-checked from the bin.

Three fields deliberately do **not** become config keys, each because the
tool already knows the answer and a hand-written copy would drift:

- **The adapter's version, URL and checksum.** `AdapterPin` is compiled in
  and `[ai] agent` names an id; a user-supplied checksum is the canonical
  drift-and-404 failure.
- **The engine pin.** `.engine-pin` is the tested pair's version; a config
  key that could disagree with the bundled binary would let a user
  "configure" a claim the release cannot honor. `doctor` reports drift
  instead.
- **The XDG config path itself.** `--config` already overrides it for
  triage; a key inside the file naming the file it lives in is circular.

`view.toml.example` ships every key above with its derived default shown
and a comment saying what absent means — and after T7 the file has no
"this build does not read them" preamble left, because every table spec
§11 names is read.

## What Windows tier-1 promotion actually requires

The phase inherits a green native `windows-msvc` `task ci` (2774 tests)
and a bench harness whose unix-only cells announce themselves as skipped.
That is tier-2 done well; it is not tier-1. Spec §14 names the promotion
criteria — "§3.1 budgets measured over ConPTY (§13.4) and validated on
winserver — not deferred to CI faith" — and the charter adds "the
unix-gated test cluster gets Windows-shaped equivalents where the behavior
exists there". Concretely, four things:

1. **CI legs.** `oracle`, `compat` and `bench` run on `ubuntu-latest` and
   `macos-latest` only today; `ci` already runs all three OSes. Tier-1
   means `windows-latest` joins the other three jobs, with a `gh-windows`
   bench class and its recorded baseline (T21).
2. **Gating semantics for the cells that stay unix-only.** A skip that
   nobody can enumerate is indistinguishable from a gap. T18 builds the
   platform-gate register on exactly the shape migration-integrity's
   capability register uses: every `#[cfg(unix)]` fence in a test or
   harness path, every `platform_block` arm and every `CLASS_SCOPED` row
   has a register row that either names its Windows equivalent or states
   why the behavior does not exist there — enforced by a drift test, so a
   new fence with no row fails the build.
3. **A Windows memory metric.** Spec §3.4 defines `pss_mb` (Linux) and
   `phys_footprint_mb` (macOS) and nothing for Windows, so `memory` is
   `platform_block`ed there and the 150 MB budget is unmeasurable on a
   would-be tier-1 platform. T19 amends the spec with the Windows
   quantity — private working set, recorded as `private_working_set_mb` —
   implements it, and adds the third budget row with the inherited 150.0.
4. **winserver evidence, not CI hope.** The ConPTY budget measurements and
   the install-from-artifact verification both run on the real Windows
   host, with their output captured as evidence files, on the same footing
   as the mbp macOS leg (T17, T22).

## Boundary with the migration-integrity phase

That plan owns four surfaces this one touches. P6 references them by name
and never re-implements them:

- **Terminal capability probing and the capability register** (its T3–T5).
  `view doctor`'s platform-capabilities section renders `tiers::register()`
  rows and `Term::caps_source()`; it adds no probe of its own. If a

  in that register, not in a doctor-local probe.
- **The ext-option set following `[native]`** (its T8, `ext_surfaces`).
  P6's `ext_multigrid` enters through that same function, gated on
  `[engine] single_grid`, so there stays exactly one place that decides

- **Generic surface-ownership conflict detection** (its T10–T13). Float
  claimants are detected from autocmds and `nvim_win_get_config`, which is
  independent of the attach mode. P6 owes that mechanism one interaction
  test (T9) proving a claimed float still resolves the same way when the
  float also arrives as its own multigrid grid.
- **The notification surface** (its T14–T18). The in-session doctor writes
  into that history rather than growing an overlay kind.

### Task 1: Wire capture — the multigrid redraw vocabulary (planning-protocol item 1)

**Files:**
- Create: `docs/multigrid-wire-capture.md`
- Create: `crates/view-oracle/tests/multigrid_capture.rs` (the capture is a
  test so it re-runs at every engine-pin bump, not a one-shot script that
  rots)

**Why:** every task from T8 to T12 consumes event names, argument shapes
and orderings that view's decoder has no variant for today. Which events
fire, in what order, with which argument tuples, and what the *global*
grid does under multigrid are exactly the facts the protocol forbids
recalling. The P1 defect class this rule exists for was a plan-authored
fixture with neither a live capture nor a committed artifact behind it.

**What must be captured**, against the pinned engine from `.engine-pin`,
attached with `UI_EXT_OPTIONS` plus `ext_multigrid`:

- Every `redraw` event emitted for: startup attach; `:vsplit`; `:split`;
  moving between windows; `:resize`; closing a window; opening a floating
  window via `nvim_open_win`; closing it; `:tabnew` and back.
- For each of `grid_resize`, `grid_line`, `grid_clear`, `grid_scroll`,
  `grid_cursor_goto`, `grid_destroy`, `win_pos`, `win_float_pos`,
  `win_external_pos`, `win_hide`, `win_close`, `win_viewport`, and any
  `win_viewport_margins`-shaped event this engine emits: the verbatim
  argument tuple with each element's type.
- **Whether grid 1 still receives `grid_line`** once multigrid is
  attached, and what it carries if it does. The compositor's whole shape
  depends on the answer, and it is the single most commonly misremembered
  fact about this protocol.
- Whether `msg_set_pos` fires at all with `ext_messages` also attached.
- The grid id space: which id the first window gets, whether ids are
  reused after `grid_destroy`, and whether `win_pos` can name a grid that
  has not yet been `grid_resize`d.
- What `nvim_input_mouse` expects for its grid argument under multigrid,
  and whether `nvim_ui_try_resize_grid` is required for per-grid sizing or
  the engine drives sizing itself from `nvim_ui_try_resize`.
- The same script's event stream under single-grid, side by side, so the
  delta is the document's spine rather than a claim about it.

**Falsifiable check:** the doc records at least one event name that
`crates/view-engine/src/ui_events.rs` has no decoded variant for today. If
it does not, the capture did not run against a real multigrid attach and
the doc is describing single-grid; the task fails rather than shipping a
document that agrees with what view already believes.

**Dependencies:** none. **Perf:** none (a capture test and a doc).

- [ ] **Step 1:** Attach a reference connection with `ext_multigrid` added
  to the shared attach set, driving the scripted sequence above; dump
  every `redraw` event verbatim, one per line, with its arguments
  unmodified.
- [ ] **Step 2:** Run the identical script single-grid and dump the same
  way.
- [ ] **Step 3:** Write the doc: one section per event with its argument
  tuple, one section for the grid-1 question, one for the id space, one
  for the mouse and resize calls, and a closing side-by-side delta table.
- [ ] **Step 4: Disconfirm.** Assert in the capture test that the
  multigrid transcript contains at least one event name absent from the
  single-grid transcript, and that the two transcripts are not equal. A
  capture that produced identical streams means `ext_multigrid` was not
  actually negotiated (the attach silently ignores unknown options), which
  is precisely the failure this step exists to catch.
- [ ] **Step 5:** `task ci`. Commit: `docs(engine): capture the multigrid
  redraw vocabulary the pinned engine emits`.

### Task 3: The bundled engine layout — resolution, `$VIMRUNTIME`, PATH fronting

**Files:**
- Modify: `crates/view-engine/src/process.rs` (bundled resolution),
  `crates/view-engine/src/env.rs` (the export and the fronting),
  `crates/view-engine/tests/env_isolation.rs` (the clearing test gains the
  bundled case)

**Why this is P6 and not earlier:** spec §16 states three things that no
code implements today — the bundled binary is the default, the engine runs
with *its own* `$VIMRUNTIME` exported, and the bundled binary is fronted on
`PATH` for child processes "so plugins that shell out to `nvim` or read the
runtime see the pin — not whatever is on PATH". `EngineConfig::default()`
names `nvim` on `PATH`, and `env.rs` clears `VIMRUNTIME` outright (correct
while there is no bundled runtime to point at, wrong the moment there is).
The release pipeline (T15) produces the layout this resolves; this task
lands first so `[engine] nvim_bin = "bundled"` (T5) has a real meaning the
day it ships rather than a placeholder that changes under it.

**Consumer call-site first:**

```rust
// crates/view/src/main.rs, where engine_config builds the spawn
let engine = bundled::resolve();
let cfg = match engine {
    // a release layout answers with its own runtime and bin dir, so the
    // child inherits the pinned pair rather than whatever PATH resolves
    Some(layout) => EngineConfig::default().with_bundled(layout),
    // a development build has no layout beside the executable; PATH nvim
    // is the honest fallback and doctor reports that it was used
    None => EngineConfig::default(),
};
```

**Interfaces:**

```rust
// crates/view-engine/src/process.rs
#[non_exhaustive]
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct BundledEngine {
    /// The pinned nvim binary shipped beside this executable.
    pub bin: PathBuf,
    /// The runtime directory that binary was built against.
    pub runtime: PathBuf,
    /// The version string the layout claims, for drift reporting.
    pub version: String,
}
impl BundledEngine {
    /// Resolves the layout shipped beside the running executable, or
    /// `None` in a build that has none.
    #[must_use]
    pub fn resolve() -> Option<Self>;
    /// Resolves a layout relative to an arbitrary executable path, so the
    /// resolution is testable without installing anything.
    #[must_use]
    pub fn resolve_from(exe: &Path) -> Option<Self>;
}
impl EngineConfig {
    #[must_use]
    pub fn with_bundled(self, layout: BundledEngine) -> Self;
}
```

The layout is `<exe_dir>/../libexec/view/nvim` with its runtime at
`<exe_dir>/../libexec/view/share/nvim/runtime`, and T15's release archive
produces exactly that shape. It is one constant in one place, asserted by
both this task's tests and T17's install-from-artifact acceptance, so the
producer and the consumer cannot drift.

**What the new tests prove:**
`bundled_layout_resolves_beside_the_executable` (a temp tree with the
layout planted); `absent_layout_falls_back_to_path_nvim`;
`bundled_spawn_exports_its_own_vimruntime` (the child's env carries the
layout's runtime, not the parent's and not empty);
`bundled_spawn_fronts_its_bin_dir_on_child_path` (a child `nvim` resolves
to the bundled one even with another nvim earlier on the parent's `PATH`);
`path_fronting_prepends_and_never_replaces` (the user's own `PATH` entries
survive after the fronted directory).

**Falsifiable check:** plant a decoy `nvim` earlier on `PATH` than the
bundled directory, spawn with a layout, and have the child report
`exepath('nvim')`: it names the bundled binary. Remove the fronting and
the same test names the decoy.

**Dependencies:** none. **Perf:** touches spawn, not key dispatch, grid
apply or paint. State it against `first_paint/shell_visible_cold_ms` — the
resolution is a handful of path checks before the child starts, and that
row is where any cost would appear.

- [ ] **Step 1: Failing test** `bundled_layout_resolves_beside_the_executable`
  against a planted temp tree; no `BundledEngine` exists yet.
- [ ] **Step 2:** `BundledEngine::resolve_from` and the thin `resolve()`
  over `std::env::current_exe`, plus `EngineConfig::with_bundled`.
- [ ] **Step 3:** The env work: `VIMRUNTIME` and `VIM` are exported from
  the layout when one is present, and stay cleared when it is not (the
  existing isolation test's contract is preserved for that case, not
  weakened — read `env_isolation.rs`'s own doc comments before touching
  the list).
- [ ] **Step 4:** PATH fronting for the child, prepending the layout's bin
  directory.
- [ ] **Step 5: Disconfirm.** Delete the fronting and confirm the decoy
  test fails; delete the export and confirm the child reports the
  parent's runtime or none. A test that passes with both mechanisms
  removed was asserting on the parent's own environment.
- [ ] **Step 6:** `task ci`. Commit: `feat(engine): a bundled engine runs
  with its own runtime and fronts its own binary`.

### Task 4: The config resolver — key registry, precedence chain, `VIEW_*` env

**Files:**
- Create: `crates/view-native/src/config/keys.rs`,
  `crates/view-native/src/config/resolve.rs`,
  `crates/view/tests/config_registry.rs`
- Modify: `crates/view-native/src/config.rs` (becomes the module root),
  `crates/view/src/main.rs` (`Cli` gains `--theme` and `--single-grid`;
  `resolve_config_path` and `engine_config` read resolved values),
  `crates/view-ai/src/config.rs` (the env layer for `[ai]`'s two keys)

**Why the registry is data:** spec §11's precedence sentence covers every
key at once, and four mechanisms need the same key list — the TOML parse,
the env lookup, the flag mapping, and the doctor's provenance row. Four
hand-maintained copies is the drift the `[native]` table already refused
(`from_parsed` walks the registry, not the file, "so an absent key is an
enabled feature by construction"). One enumerable table is the same
answer.

**Consumer call-site first:**

```rust
// crates/view/src/main.rs
let file = ViewConfig::load(config_path.as_deref()).unwrap_or_else(|e| { /* notice, defaults */ });
let resolved = config::resolve(&file, &Overrides::from(&cli));
// every read below asks the resolver, never the file, so precedence is
// answered in one place instead of at each call site
let tier = resolved.ui.tier.value;          // Option<TierChoice>, None means derive
let bin = &resolved.engine.nvim_bin.value;
// the derived arm is a sentinel the pure layer can produce; only the bin
// can probe a terminal, so only the bin turns the sentinel into a tier
let tier = tier.map_or_else(|| probed_tier(&term), Tier::from);
```

**Runner-up considered (protocol step 2):** a resolver that answers by
lookup rather than by struct, `resolved.get("ui.tier")` returning
`Option<(&str, Source)>` with every value stringly typed:

```rust
// the runner-up, side by side rather than as a strawman
let tier: Tier = resolved.get("ui.tier").map(|(v, _)| v.parse()).transpose()?.unwrap_or_else(probe);
```

It makes the doctor's provenance walk trivial (iterate the map) and adds
no per-key struct field. Rejected because every consumer then re-parses
and re-handles a failure the loader already handled — `nvim_bin` becomes a
string a caller must turn back into a `PathBuf`, and a typo in a key name
is a silent `None` instead of a compile error. The typed struct keeps
parse-once, and the doctor's walk is served by a `rows()` method over the
same struct, which is one function rather than a whole second
representation.

**Interfaces:**

```rust
// crates/view-native/src/config/resolve.rs
/// Where a resolved value came from, in the precedence order the spec
/// states: a command-line flag beats an environment variable, which beats
/// the config file, which beats the value view derives on its own.
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Source { Flag, Env, File, Derived }
impl Source {
    #[must_use]
    pub fn label(self) -> &'static str;
}

/// One resolved answer and the reason it is that answer.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Resolved<T> { pub value: T, pub source: Source }

/// Which rendering tier a user asked for. There is no `Auto` variant:
/// "auto" is the absence of a choice, carried as `None`, so the pure
/// layer never has to name a value it cannot compute.
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum TierChoice { Full, Standard, Basic }

/// Every value a flag may override, taken from the parsed command line.
#[derive(Debug, Clone, Default)]
pub struct Overrides {
    pub tier: Option<TierChoice>,
    pub theme: Option<String>,
    pub nvim_bin: Option<PathBuf>,
    pub appname: Option<String>,
    pub single_grid: Option<bool>,
}

/// Resolves every key against the process environment.
#[must_use]

**The flip is gated on measurement, not on the tests passing.** Before

**Baseline policy for the flip, stated because the ratchet fires before
the spec bar.** `plan_record` keeps `min(recorded, measured)` per metric

3. The flip commit re-records the baseline for the new attach mode, and
   the commit body carries the paired before/after matrix — this is the
   task's evidence, not a courtesy.

   only rises by hand-resetting the class's recorded cells. That reset is
   defensible exactly once here — the shipped attach mode changed, so
   the old floor was measured against a configuration view no longer
   ships — and it is defensible only when the paired evidence is in the
   same commit. A reset with no evidence in the body is the failure this
   step exists to prevent.

/// One fact the doctor reports, and how sure it is of it.
///
/// `Observed` is a fact read from a running session or a live probe.
/// `Predicted` is what would happen on the next launch, derived from
/// config alone. Printing the second as the first is the failure mode
/// that makes a diagnostic tool untrustworthy, so the distinction is in
/// the type rather than in the wording of each row.
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Confidence { Observed, Predicted }

/// How the doctor judges a row.
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub enum Verdict { Ok, Note, Warn, Problem }

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Row {
    pub label: String,
    pub value: String,
    /// Present when the row has something to say beyond its value: the
    /// key that reverses a supersession, the command that fixes a drift.
    pub detail: Option<String>,
    pub confidence: Confidence,
    pub verdict: Verdict,
}

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct Section { pub title: &'static str, pub rows: Vec<Row> }

#[derive(Debug, Clone, PartialEq, Eq)]
pub struct DoctorReport { pub sections: Vec<Section> }

impl DoctorReport {
    /// The worst verdict any row carries, which is what the process exit
    /// status is derived from.
    #[must_use]
    pub fn worst(&self) -> Verdict;
}
```

### Task 16: ACP adapter packaging and checksum distribution (P5's recorded deferral 1)

**Files:**
- Modify: `crates/view-ai/src/provision.rs`, `.anodizer.yaml`,
  `docs/ai.md`

**What P5 built and what this finishes.** P5's provisioning mechanism
downloads a pinned npm tarball, verifies it against a compiled-in
`sha256`, extracts it into the platform cache and installs its
dependencies with `npm ci` against a committed lockfile. The charter split
was explicit: mechanism in P5, "packaging and checksum distribution" in
P6. Three concrete gaps close here:

1. **The release carries the adapter.** The pinned tarball ships inside
   the platform artifact and is cosign-signed with everything else, so a
   first `[ai]` use on a machine with no network — or behind a proxy that
   blocks the npm registry — still works. "Single install command; no
   post-install steps" (spec §16) does not survive a first-run download
   that can fail.
2. **`ensure_adapter` prefers the bundled copy.** Resolution order becomes
   bundled artifact → platform cache → network download, with the
   *identical* checksum verification applied to all three. A bundled file
   is not trusted more than a downloaded one; it is verified the same way,
   because the reason to verify is tampering, not transport.
3. **The checksum manifest is distributed and verified, not just
   compiled in.** The artifact carries a manifest listing the adapter
   file, its version and its `sha256`, covered by the release's own
   signature, and `doctor` reports which source answered.

**Interfaces:**

```rust
// crates/view-ai/src/provision.rs
/// Where a resolved adapter came from, for the doctor's own row.
#[non_exhaustive]
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum AdapterSource { Bundled, Cache, Downloaded }

/// Resolves the adapter, preferring what shipped with this build.
///
/// Every source is checksum-verified against the same pin: a file that
/// arrived in the release archive is not more trustworthy than one that
/// arrived over the network, only faster and available offline.
pub fn ensure_adapter_from(id: &str, bundled_root: Option<&Path>)
    -> Result<(PathBuf, AdapterSource), ProvisionError>;
```

**What the new tests prove:**
`a_bundled_adapter_is_used_without_network` (a stub bundled root, no
server running);
`a_corrupt_bundled_adapter_is_refused_not_preferred` (flip one byte: the
error names the checksum mismatch and the file, and resolution does not
silently fall through to a download that would mask a tampered artifact —
the fall-through decision is stated in the error rather than taken
silently);
`the_manifest_version_matches_the_compiled_pin` (a release whose manifest
and binary disagree fails at build, not at a user's first run);
`the_doctor_row_names_the_source`.

**Falsifiable check:** build the artifact, cut network access, run the
adapter provisioning path: it resolves from the bundled copy with
`AdapterSource::Bundled`. Remove the bundled file and the same run fails
with the download error rather than silently succeeding from a stale
cache.

**Dependencies:** T15, T13 (the doctor row it fills).

**Perf:** none.

- [ ] **Step 1: Failing test** `a_bundled_adapter_is_used_without_network`.
- [ ] **Step 2:** `ensure_adapter_from` and the three-source resolution.

- [ ] **Step 4:** The doctor's source row.

### Task 17: Install from the built artifact, in a clean environment, on all three tier-1 platforms

**Files:**
- Create: `crates/view-harness/src/bin/install_artifact.rs`
- Modify: `Taskfile.yml` (an `acceptance:install` entry), `README.md`

**Why a program and not a checklist:** the charter's exit gate is
"distribution artifacts verified by installing from the built artifact in
a clean environment on each tier-1 platform (real Windows via winserver,
real macOS via mbp — evidence, not CI-hope)". A checklist produces a
claim; a program produces output that can be pasted as evidence and
re-run when anything changes.

**Why a Rust harness binary and not a bash script with a `.ps1` twin.**
This is the one acceptance leg that must run on Windows, and the two
alternatives both cost more than they save. A `.sh` plus a hand-kept
`.ps1` twin is two implementations of one contract, and the twin that
drifts is always the one nobody runs locally; the drift shows up as a
Windows leg that passes because it checks less. A bash-only script under
Git-Bash would work for the file checks and then fail at check 5, the pty
edit — the check that proves the artifact is an editor rather than a
binary that starts — because a Windows pty is ConPTY and Git-Bash's
`winpty` shim is not the terminal view ships against. `view-harness`
already depends on `portable-pty`, whose Windows backend is ConPTY, so
the one implementation runs the same checks on all three platforms and
check 5 exercises the real thing. The precedent for a harness binary
standing in for a shell script is in the tree:
`crates/view-harness/src/bin/rtt_acceptance.rs`, which is a binary
precisely because its mechanism is platform-shaped.

It gets its own target rather than joining `task acceptance`, because
that target's existing legs are bash and need tmux:

```yaml
acceptance:install:
  desc: Install the signed artifact into an empty prefix and prove it edits a file (task acceptance:install -- --artifact dist/view-x86_64-pc-windows-msvc.zip)
  cmds:
    - cargo run --release -p view-harness --bin install-artifact -- {{.CLI_ARGS}}
```

**What the binary does**, given an artifact path or URL:

1. `cosign verify-blob` against the artifact and its signature.
2. Unpack into an empty prefix with a scrubbed environment (no `PATH` nvim,
   no `XDG_CONFIG_HOME` pointing at a real config, no `NVIM_APPNAME`).
3. `view --version`, then `view doctor`: assert exit 0 and assert the
   engine section reports the bundled layout present with a version equal
   to `.engine-pin`.
4. Assert the resolved engine is the bundled one and not a system nvim, by
   planting a decoy `nvim` earlier on `PATH` and re-running the engine row.
5. Open a file, type, save, quit through a pty; assert the file's content,
   which is the smallest end-to-end proof that the installed artifact is
   an editor and not just a binary that starts.
6. Assert the adapter resolves from the bundled copy with the network
   unavailable (T16), on the platforms where the adapter is shipped.
7. Print a machine-readable summary line per check, so a failing leg names
   the check rather than requiring a log read.

**Falsifiable check:** run the binary against an artifact with the bundled
engine deliberately removed: it fails at check 3 naming the missing
layout. Run it against an unsigned artifact: it fails at check 1. A run
that passes on either is not verifying, it is reporting.

**Dependencies:** T15, T16, T14 (the exit-code contract check 3 relies on).

**Perf:** none.

## Recorded deferrals (this plan's own — recorded, never silently absent)

Each of these is a thing a reader might expect in P6 and will not find.

   the browser pane, in-pane media and the N-surface tiling layout in the

   to accept it (`PaneKind` is an enum with one variant today) without
   building any of it now. Chartered, not deferred by this plan's
   judgment.

2. **`view doctor --json`.** Nothing in the charter or the spec asks for a
   machine-readable doctor, and T17's acceptance script gets what it needs
   from the exit-code contract plus a summary line. Recorded as the
   natural shape if a consumer appears (the report model is already plain
   data, so the renderer is the only new surface), not built speculatively.

3. **A Windows tap channel** for the internal-boundary bench cells
   (`input_path`, `output_path`, `echo_path`, `echo_speculated`, and the
   two AI rows). After T18's `output_path` scoping edit, every budget row
   these cells carry is scoped to a linux class and `echo_path` carries
   none at all, so no Windows bar exists for any of them and building the
   channel would produce numbers nothing reads. T18 records each as a
   register row with its own reason. If a Windows-class bar is ever wanted
   for one of them, the channel is the prerequisite and this is the note
   that says so.

4. **ACP v2 support.** T25 re-verifies the protocol's state and, if v2 has
   left draft, surfaces a pitch for the user's ruling. Implementing it
   unasked would branch diff review's whole hunk model against a draft
   surface; skipping the pitch would be a silent de-scope. The pitch is
   the deliverable; the implementation is the user's call.

5. **Attach to an already-running instance (`:detach` / `:connect`).**
   Chartered post-v0.1 in `.claude/plans/2026-08-14-post-v01-charters.md`
   (C1), explicitly after remote editing ships. Named here only so its
   absence from a phase that touches panes and sessions is a recorded
   boundary rather than an oversight.

6. **A second bundled ACP adapter.** `AdapterPin` is already a table
   rather than a single row, and `[ai] agent` already accepts an arbitrary
   command for anything unpinned. Adding a second pinned adapter is a data
   change whenever a second agent is worth shipping, not a P6 task.
