# P5.5 Implementation Plan — Remote Editing (with Speculative Echo)

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development to implement this plan
> task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** local-feel remote editing (spec:623, §9 invented capability; also
spec:350-353, §5.6 — v0.1 CORE, ruled 2026-08-05, spec:906, no
"post-v0.1" framing anywhere in this plan). The engine spawns over SSH;
paint and input stay local; speculative echo hides link latency; clipboard
is already identical local/remote via OSC52. Sequenced first inside P5.5
alongside P1 supervision (spec:615-616, `HANDOFF.md:67-68`).

**This plan is two ordered sub-efforts, not one capability with a bolt-on.**
Speculative echo is P3's hard *prerequisite*, established by the pitch
table's own arithmetic (`p4-end-perf-pitch-table.md:64-80`,
`invention-research.md:248-273`):

```
                 local today                remote, unspeculated        remote, speculated
echo p99 bar  |  0.727 ms  vs  8.0 ms   |   0.727 ms + 2*RTT        |   local paint, RTT hidden
              |  12x clear             |   breaks the 8 ms bar      |   bar met on the
              |                        |   at any RTT above ~3.6 ms |   speculated metric
```

Without speculation, remote editing has no defensible latency story and
this plan's own "local-feel" name is a claim it cannot make. **Part A
(Tasks 1-6) builds speculative echo. Part B (Tasks 7-15) builds the SSH
transport on top of a latency story that already has a floor.** Part B
tasks depend on Part A landing first; no task in Part B ships ahead of
Part A's exit gate (its own new metric recorded, its own
`unexplained_paints` re-scoping done — see Task 5).

**Architecture — Part A:** a display-only predictor + epoch model in
`view-core`, mode-gated to insert-mode plain-character insertion; a
speculated layer in `view-surface` reconciled against the authoritative
grid on every redraw, epoch-stamped so a late or reordered redraw can never
apply against a stale prediction (resolves open question P3-3 below); a
new gated bench metric with its own budget row; `unexplained_paints`
re-scoped so the safety net still catches genuinely inexplicable paints
once speculation legitimately produces explained ones.

**Architecture — Part B:** the remote engine is spawned by wrapping the
system `ssh` client as the child `Command`, not a new SSH library —
`EngineHandle::start_pumped` already takes the child's stdout/stdin as
generic `Read`/`Write` (`handle.rs:245-259`), the identical shape the local
spawn already uses, so a remote engine is a different `Command`, not a new
interface. `EngineConfig` gains an optional remote spec; `build_command`
branches. No new crate dependency, no audit-deps carve-out, no reopened
async question — the system `ssh` binary carries its own config, agent
forwarding, and host-key verification for free, which a hand-rolled SSH
client would have to reimplement to match.

**Tech stack:** Part A: no new dependency. Part B: no new dependency (see
above) — this **supersedes** the research's tentative `ssh2`-crate
recommendation (`invention-research.md:593-600`) with a stronger finding
from this plan's own seam inventory (§ "Open design questions" below).

## Global Constraints

Hard rules, embedded verbatim. Every task states which rule bounds it.

- **nvim owns all buffer text. No view subsystem holds authoritative text
  state. Buffer mutation happens only through `Effect::Rpc`.** Binds
  hardest in Part A: a speculated cell is display-only by construction and
  never becomes an `Effect::Rpc` source — this is architected around, not
  tested against (`p4-end-perf-pitch-table.md:86`). Binds in Part B too:
  the remote engine is still the sole owner of buffer text; only the
  transport between view and that engine changes.
- **The paint loop never awaits RPC. The RPC reader thread never blocks.**
  Binds hardest in Part A: a speculated paint happens *before* the
  authoritative redraw arrives, by design — this rule is what makes that
  safe rather than a race, since the paint that shows a prediction was
  never waiting on the RPC that will confirm or correct it.
- **No unwrap/expect/panic in lib crates.** Every new fallible path (SSH
  connect failure, epoch-mismatch reconciliation, doctor-guidance stub)
  returns through a typed error, never panics.
- **Dependency direction: core ← surface ← {native, ai}; only view-engine
  speaks RPC; only view-tui touches the terminal.** The predictor's pure
  state lives in `view-core`; the speculated layer lives in `view-surface`
  (surface depends on core, legal edge); the remote spawn machinery stays
  entirely inside `view-engine`, same as the local spawn it extends.
- **Performance is a contract.** Speculative echo's entire purpose is a
  latency claim — every task in Part A states its latency consequence as
  the primary content of its acceptance criterion, not an addendum.
- Use `task` targets, never raw cargo/git, for build/fmt/lint/test/commit.
- Comments are WHY-only; doc comments render for users. No session-
  narrative markers.
- Non-conventional commit prefixes are parenthesised scopes:
  `feat(speculate):`, `feat(remote):` — never `speculate:`/`remote:`.
- **Never weaken `echo.minimal`'s existing 1.10 budget, the 5 µs tap bar,
  or the 1.15 calibration floor.** The speculated path gates on its own
  *new* metric; the honest row keeps measuring the honest unspeculated
  round trip — already ruled three places (`2026-08-08-measurement-layer-rulings.md`
  §6, `budgets.toml`'s `echo.minimal` `why`, spec's own echo row) and
  restated as this plan's own constraint in Task 5.
- **v0.1 framing:** this is a CORE v0.1 feature (2026-08-05 ruling) — no
  task, comment, or commit message uses "post-v0.1" language about
  anything this plan ships. (Attach/detach via `:detach`/`:connect` *is*
  correctly post-v0.1 — chartered per the amended `spec:352-354` in
  `2026-08-14-post-v01-charters.md` C1, gated on this plan shipping — this
  plan does not build it and does not need to say so defensively; spawn,
  not attach, is the whole charter.)
- **Cross-plan landing order: Task 15 depends on P1 supervision's
  interfaces, not just this plan's own Part A→Part B gate.**
  `Engine::restart()`, `Liveness::Dead`, `HeartbeatWatch`, and the
  `EngineBusyState` extension point Task 15 extends additively are all
  defined by the P1 supervision plan
  (`.claude/plans/2026-08-09-p5_5-supervision.md`),

## Open design questions — resolved in this plan

Three left open by the research, one this plan's own seam inventory
resolves more concretely than the research's tentative answer, and four
more surfaced by review that the original draft assumed rather than
decided.

1. **Sync SSH crate vs. async, given the tokio ban.** *Superseded, not
   just resolved.* The research recommended a synchronous crate (`ssh2`)
   over an async one (`invention-research.md:593-600`). This plan goes
   further: **no SSH crate at all.** `EngineHandle::start_pumped` already
   takes the child's stdout/stdin as generic `Read + Write`
   (`handle.rs:245-259` — confirmed against the as-built tree this
   session), the exact shape `Engine::spawn`'s local `Command` already
   produces (`process.rs:428-493`). Wrapping the system `ssh` binary as
   the child `Command` — `ssh -T -o BatchMode=yes <opts> <host> -- <remote
   nvim> --embed <args>` — produces the identical `Child` with piped
   stdio the local path already handles, so `Engine::spawn`'s downstream
   code needs **zero** new abstraction, no new dependency, and therefore
   no `audit-deps.sh` carve-out to argue for. It also gets `~/.ssh/config`,
   `ssh-agent` forwarding, `ProxyJump`, and host-key verification for
   free, which any in-process SSH library would have to reimplement to
   match — a config-derivability win as well as a complexity win. Rejected
   runner-up: an `ssh2`/libssh2 binding, which reopens exactly the
   "avoid reimplementing what a trusted system tool already does
   correctly" argument that OSC52's own design already made for clipboard
   (`spec:623` cites OSC52 precisely because it defers to the terminal
   emulator instead of reimplementing clipboard transport) — the same
   argument applies to SSH transport once the seam inventory shows the
   system binary is a drop-in `Command`.
2. **Where does the remote connection live relative to `Engine`?** *Also
   resolved more concretely than the research's tentative "new `Transport`
   abstraction" lean* (`invention-research.md:601-610`). Given (1) above,
   there is exactly one flow — build a `Command`, take its piped stdio,
   hand it to `EngineHandle::start_pumped` — whether that `Command` is
   `nvim --embed` or `ssh host -- nvim --embed`. `EngineConfig` gains an
   optional field describing the remote target (Task 8); `build_command`
   branches on its presence. A `Transport` trait was considered and
   rejected: it would introduce an interface boundary for something that
   is a `Command`-construction difference, not an interface difference —
   `EngineHandle` is *already* transport-agnostic by construction (it
   takes `Read`/`Write`), so adding a trait teaches nothing it does not
   already know, at the cost of a new abstraction with one production
   implementation on each side.
3. **Speculation rollback under real network jitter — late/reordered
   redraws.** *Resolved by the design itself, not by new measurement* (the
   research found no evidence either way and made no recommendation,
   `invention-research.md:611-618`). Task 1's epoch counter is the answer:
   every predicted cell is stamped with the epoch active when it was
   predicted, and Task 3's reconciliation only ever applies a redraw
   against the epoch it names — a redraw whose epoch does not match the
   *current* epoch (because a mode change, control char, or a newer
   keystroke has already advanced it) is applied as a hard reset to
   authoritative content, discarding whatever was speculated, rather than
   attempting to reconcile it against a prediction it was never about.
   This makes correctness independent of arrival order by construction:
   there is no code path that trusts a redraw's *timing* to mean anything,
   only its epoch tag. No real RTT measurement is needed to prove this
   safe; Task 4's oracle coverage proves it by injecting reordering
   directly. That said, epoch-matching only catches a redraw that *names*
   a stale epoch — it says nothing about a prediction whose epoch stays
   current but whose exact cell coordinates a redraw simply never revisits
   (a partial update, a scroll). Task 1/3's `SPECULATION_MAX_AGE` bound
   closes that orthogonal gap with an age cap, not a content comparison.
4. **Does `cfg.env_plan()` reach the remote nvim?** *Not by default —
   ssh does not forward a local process's environment to the remote side
   without server-side `AcceptEnv` cooperation this plan cannot assume any
   target has configured.* Rather than depend on that, Task 7 renders
   `env_plan()`'s SET entries into the one remote command string view
   constructs itself (`ssh ... -- 'env' 'VAR=value' '--' 'nvim' '--embed'`,
   every token POSIX single-quote-escaped), which works on any POSIX
   remote unconditionally. The single-string construction is load-bearing,
   not stylistic: ssh does not preserve `Command::arg()` boundaries to the
   remote side — it joins everything trailing the destination argument
   with spaces and hands that one string to the remote shell to re-parse —
   so a design that passed `env`/each `VAR=value` as separate arguments
   would silently word-split (or, for a value containing `$`/`;`/a
   backtick, execute) the moment a value contained a space or a quote.
   `HOST_REDIRECT_VARS` (`env.rs:67`)'s path-shaped vars (`MYVIMRC`,
   `XDG_*`) are the concrete reachable case, not a theoretical one.
   `env_remove` entries are a documented, deliberate divergence: they
   exist to strip host-inherited vars from a *local* hermetic child and
   have nothing to unset on a remote host that never inherited the local
   shell's environment in the first place.
5. **What happens on Windows, given the repo's own CI mirrors
   windows-msvc?** *Client-side: supported, no design change — Windows
   ships OpenSSH's `ssh.exe`, and `Command::new("ssh")` resolves it the
   same way as any other `PATH`-resolved binary; Task 10 gains
   Windows-specific guidance for the one divergence (the "OpenSSH Client"
   optional feature can be absent, unlike POSIX where `ssh` is normally
   preinstalled).* Remote-target-side: **out of scope for v0.1, stated
   explicitly rather than silently assumed** — the single-quote-escaped
   command line Task 7 constructs is POSIX-shell-shaped (both the
   escaping rule and the `env VAR=value --` grammar inside it), and a
   `cmd.exe`/PowerShell remote target would need a different
   command-line grammar and a different quoting rule this plan does not
   design. `RemoteSpec`'s doc comment states the POSIX assumption; Task
   10 gets a verify-at-implementation step run on the winserver mirror
   confirming the *client* path (Windows as the `--remote`-issuing
   machine) behaves identically to POSIX.
6. **What happens when the ssh connection drops mid-session, and how does
   that interact with supervision's auto-restart?** *Deliberately not a
   special case.* `EngineHandle` cannot distinguish an SSH child's stdio
   from a local child's — a dropped connection surfaces as ordinary EOF,
   which the supervision plan's `Liveness::Dead` path already owns with
   zero remote-specific code. `Engine::restart()` re-invokes the same
   `build_command`, which re-runs `ssh` unchanged. Task 15 adds the
   remote-specific pieces that path still needs on its own: capped
   reconnect backoff (so a dead host does not spin the shell into
   thousands of instant reconnect attempts), a give-up threshold, and a
   decision on `ControlMaster`/`ControlPersist` (OFF by default — a user
   who wants connection reuse already has their own `~/.ssh/config` for
   it, since this plan shells out to the user's real `ssh`, not a
   private one).
7. **What is the remote working directory for `--remote host:path`, given
   non-interactive ssh's own cwd behavior?** *No `cd` machinery needed.*
   Non-interactive SSH sessions start at the remote `$HOME` by POSIX/
   OpenSSH convention (the same behavior `scp host:path` already relies
   on), so a relative `path` in `--remote host:path` resolves exactly the
   way it would from an interactive login shell, with no special-casing
   in `build_command`. Task 9's CLI parsing passes `path` through to nvim
   verbatim — it does not attempt local resolution, since "relative to
   what" only has an answer on the remote host, not the local one.

## CLI invocation shape — decided, with alternatives shown

Config-derivability rule: enumerate what is auto-determinable, require only
a genuine user choice. Three shapes considered as call-sites:

```bash
# A -- URI-scheme prefix (rejected: invents syntax view users have never
#      seen; no existing view or nvim flag uses a `scheme:` prefix)
$ view ssh:prod-box/etc/app.conf

# B -- fully separate flags (rejected: every field the user already wrote
#      in ~/.ssh/config becomes a second place to write it, and the two
#      can drift)
$ view --ssh-host prod-box --ssh-user deploy --ssh-port 2222 --ssh-path /etc/app.conf

# C -- scp/ssh's own [user@]host[:path] syntax behind one flag (CHOSEN)
$ view --remote prod-box                            # $HOME on prod-box; user/port/identity from ~/.ssh/config
$ view --remote deploy@prod-box:/etc/app.conf        # explicit user + path
$ view --remote prod-box --ssh-port 2222             # override when ~/.ssh/config lacks a Port line
$ view --remote prod-box --ssh-opt ProxyJump=bastion  # generic escape hatch: -o KEY=VALUE, repeatable
```

**Chosen C** because every engineer who can already run `scp host:path` or
`ssh host` already knows this syntax — zero new syntax to learn, which is
the "painless migration" contract (spec §1) applied to the CLI surface
itself, not just the editing experience. `--ssh-opt` (repeatable, mapping
directly to `ssh -o KEY=VALUE`) is the one generic override this plan
ships instead of a per-option flag for every possible SSH setting
(`IdentityFile`, `ProxyJump`, `ConnectTimeout`, ...): a closed list of
flags is a maintenance treadmill the moment a user needs an option this
plan's authors did not anticipate, exactly the reasoning `main.rs`'s
passthrough field already uses for nvim's own CLI flags
(`main.rs`'s doc comment on `passthrough`, "enumerating each nvim flag here
... was rejected as a maintenance treadmill"). Only `--remote <target>` is
required; `--ssh-port` and `--ssh-opt` are overrides with correct derived
defaults (`~/.ssh/config`, matching plain `ssh`'s own resolution order).

### Task 1: Predictor + epoch model in `view-core`

**Files:** Create `crates/view-core/src/native/speculate.rs`; modify
`crates/view-core/src/msg.rs` (additive `Msg`/`Effect` arms, `#[non_exhaustive]`)

**Rule bound:** "nvim owns all buffer text" — `SpeculateState` is
architected so nothing it holds can become an `Effect::Rpc` payload; it is
read only by `view-surface::render` (Task 2) and by Task 3's reconciler,
never by the RPC dispatch path.

**Design:** Mosh-paper shape (`p4-end-perf-pitch-table.md:91-94`):
display-only insert-mode plain-character prediction; epochs reset on mode
change and any control character. Everything else is unspeculated by
default — no cursor-motion, no deletion, no multi-byte-composition
speculation in v0.1.

**Interfaces:**

```rust
// view-core/src/native/speculate.rs
/// Monotonic epoch, advanced on every mode change and every control
/// character. A predicted cell is meaningless once its epoch is stale --
/// see [`SpeculateState::reconcile`] and open design question 3 in the
/// plan this module implements.
#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord)]
pub struct Epoch(u64);

/// One display-only predicted glyph: what plain-character insert-mode
/// typing is expected to show at `row`/`col` before the authoritative
/// redraw confirms or corrects it. `predicted_at` bounds how long a
/// prediction may survive an authoritative redraw that never happens to
/// touch its exact cell (a partial redraw batch, a scroll that moves
/// content without re-sending it) -- see [`SpeculateState::expire_stale`]
/// and open design question 3's age-cap addendum.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct PredictedCell {
    pub row: u16,
    pub col: u16,
    pub glyph: char,
    pub epoch: Epoch,
    pub predicted_at: SinceStamp,
}

/// Pure state: no I/O, no RPC awareness. Mode-gated -- [`predict`] is a
/// no-op outside insert mode, so a picker query or a normal-mode motion
/// never accumulates speculative state it would have to unwind.
#[derive(Debug, Clone, Default)]
pub struct SpeculateState { epoch: Epoch, pending: Vec<PredictedCell> }

/// How long a prediction may sit in `pending` without any authoritative
/// redraw having touched its cell before it is force-discarded, regardless
/// of epoch. Bounds the case `reconcile`'s per-cell matching cannot close
/// on its own: a redraw batch that never happens to re-send the exact
/// predicted cell (a partial update, a scroll) would otherwise leave a
/// stale glyph on screen indefinitely. Sized above the largest RTT tier
/// this plan's own acceptance proof exercises (300 ms, see the RTT-
/// injection acceptance task) with a wide margin, so a legitimately slow
/// but healthy round trip is never mistaken for staleness.
pub const SPECULATION_MAX_AGE: Duration = Duration::from_secs(1);

impl SpeculateState {
    /// Folds one insert-mode plain-character keystroke into a new
    /// predicted cell at the engine's last-known cursor position, tagged
    /// with the current epoch and `now`. A no-op outside insert mode or
    /// for any non-plain-character key (control chars advance the epoch
    /// instead, via [`Self::reset_epoch`]).
    #[must_use]
    pub fn predict(&mut self, mode: &str, key: char, cursor: (u16, u16), now: SinceStamp) -> Option<PredictedCell>;
    /// Advances the epoch and clears every pending prediction -- called on
    /// mode change and on any control character, per the design's
    /// unspeculated-by-default rule.
    pub fn reset_epoch(&mut self);
    /// Discards every prediction whose `predicted_at` is older than
    /// [`SPECULATION_MAX_AGE`] as of `now`, independent of epoch. Called
    /// from the runtime loop's own per-pass observation, the same
    /// discipline `HeartbeatWatch`'s prober-driven tick already
    /// establishes -- a bounded, host-supplied clock, never a clock read
    /// from inside pure `view-core`.
    pub fn expire_stale(&mut self, now: SinceStamp);
    #[must_use] pub fn pending(&self) -> &[PredictedCell];
}
```

**Falsifiable check:** a headless test drives `predict()` with insert-mode
plain characters and asserts pending cells accumulate with the same epoch
and the `now` passed in as `predicted_at`; a mode change or control char
clears them and bumps the epoch; a non-insert-mode key produces no
prediction.

### Task 3: Reconciliation against authoritative `GridLine`, epoch-safe rollback, and an age bound

**Files:** Modify `crates/view-core/src/native/speculate.rs`,
`crates/view/src/runtime.rs` (dispatch on redraw, per-pass expiry)

**Rule bound:** resolves open design question 3 (epoch-tagged
reconciliation is safe under reordering by construction, § above) — states
the mechanism precisely here since this is where it is implemented. Also
closes the gap `reconcile`'s own per-cell matching cannot close on its
own: a redraw batch that never happens to re-send a predicted cell's exact
coordinates (a partial update, a scroll that moves content without
resending it) would otherwise leave `predict`'s output in `pending`
un-reconciled indefinitely, with a stale glyph still painted. Task 1's
`SPECULATION_MAX_AGE` bound and `expire_stale` close it deterministically,
independent of redraw batching or scroll-event granularity this plan does
not need to characterize precisely to stay correct.

**`expire_stale` is wired to the loop's own unconditional per-pass site,
not to redraw dispatch.** A call site gated on `Msg::Redraw` arriving
would never fire during a total redraw stall — the exact failure class
`SPECULATION_MAX_AGE` exists to bound — so `expire_stale` is called once
per loop pass unconditionally, the same discipline `runtime.rs`'s existing
`note_write_stall` call already establishes at its own call site
(`runtime.rs:1138`, immediately before the loop blocks waiting for the
next message, so it runs every pass, including passes where that wait
times out against the write-stall watch's own armed deadline with nothing
delivered). `reconcile` keeps its redraw-triggered call site — it
legitimately needs redraw content to compare predictions against; only
`expire_stale`'s wiring changes.

**Interfaces:**

```rust
impl SpeculateState {
    /// Applied on every authoritative redraw. Compares the redraw's cells
    /// at each pending prediction's coordinates:
    /// - matching glyph, current epoch: the prediction is confirmed,
    ///   dropped from `pending` (nothing left to paint speculatively --
    ///   the real thing is now on screen).
    /// - mismatching glyph, current epoch: a genuine misprediction --
    ///   dropped, and the authoritative redraw wins (it always would have;
    ///   this is not a special case).
    /// - **any prediction not tagged with the current epoch: dropped
    ///   unconditionally**, regardless of glyph match, because a stale
    ///   epoch means a mode change or control char has already
    ///   invalidated whatever context produced it -- this is what makes
    ///   a late or reordered redraw safe without measuring real network
    ///   jitter (design question 3).
    pub fn reconcile(&mut self, redraw: &[GridLine]);
}
// reconcile stays gated on Msg::Redraw arriving -- it legitimately needs
// redraw content to compare predictions against. expire_stale does NOT
// share that call site: a call reachable only when a redraw arrives is
// provably unreachable under a total redraw stall, the exact class the
// age bound exists to catch. expire_stale is instead called once per loop
// pass, unconditionally, at the same discipline runtime.rs's own
// note_write_stall call already establishes:
//   // top of every pass, unconditionally (runtime.rs:1138's discipline):
//   speculate.expire_stale(now);
//   ...
//   // only inside the Msg::Redraw(damage) dispatch arm:
//   speculate.reconcile(&redraw);
```

**Falsifiable check:** three reconciliation cases, each its own test, plus
two expiry cases. (a) A redraw arriving in-order confirms a matching
prediction — `pending()` empties. (b) A redraw arriving in-order with a
mismatched glyph — the prediction is dropped, no crash, no stale paint
survives. (c) **The reordering case**: a redraw tagged with a stale epoch
(simulating a late arrival after a mode change already advanced the
epoch) is dropped unconditionally, even when its glyph would have
matched — proving epoch, not glyph match, is the safety property. (d)
**The unbounded-staleness case, pure-function level**: a prediction whose
epoch stays current and whose cell is never touched by any redraw
(simulating a partial update that never covers it) is discarded once
`SPECULATION_MAX_AGE` elapses, proving `expire_stale`'s own logic closes
the window `reconcile` alone leaves open. (e) **The wiring-level case**:
proves the per-pass call site itself, not just `expire_stale`'s logic in
isolation — drives `runtime.rs`'s loop with **zero** `Msg::Redraw`
messages arriving at all (not merely a redraw that misses the predicted
cell's coordinates) for longer than `SPECULATION_MAX_AGE`, and asserts
`pending()` is still empty afterward, proving expiry is reachable under a
genuine total redraw stall — the class a redraw-gated call site could
never resolve, no matter how correct its own internal logic is.

**Interfaces:**

```rust
// view-engine/src/process.rs
/// A remote target, resolved from the CLI's `--remote`/`--ssh-*` flags
/// into the arguments `build_command` needs. Kept as a small, explicit
/// struct rather than a pre-built `Vec<OsString>` so a caller can inspect
/// what was resolved (auth-failure guidance, a future `:View remote`
/// introspector) without re-parsing an argument vector. Assumes a POSIX
/// remote shell (v0.1 scope): the constructed command line is
/// POSIX-shell-shaped and is not designed for a `cmd.exe`/PowerShell
/// remote target.
#[non_exhaustive]
#[derive(Debug, Clone)]
pub struct RemoteSpec {
    pub target: String,            // "[user@]host", ssh's own syntax verbatim
    pub remote_nvim_bin: String,   // defaults to "nvim", resolved on the remote $PATH
    pub port: Option<u16>,
    pub extra_ssh_opts: Vec<String>,  // "-o KEY=VALUE" pairs, from --ssh-opt
}
```

`build_command` (`process.rs:606-618`) branches. The destination argument
(`remote.target`) is parsed locally by the ssh client itself, same as
`-T`/`-o`/`-p`; everything after it is a different matter (see below):

```rust
fn build_command(cfg: &EngineConfig) -> Command {
    match &cfg.remote {
        None => {
            let mut c = Command::new(&cfg.nvim_bin);
            c.arg("--embed").args(&cfg.extra_args);
            c
        }
        Some(remote) => {
            let mut c = Command::new("ssh");
            c.args(["-T", "-o", "BatchMode=yes"]);   // no pty, no interactive prompt hang
            if let Some(port) = remote.port { c.args(["-p", &port.to_string()]); }
            for opt in &remote.extra_ssh_opts { c.args(["-o", opt]); }
            c.arg(&remote.target);
            c.arg(remote_command_line(remote, cfg));
            c
        }
    }
    // stdio: UNCHANGED from today -- Stdio::piped() x2, Stdio::null() for
    // stderr, exactly as the local path already sets
}
```

`-o BatchMode=yes` is the rule-bound choice: it turns an auth failure into
an immediate, non-interactive error (`Permission denied`, connection
refused) rather than a password prompt the embedded, headless process
cannot render — the SSH-transport analogue of "the paint loop never awaits
RPC," since a blocking password prompt on the child's stdin would hang the
handshake the exact way an unhandled `SwapExists` prompt would (P1 Task 4's
same class of problem, solved the same way: make the failure mode loud and
immediate instead of a silent hang).

**Environment reaches the remote nvim explicitly, quoted as one command
view builds itself.** `cfg.env_plan()`'s `SET` entries (`process.rs:238`)
are applied today via `command.env()` on the local child — for the local
path that *is* the remote nvim's process, so it's sufficient. For the
remote branch, `command.env()` only touches the local `ssh` process's own
environment, which `ssh` does not forward to the far side; forwarding it
would require the remote sshd to opt in with `AcceptEnv`, a server-side
setting this plan cannot assume any target has configured. Rather than
depend on that cooperation, the SET entries ride the remote command line
itself. **Building that command line as separate `Command::arg()`
elements does not work**: OpenSSH does not preserve argv boundaries past
the destination argument — everything trailing it is joined with spaces
into ONE string and handed to the remote user's shell to re-parse. A value
containing a space would silently word-split into extra remote shell
tokens; a value containing `$`, backticks, or `;` could execute on the
remote shell. `HOST_REDIRECT_VARS` (`env.rs:67`) forwards path-shaped vars
(`MYVIMRC`, `XDG_*`) that plausibly contain spaces, making this a reachable
bug, not a theoretical one. The fix is to build and quote that one string
ourselves, since there is no argv boundary for `Command` to preserve in
the first place — ssh flattens it regardless:

```rust
/// Builds the single string ssh hands to the remote shell for re-parsing.
/// ssh does not preserve `Command::arg()` boundaries across the wire:
/// every argument trailing the destination is joined with spaces into one
/// string before the remote side ever sees it, so view constructs that
/// one string itself rather than relying on argv passthrough it does not
/// control. Every token -- `env`, each `KEY=value`, `--`, the remote nvim
/// path, its flags, and every one of `cfg.extra_args` -- is POSIX
/// single-quote-escaped uniformly, not just the ones judged to "need" it:
/// classifying which tokens are safe is exactly the mistake that leaves a
/// space/quote/`$`/`;`/backtick-bearing value unescaped.
fn remote_command_line(remote: &RemoteSpec, cfg: &EngineConfig) -> String {
    let mut tokens = vec!["env".to_string()];
    for (key, value) in cfg.env_plan() {
        if let Some(value) = value {
            tokens.push(format!("{}={}", key.to_string_lossy(), value.to_string_lossy()));
        }
        // a `None` (env_remove) entry is a local-only hermetic-isolation
        // concern -- it has nothing to unset on a remote host that never
        // inherited the local shell's environment in the first place, so
        // it is deliberately not forwarded.
    }
    tokens.push("--".to_string());
    tokens.push(remote.remote_nvim_bin.clone());
    tokens.push("--embed".to_string());
    tokens.extend(cfg.extra_args.iter().map(|a| a.to_string_lossy().into_owned()));
    tokens.iter().map(|t| shell_quote(t)).collect::<Vec<_>>().join(" ")
}

/// POSIX single-quote escaping: wrap `token` in `'...'`, and replace every
/// literal `'` inside it with `'\''` (close quote, escaped quote, reopen
/// quote) -- the standard rule for a string a POSIX shell parses back as
/// exactly one word regardless of its contents.
```

### Task 12: Oracle coverage — stub-`ssh` double (CI-safe) + opt-in real SSH

**Files:** Create `crates/view-oracle/src/remote.rs`,
`scripts/test-fixtures/fake-ssh` (the stub double Task 7/11 already lean on)

**Design:** CI hosts cannot be assumed to have a reachable SSH daemon or
network egress, so the primary coverage path is a stub: a short script on
`PATH` (or injected via `EngineConfig::nvim_bin`-equivalent override in the
harness) that reproduces real OpenSSH's own argv-flattening behavior
rather than a more forgiving one. Real ssh parses its own connection
options (`-T`, `-o`, `-p`, the destination) locally, then joins
**everything trailing the destination** with spaces into one string and
hands that string to the remote shell (`sh -c`) to re-parse — it does not
preserve the caller's argv boundaries. A double that instead exec'd its
trailing arguments directly, preserving them as a normal argv, would be
strictly more forgiving than real ssh: it would happily run even against
a caller that got quoting wrong, and the stub would give false confidence
about exactly the class of bug this plan's env-quoting finding was. The
stub therefore does the same thing real ssh does: after stripping its own
recognized connection flags, it joins whatever remains with `IFS`
(spaces) and execs `sh -c "$joined"` — exactly reproducing the RPC-pipe
shape *and* the re-parsing hazard a real SSH session would present,
without a network hop.

```sh
# scripts/test-fixtures/fake-ssh -- sketch, not the literal implementation
#!/bin/sh

# ssh client would, leaving only the trailing "command" arguments

# real ssh joins every trailing argument with spaces and hands the result
# to the remote shell -- reproduced here, not bypassed, since a double
# that preserved argv boundaries would be more forgiving than reality and
# could pass with broken quoting a real remote host would reject
exec sh -c "$*"
```

target when one is configured via an environment variable

### Task 15: Reconnect on dropped SSH — the likeliest real failure mode

**Files:** Modify `crates/view-engine/src/process.rs` (backoff constants,

connection — a laptop sleeping, a VPN blip, a bastion recycling — is the
likeliest real failure mode remote mode will hit in practice, ahead of
outright auth failure (Task 10) or a nonexistent binary (Task 7's
disconfirm test); it needs a task with its own falsifiable check, not a
mention inside another task's prose.

**Landing-order dependency, not just this plan's own Part A→Part B
gate.** This task's own code consumes interfaces this plan does not
define: `Engine::restart()`, `Liveness::Dead`, `HeartbeatWatch` (the
heartbeat/liveness machinery), and the `EngineBusyState` extension point
the banner text below extends additively. All four land with the P1
supervision plan, not with anything in the tree this plan is authored
against (`b96296c`). **Task 15 does not begin implementation until
supervision's Tasks 1-3 (heartbeat probe, `Liveness`/`Dead`,
`Engine::restart()`) have landed in the tree** — Tasks 7-14 earlier in
this Part consume no supervision interface and are not gated on it.

**Design:** `EngineHandle` cannot distinguish an SSH child's stdio from a
local child's, so a dropped connection needs zero special-casing to be
detected — it surfaces as ordinary read-side EOF, which the supervision
plan's `HeartbeatWatch`/`Liveness::Dead` path already owns. What remote
mode adds on top is specific to *recovering* from that Dead state when
the underlying transport is `ssh`: reconnecting means re-running the same
`build_command` remote branch, and a naive unconditional retry would spin
the local shell into repeated instant `ssh` invocations against a host
that is still unreachable. `Engine::restart()` (supervision plan, Task 3)
is reused unchanged; this task adds capped backoff *around* the decision
to call it when the dead engine is remote:

```rust
// view-engine/src/process.rs
/// Backoff applied between successive `Engine::restart()` calls when the
/// dead engine's config carries a `RemoteSpec`. A local engine restarts
/// immediately since a crashed local process is not going to become
/// reachable by waiting; a remote engine's unreachability is often
/// transient (network blip, host reboot window), so retrying immediately
/// every time would just spin `ssh` uselessly.
pub const REMOTE_RECONNECT_BACKOFF_BASE: Duration = Duration::from_secs(1);
pub const REMOTE_RECONNECT_MAX_ATTEMPTS: u32 = 5;   // ~31s total before giving up, doubling from the 1s base
```

**`ControlMaster`/`ControlPersist`: decided OFF by default.** This plan
shells out to the user's own `ssh`, which already reads the user's own
`~/.ssh/config` — a user who wants connection multiplexing/reuse across
reconnect attempts already has the standard way to configure it
(`ControlMaster auto`, `ControlPersist 10m` in their own config), and
`--ssh-opt ControlMaster=auto` (Task 9's generic escape hatch) covers a
one-off override without this plan inventing a second, view-specific
place to configure the same behavior ssh already exposes.

**UI coordination with supervision:** the backoff/give-up sequence
extends supervision's existing `EngineBusyState` additively — no new UI
state machine. While backoff is in progress the banner shows
`connection lost — reconnecting (N/5)`, deliberately cause-neutral.
`EngineHandle` sees a remote nvim process crashing and a network
connection dropping as the identical signal — ordinary read-side EOF —
so nothing in this plan can honestly attribute the failure to one cause
or the other, and the banner does not pretend otherwise. Recovery is
identical either way too: the same reconnect/backoff sequence runs
regardless of which one actually happened, since `build_command`'s remote
branch is simply re-run either way and there is no code path that
distinguishes them. If `REMOTE_RECONNECT_MAX_ATTEMPTS` is exhausted, it
becomes the same `Dead` banner+modal supervision's Task 2 already defines
(immediate, no grace period), with `Restart` in that modal triggering one
more manual attempt.

**Falsifiable check:** killing the stub-`ssh` double's process mid-session
surfaces as `Liveness::Dead` within one heartbeat interval; the reconnect
loop retries with the documented backoff (asserted via the actual
inter-attempt delays, not just "it retries"); a stub-ssh double
configured to keep failing exhausts at exactly
`REMOTE_RECONNECT_MAX_ATTEMPTS` and lands on the same Dead banner+modal
supervision defines, not a new state.

- [ ] **Step 1: Failing test.** Kill the stub-ssh double's underlying
  process mid-session; assert the engine reaches `Liveness::Dead`. FAIL

  check that remote mode did not silently break it).
- [ ] **Step 2: Failing test for backoff.** A remote engine's restart is
  attempted with the doubling backoff, asserted via the actual recorded
  inter-attempt timestamps against `REMOTE_RECONNECT_BACKOFF_BASE`. FAIL
  (no backoff exists yet), implement, pass.
- [ ] **Step 3: Failing test for give-up.** A stub-ssh double configured
  to always fail exhausts at `REMOTE_RECONNECT_MAX_ATTEMPTS` and stops
  retrying automatically, landing on supervision's Dead banner+modal.
  FAIL, implement the attempt cap, pass.
- [ ] **Step 4:** Wire the cause-neutral `connection lost — reconnecting
  (N/5)` banner text into supervision's existing `EngineBusyState`
  additively — no new variant beyond what carries the attempt count.
- [ ] **Step 5:** Build `scripts/acceptance/remote-reconnect.sh`: spawn
  against the stub-ssh double, kill the ssh process mid-edit, observe the

