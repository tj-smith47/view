## 1. The mechanism: nvim's layout is the layout, view draws the rest

Under `ext_multigrid` nvim tells view where every window sits
(`win_pos grid win startrow startcol width height`, decoded into
`UiEvent::WinPos { grid, win, startrow, startcol, width, height }` at
`crates/view-core/src/events.rs:52`) and paints only chrome into the global
grid: the `│` separator column between horizontal neighbours and, with
`laststatus=2`, a status row under every window. The window's own text
arrives in a grid of its own.

`nvim_ui_try_resize_grid(grid, w, h)` on a split window sets that window's
*inner* size (`w_width_request`/`w_height_request` → `win_set_inner_size`,
nvim `src/nvim/ui.c:754-777` at the pinned v0.12.4; verified 2026-09-20).
The layout slot the window occupies does not change; the grid nvim draws
text into becomes smaller than the slot, and the difference is the UI's to
fill. That is the whole mechanism: in tiles mode view requests an inner size
smaller than each slot and paints a frame and a gap into the difference.
nvim keeps owning the layout tree, `<C-w>` commands keep working, a plugin
that splits windows keeps working, and view never resizes a window it did
not create.

Three facts about the request decide the geometry, all read from the pinned
source:

- The request is a standing one. `w_width_request`/`w_height_request` are
  written only by `ui.c:774-775`, and `win_set_inner_size`
  (`window.c:7000-7003`) reads them unclamped on every layout change
  (`win_new_width` at `window.c:7071-7077`, `win_new_height` at
  `window.c:6898-6904`). After a `:vsplit` halves a slot, the grid keeps the
  old and now too-wide request until view sends a new one. So view re-sends
  on every `win_pos` whose slot size changed, in every case.
- A request of `0, 0` is the only value that returns a window to its slot
  size (`ui.c:773`, "non-positive indicates no request"). That is what a
  gapless tile, a tile too small to frame, and a flip to `"nvim"` mode send.
- The request ignores `winbar`. `window.c:7005-7008` takes
  `w_height_request` when it is set, and `w_height_outer` is that plus the
  winbar row (`window.c:7050-7052`), so a window with a winbar gets one row
  more grid than the request names. The top margin arrives as
  `win_viewport_margins` (`window.c:7057-7061`), already decoded into
  `UiEvent::WinViewportMargins { grid, win, top, bottom, left, right }`
  (`crates/view-core/src/events.rs:136`) and today dropped unread
  (`crates/view-core/src/update/ui_event.rs:405`). The height request
  carries that margin as a term.

### Tile geometry

For a window whose slot is `S = (row, col, w, h)` in global-grid cells, with
`m` the `win_viewport_margins` top margin for that grid (`0` for a window
with no winbar):

| look | inner request | grid origin | frame cells |
|---|---|---|---|
| tiles, `gaps = true` | `(w - 4, h - 4 - m)` | `(row + 2, col + 2)` | the ring at offset 1 inside the slot; offset 0 is gap |
| tiles, `gaps = false` | `(0, 0)`, no request, so the grid is the slot | `(row, col)` | none inside the slot; the lattice is nvim's own separator column and status row, restyled |
| tiles, slot too small to frame: `w < 5` or `h < 5 + m` | `(0, 0)` | `(row, col)` | none; the tile is drawn bare |
| `"nvim"` | `(0, 0)` | `(row, col)` | none |

`MIN_FRAMED_SLOT = (5, 5)` is the slot's own minimum: a gapped frame spends
two columns and two rows per side, so a slot of 5 is the narrowest that
leaves one inner cell. The height test carries the winbar margin on top of
it, because the request is what has to stay positive. A 5-row slot with a
winbar gives `h - 4 - m = 0`, and `ui.c:773-775` stores each axis as
`MAX(value, 0)` and reads a non-positive one as no request at all
(`window.c:7005-7008` then takes the slot's own height for that axis). The
grid would fill the whole slot while the painter drew a ring for a one-row
inner, so the window text would paint over the top and bottom edges. The
rule is therefore "either axis of the request would be under 1", which is
`w < 5 || h < 5 + m`, and `inner_request` answers `(0, 0)` there.

Gapped, two windows side by side, the slot for the left window is columns
0–39, the separator is column 40, the right window is columns 41–80. Cell
map, `g` gap, `f` frame, `.` inner grid, `s` nvim's separator column
(painted as gap):

g f . . . . . . . . . . . . . . . . . f g   s   g f . . . . . . . f g

The horizontal distance between two frames is three cells (two gaps and the
separator column); the vertical distance is three rows (two gaps and the
status row). The screen edge gets the same: view attaches the outer grid two
columns and one row short, places it at terminal `(1, 1)`, and paints the
outer ring as gap, so a frame sits two cells in from the terminal edge. The
bottom takes no ring row: view holds `laststatus = 2` under tiles whatever
`[native] statusline` says, so the bottom tiles' status rows sit where it
would. With `cmdheight = 1` nvim's command line row sits below the status
row and is not part of the margin, so the bottom then shows two empty rows
and the command line row. Amended 2026-09-23: a bottom ring row on top of
the status row left three empty rows under the frames against two on every
other side, and a hold that followed the switch left one.

Gapless paints no ring inside a slot. Every tile fills its slot, and the one
cell between two tiles is the cell nvim already draws there: the separator
column, and the status row under a window. view restyles those cells as the
frame, with `┬ ┴ ├ ┤ ┼` junctions where a separator meets a status row. The
outer edge comes from attaching the outer grid one column and one row short
and placing it at terminal `(1, 1)`, so the top and left tiles take an edge
from the ring. A bottom tile takes its bottom edge from its own status row,
which `laststatus = 2` gives every window and which view restyles like any
other lattice cell; nvim's command line sits in the row under it. Only the
right edge comes from the terminal edge. Every tile then has exactly one
frame cell between it and its neighbour, which is what makes a junction
glyph possible: a doubled line has no cell for a junction to sit in.

Cell map, gapless, the same two windows, `r` the outer ring, `f` frame,
`.` inner grid. The bottom `f` run is the two windows' status rows, and the
command line's row sits under the map:

```

r . . . . . . . . . . f . . . . . . . . . . .
r . . . . . . . . . . f . . . . . . . . . . .
r . . . . . . . . . . f . . . . . . . . . . .
r f f f f f f f f f f f f f f f f f f f f f f
```

The outer attach size is one function for both looks:
`grid_target_for(size, chrome_rows, statusline, ring)`, where `ring` is `0`
under `"nvim"`, `2` under gapped tiles and `1` under gapless, subtracted
from the width, with `ring.min(1)` off the height (the held status rows
stand in for the bottom ring row), and the outer grid's
horizontal screen offset is
`u16::from(ring > 0)`.

Vertically the pill and the ring stack, top to bottom: the pill at terminal
row 0 spanning the full terminal width, the ring's top row under it, and
grid 1's first row at `chrome_rows + u16::from(ring > 0)`. The placement
offset is `view_surface::render`'s (`crates/view-surface/src/lib.rs:394`,
`let offset = model.chrome_rows()`), which gains the ring term; the pill
spans the full width because it is chrome view owns outright and the ring
frames the grid, not the session.

`statusline` is `false` under tiles, because tiles mode paints no
bottom bar and reserves no row for one, so `Model::statusline_rows()`
(`crates/view-core/src/model.rs:1222`) answers 0 there. The spawn's `--cmd`
geometry (`crates/view/src/main.rs:1057`) passes the same `ring`, so the
child sources the user's config at the size it will be attached at;
`crates/view-core/src/model.rs:1271-1277` states why the two have to agree.
`crates/view/src/startup.rs:1102`'s floor call follows the same signature.

Frame glyphs come from the probed `BorderSet` (`view_surface::overlay`):
rounded corners under `unicode_boxes`, ASCII `+ - |` otherwise. Gapless
junctions are `┬ ┴ ├ ┤ ┼` under `unicode_boxes` and `+` otherwise.

### Frame content

- Gapped, top edge, left-aligned inside the run after one frame cell and one
  space: the buffer's tail name, `[+]` when modified. The run is
  `FloatTitle` fg, bold, over the tile's background, the same style §7.1
  gives a float's title.
- Gapped, bottom edge: the status segments of §3.
- Gapless, bottom edge: the name left-aligned and the segments
  right-aligned, both in the one row the tile has. Gapless has no top edge
  of its own, so the top-edge name is a gapped-only element.
- Frame fg: the active tile's is `accent`; every other tile's is
  `WinSeparator` fg as the colorscheme states it, the way a float border
  takes a stated `FloatBorder`. Where the separator is only `Normal` fg
  again, the float border's own derivation (60 % of that fg) stands in.
  Amended 2026-09-23: the 50 % blend toward the background left inactive
  frames unreadable under the user's transparent Dracula config
  (`#6272a4` to `#313952`).

### `accent`

§7.1 names `accent` as `Function` fg with `Statement` as fallback, and the
inventory found no code that resolves it. Neither group can join
`chrome_groups!`: nvim emits `hl_group_set` only for the UI-element groups
in `hlf_names` (`highlight.c:138`, `highlight_group.c:2282`), and
`every_group_is_one_nvim_broadcasts` (`crates/view-core/src/theme.rs:668`)
fails any row whose name is absent from `BROADCAST`, which neither name is.

So `accent` is probed, on the shape `probe_default_hl`
(`crates/view-engine/src/nvim_api.rs:3540`) already has for `Normal`:

```rust
// crates/view-core/src/msg.rs, beside RpcCall::GetDefaultHl
GetAccentHl { generation: u64 },

// crates/view-core/src/msg.rs, beside Msg::HlProbeReply
AccentProbeReply {
    generation: u64,
    function_fg: Option<u32>,
    statement_fg: Option<u32>,
},

// crates/view-core/src/theme.rs
impl Theme {
    #[must_use]
    pub fn accent(&self) -> ResolvedStyle;
}
```

`Theme::accent()` answers the first of: `[ui.tokens] accent` where the user
wrote one, `Function`'s probed fg, `Statement`'s probed fg, the `Emphasis`
fallback. The user's token comes first because that is the order `Source`
gives every other key (`crates/view-core/src/config.rs:14`: flag, env, file,
derived). The probe is re-issued on `Msg::ColorSchemeChanged` beside the
`Normal` one.

`[ui.tokens]` is a new table. `crates/view-native/src/config.rs` carries no
`tokens` key today, so Task 1 adds the parser, the `ConfigKey` row
(`crates/view-native/src/config/keys.rs:51`) and the `view.toml.example`
block that `the_registry_and_the_example_document_the_same_keys` requires.

This is the first consumer of the accent role; the float border keeps
`FloatBorder` (§7.1 amended 2026-08-21) and is not changed by S3.

The active tile is the pane `GridRegistry::cursor_grid()`

### Floats over an inset grid

nvim resolves a `relative = "win"` float from the window's *slot* origin:
`window.c:900-903` sets `comp_row`/`comp_col` from `w_winrow`/`w_wincol`,
`window.c:955-957` adds the anchor grid's own comp position, and
`win_float_pos` (`window.c:983-988`) sends the result. nvim does not know
view's inner origin, so under gapped tiles every cursor-anchored float (an
LSP hover, a completion menu at `bufpos`) resolves two rows and two columns
up and left of the text it belongs to.

The registry corrects it: a `GridEvent::Float` whose `anchor_grid` is a
tiled window pane is shifted by that pane's inset before it is placed, and
clamped to the outer grid. A float anchored to grid 1 is not shifted, and
under gapless the inset is zero, so nothing moves. `ext_popupmenu`'s
`grid, row, col` (`crates/view-surface/src/lib.rs:793-815`) positions
through the same origin and is corrected with it.

### Mouse

`nvim_input_mouse(grid, row, col)` resolves by grid coordinates
(`mouse.c:1711-1720`), so a click is handed to nvim relative to the inner
origin, which is what `Pane.origin` already is (§1, Task 1 step 2). A grid-1
position under multigrid resolves only to split separators
(`mouse.c:1800-1802`), so a click on a frame cell or a gap belongs to
nothing: `position_owner` (`crates/view-core/src/update/mouse.rs:66`)
already answers `None` off every pane, and that is the answer a frame cell
gets. Separator drag-resize is not supported today either, so nothing
regresses.

### Paint cost

Frames repaint only when a slot changes (`win_pos`), the cursor grid
changes, the theme changes, or the terminal resizes. A `grid_line` on a
window grid damages that grid's rows and nothing of the frame.

The inner-size request is the expensive half, and it lands on a felt cell.
Every `nvim_ui_try_resize_grid` ends in `redraw_later(wp, UPD_NOT_VALID)`
(`window.c:7040`), so nvim re-sends every `grid_line` of that window. At
attach the first `win_pos` batch would trigger one request per window, which
is a second full redraw of the whole screen over RPC, and
`startup.settled_ratio_p50` is `kind = "felt"` with a bar of 1.0 seated at
1.0287486403697355 on `dev-linux`/`user` (`crates/view-bench/budgets.toml`,
the `[[shortfall]]` at line 599). Three things hold it:

- the request goes out only when the slot, the look or the top margin
  changed since the last one sent for that grid, an idempotent guard in the
  registry keyed on all three, with its own pin. The look is part of the key
  because a gaps flip changes what every window owes while leaving slots
  whose neighbours absorb the ring change exactly where they were;
- the spawn `--cmd` geometry carries the ring, so the outer size is right
  before init.lua runs and only the per-window insets cost a redraw;
- the `--cmd` cannot pre-request inner sizes, because the windows do not
  exist yet, so one relayout at attach is the floor under gapped tiles, and
  Task 1 measures what it costs on the `user` seat under both look modes.

The planted isolation config names `panes = "nvim"` (§8), so a leg that
wants tiles asks for them, and which door it uses follows from what it
spawns. A leg that runs the `view` binary -- the bench `user` seat, every
`PtySession` replay -- exports `VIEW_UI_PANES=tiles`, which `layer()`
(`crates/view-native/src/config/resolve.rs:464`) ranks above the file. A leg
attached through `EngineSession` calls `set_panes("tiles")`
(`crates/view-oracle/src/lib.rs:591`): that driver builds its own `Model`
and never runs `view-native`'s resolver, so the variable reaches nothing
there. No leg rewrites the planted file.

## 2. Look modes

```toml
[ui]
panes = "auto"   # "auto" | "tiles" | "nvim"
gaps = true      # false = gapless: frames share edges, no outer gap
```

| `panes` | what is on screen |
|---|---|
| `"tiles"` | frames, gaps per `gaps`, accent on the active tile, status in the bottom edge, the top pill |
| `"nvim"` | what the tree paints today: nvim's `│` separators restyled through `WinSeparator`, view's bottom statusline bar, the tabline only when `[native] tabline = true` |
| `"auto"` | `"nvim"` when a tiling window manager owns the layout, else `"tiles"` |

Detection for `"auto"`, in this order, first match wins, and the marker is
kept for the report row:

| marker | value |
|---|---|
| `HYPRLAND_INSTANCE_SIGNATURE` set | `nvim` |
| `SWAYSOCK` set | `nvim` |
| `I3SOCK` set | `nvim` |
| `XDG_CURRENT_DESKTOP` names (case-insensitive, any colon-separated member) one of `Hyprland`, `sway`, `i3`, `river`, `niri`, `bspwm`, `dwm`, `awesome`, `qtile`, `xmonad`, `herbstluftwm`, `leftwm` | `nvim` |
| `_NET_WM_NAME`-class hints where a desktop name is absent (pending the user's ruling) | `nvim` |
| anything else, including `SSH_CONNECTION`/`SSH_TTY` set, no `DISPLAY`/`WAYLAND_DISPLAY`, macOS, Windows, GNOME, KDE | `tiles` |

The `_NET_WM_NAME` row is the roadmap's own, carried as the roadmap states
it. Reading it needs an X connection at startup, and every window manager on
the list above already exports one of the first four markers, so the session
report carries a pitch to drop the row and the row stands until the user
rules. Task 1 builds the four environment markers and the fallback either
way, so the ruling changes one row and nothing else.

The fallback is `tiles`, which is also what an ssh session gets, because the
client's environment never reaches the server.

`[engine] single_grid = true` drops `Ext::Multigrid`
(`crates/view-native/src/config.rs:797`), and without multigrid there is no
`win_pos` and no per-window grid, so tiles cannot exist. `resolve.rs`
resolves `panes` to `nvim` with a notice whenever `single_grid` is true,
whatever the file or the flag says.

The resolved mode and its marker are a `ResolvedConfig` row
(`crates/view-native/src/config/resolve.rs:377`, `rows()`), shown as
`ui.panes = nvim (derived: HYPRLAND_INSTANCE_SIGNATURE)`. Doctor (S7) reads
the rows and inherits it; no `doctor` command exists in `crates/view/src`
today, and the row is the mechanism it will read. `VIEW_UI_PANES` and
`--panes` follow the flag > env > file > derived chain `layer()`
(`resolve.rs:464`) gives every other `[ui]` key.

`[ui]` is not a new table. It carries `tier` and `theme` today, parsed into
the crate-private `UiFile` (`crates/view-native/src/config.rs:115`) that
`ViewConfig` (`config.rs:519`) holds, and resolved into `ResolvedUi`
(`config/resolve.rs:95`). S3 adds `panes`, `gaps`, `tokens` and `surfaces`
to both types; Task 1 adds the first three and Task 4 the fourth, and
Task 1's signature block gives both shapes.

`:View panes tiles|nvim|auto` flips the mode live. It is a resize-class
repaint: view re-attaches the outer grid at the new size (the ring appears,
changes width or disappears), sends `(0, 0)` or the new inset to every
window grid, and marks the grid `dirty_full`. `:View panes` with no argument
reports the mode and its marker as a notice.

`:View panes` is a `CommandForm` (`crates/view-core/src/native/mappings.rs:117`)
of `feature: "ui", verb: "panes"`. `"ui"` is not a feature id, and
`Msg::FeatureInvoke`'s dispatch (`crates/view-core/src/update/mod.rs:432`)
matches on feature ids today, so Task 1 teaches that dispatch the one
non-feature form and `is_reachable_feature` the exemption that goes with it.

## 3. Status in the frame, and the bar under `"nvim"`

Tiles mode holds `laststatus` at 2, so every window gets a status row. That
row is where nvim paints its own status text into grid 1, and view paints
over it: gap under `gaps = true`, the frame's bottom edge under
`gaps = false`. `"nvim"` mode keeps today's hold at 0 and the bottom bar.

The held value is a row in the static `CHANNELS` table
(`crates/view-core/src/native/channels.rs:216-229`):

```rust
SurfaceChannels {
    surface: Surface::Statusline,
    channels: &[
        Channel::Hold { option: "laststatus", scope: Scope::Global, value: ChannelValue::Int(0) },
        Channel::Covered { option: "statusline", by: "laststatus" },
    ],
},
```

A per-mode value makes that one row's *value* a function of the look, and
the row stays the only claim on `laststatus`:

```rust
// crates/view-core/src/native/channels.rs, on ChannelValue
/// The two values one option takes, keyed by look. Resolved before the
/// value reaches the wire, so no path can hold a look-keyed spelling.
ByLook { nvim: &'static ChannelValue, tiles: &'static ChannelValue },

// the Statusline row's Hold becomes
value: ChannelValue::ByLook {
    nvim: &ChannelValue::Int(0),
    tiles: &ChannelValue::Int(2),
},
```

A second claimant is what makes this a trap rather than a preference.
`supersede::takeovers()` (`crates/view-native/src/supersede.rs:225`) skips
any `Hold` whose option `channels::shared_by_surfaces`
(`crates/view-core/src/native/channels.rs:354`,
`claimants_of(channel).count() > 1`) answers true, and `session_held()`
(`channels.rs:365`) then holds that option against the whole attach set
rather than any feature's switch. A `Surface::Frame` row carrying its own
`Hold` on `laststatus` would make the option shared, so **both** rows would
be skipped, no feature would own the option, and
`[native] statusline = false` would stop handing the row back. So
`Surface::Frame` exists as the surface the frame paints and carries an empty
channels row, the shape `Surface::Grid` already has.

`supersede::plan(cfg, features, look)` (`supersede.rs:281`, one argument
wider) carries the look into `plan_from(cfg, features, takeovers, look)`
(`:298`) and on into `takeover_call(row, look)` (`:191`, called at `:312`),
and `takeover_call`'s `value.wire(look)` is where a `ByLook` resolves.
`takeovers()` (`:225`) copies the value off the static table untouched and
`TakeoverKind::Option.value` stays a `ChannelValue`, so a `ByLook` may sit
in a derived row right up to `wire`.

`ChannelValue::wire` (`channels.rs:60`) takes the look as a second argument
and stays total over all four variants, so a `ByLook` that reaches it
answers its own look's leg instead of needing a fourth arm that guesses.
Its three production callers (`crates/view/src/native.rs:269`,
`supersede.rs:199` and `:207`) each pass the session's look, by
add-beside-then-switch, and every one of them already knows it: they are
the takeover and the hand-back, both of which run against a resolved
config. `NativeSession` takes the look from the `ViewConfig` its `load`
(`native.rs:113`) is already handed: a `look: Look` field set there from
`resolved.ui`, read by `follow_up` (`:187`) and by the session-held walk at
`:262-271`. `all_enabled` (`:395`, inside the `#[cfg(test)]` impl at
`:377`) takes the default look, and the `wire()` call in `mod tests`
(`:409`) at `:555` passes it.
`laststatus_is_claimed_by_one_surface_whatever_the_look` in `channels.rs`
holds the single claim, and
`an_enabled_statusline_yields_one_entry_reversed_by_its_own_off_switch`
(`supersede.rs:331`) asserts `OptionValue::Int(0)`, so it keeps passing
under `look = nvim` beside the two new plan pins.

The status row under tiles is the frame's, not the statusline feature's, so
`[native] statusline = false` under tiles hands the segments back and leaves
the row standing: the tile keeps its bottom edge and the edge carries no
segments. Under `"nvim"` that switch keeps handing the whole row back as it
does today, and the user's own `laststatus` (0, 1, 2 or 3) then decides what
nvim draws there.

One consequence is owed to `docs/surface-ownership.md`. Under
`laststatus=2` the `Covered { statusline, by: "laststatus" }` row no longer
covers anything: nvim evaluates a `statusline` expression once per window
per status redraw, so a lualine config keeps paying for a row view paints
over. The page says so in words.

Segments, left to right in the bottom edge, one space between, in the
frame's own fg unless named. The sources are `StatuslineState`'s
(`crates/view-core/src/native/statusline.rs:27-52`), whose fields are
private and read through `StatuslineState::view(width)`:

| segment | source today | scope |
|---|---|---|
| mode (`NORMAL`, `INSERT`, macro recording fused) | `msg_showmode` | active tile only |
| git branch | the bridge's git trigger group | every tile, per buffer |
| diagnostics `E n W n` | the bridge's `DiagnosticChanged` callback; `error`/`warn` roles | every tile, per buffer |
| position `row:col` | `msg_ruler`, which nvim emits only under `laststatus=0` | every tile, from the bridge instead (below) |
| showcmd | `msg_showcmd` | active tile only |

`StatuslineState` is per session and the tiles need per-window values. Task
2 makes the bridge (`crates/view-engine/src/nvim_api.rs`, the `view_bridge`
autocmd channel) send one `window` trigger per window on `WinEnter`,
`BufEnter`, `BufModifiedSet`, `DiagnosticChanged`, `CursorMoved` and
`CursorMovedI` carrying `{win, buf, name, modified, row, col, errors,
warnings}` for the window that changed, and `Model` keeps a
`window_status: HashMap<WinHandle, WindowStatus>`.

`msg_ruler` stops the moment `laststatus` is 2: `statusline.c:450` returns
and clears the ext ruler when `w_status_height > 0`, and
`statusline.c:543-550` emits it only when the ruler is not part of a status
line. So the position segment comes from the trigger in tiles mode and from
`msg_ruler` in `"nvim"` mode, and the two never both feed one tile.

The `CursorMoved` trigger is throttled on the nvim side to one message per
event-loop tick (`vim.schedule` with a pending flag; `vim.schedule` defers
to the next tick of the loop, not to a redraw), so the input path gains no
RPC round trip: the segment lags the cursor by at most one tick, and a
keystroke never waits for it.

Under `"nvim"` mode the bar is what ships today (`full-statusline-bar.txt`
golden), and this task also gives it what the roadmap's #26 asked for: its
own background (`StatusLine` bg), the mode segment in `accent`, and a
filetype segment after the file name. Nothing else about it changes.

## 4. The top pill

The tab row becomes a pill: tabpages (or buffers when there is one tabpage
and `[native] tabline_shows = "buffers"`) centred, the current one on
`TabLineSel`, the rest on `TabLine`, the row on `TabLineFill`. The left edge
carries session identity (the `--remote` host, when there is one) and the
right edge the agent state.

That state has two sources, and the pill reads both.
`view_core::native::ai_registry::SessionState` is
`NotStarted | Trusted | Active | Crashed` (`ai_registry.rs:18-27`), and
"waiting" is the panel's own `AiPanelState::pending_permission`
(`crates/view-core/src/native/ai_panel/mod.rs:176`). The pill prints:

| condition | word |
|---|---|
| `pending_permission.is_some()` | `waiting` |
| `SessionState::Active` | `running` |
| `SessionState::Crashed` | `crashed` |
| `SessionState::Trusted` or `NotStarted` | `idle` |

```toml
[native]
tabline = true            # tiles mode default; false leaves the row to nvim and your plugins
tabline_shows = "tabs"    # "tabs" | "buffers": buffers only while there is one tabpage
```

`[native] tabline` keeps its bool type and gains a derived default: `true`
under `panes = "tiles"`, `false` under `"nvim"`, and an explicit value wins
in both. Today's default is fixed in `NativeConfig::defaults()`
(`crates/view-native/src/config.rs:648`) from the registry's `default_on`
bit, before a `ResolvedConfig` exists, so the derivation moves into
`resolve.rs`'s layering and answers `Source::Derived`, which is what makes
the report row read `derived`. Today's row in `view.toml.example` ("the one
switch that ships off") is rewritten to say so.

The pill is one row and it is reserved whenever `tabline` is on, since a
pill with one workspace still carries the session identity;
`Model::chrome_rows()` (`crates/view-core/src/model.rs:1209`) returns 1
whenever the pill is on, and keeps today's more-than-one-tab rule for
`"nvim"` mode. The row is terminal row 0 and spans the full terminal width,
with the outer ring's top row under it and grid 1 under that, the stacking
§1 states.

Buffers come from a bridge trigger on `BufAdd`/`BufDelete`/`BufEnter`
listing the listed buffers, and `ext_tabline` keeps carrying tabpages. A
click on a name switches directly rather than through an ex command: under
`"buffers"` it sends `RpcCall::SelectBuffer { buf }` (`nvim_set_current_buf`),
under `"tabs"` `RpcCall::SelectTab { tab }` (`nvim_set_current_tabpage`).
Neither call exists today, and neither does any tabline click routing:
`position_owner` (`crates/view-core/src/update/mouse.rs:66`) answers `None`
for every row the tabline reserved, so Task 3 adds the routing with the
calls.

## 5. Surfaces: overlay or windowed, per surface

```toml
[ui.surfaces.tree]
placement = "overlay"   # "overlay" | "windowed"
anchor    = "left"      # left | right
size      = 30          # percent of columns; [native] tree_width is its alias

[ui.surfaces.agent]
placement = "overlay"
anchor    = "right"     # left | right
size      = 30          # [ai] panel_width is its alias

[ui.surfaces.palette]
placement = "overlay"
anchor    = "center"    # overlay: center | top | bottom; windowed: top | bottom
size      = 40          # percent of rows

[ui.surfaces.notifications]
placement = "overlay"
anchor    = "top-right" # overlay: top-left | top-right | bottom-left | bottom-right; windowed: left | right | top | bottom
size      = 30          # percent of columns (left/right) or rows (top/bottom)

[keys]
toggle_gaps    = "<leader>ug"
cycle_surfaces = "<leader>uw"   # config -> all windowed -> all overlay -> config
```

`anchor` is one field with two readings, the float anchor in overlay mode
and the tile edge in windowed mode, on the existing `Anchor` enum
(`crates/view-core/src/native/geometry.rs:60`, today
`Center | Left | Right | Top | Bottom`, `#[non_exhaustive]` with
`#[default] Center`), extended with `TopLeft`, `TopRight`, `BottomLeft` and
`BottomRight` for the notification float. The allowed set is per surface, as
the table above lists it. A value outside the set is a startup notice
through `discarded()` (`resolve.rs:515`) and the default, never a rejected
config.

### What windowed means

A windowed surface is an nvim window view creates through `Effect::Rpc`
(`nvim_open_win` with `split = left|right|above|below` and `win = 0`,
`src/nvim/api/win_config.c:48-57`) over a scratch buffer with
`buftype = nofile`, `bufhidden = wipe`, `buflisted = false`,
`filetype = view-<surface>`, `winfixwidth`/`winfixheight`, and
`modifiable = false` with `readonly` set. The compositor draws the surface's
own view into that pane's rect and never paints the window's `grid_line`.
That is the §15.1 tile kind the roadmap names (a tile whose content is not
an nvim grid), and S6's image, media and browser tiles reuse it.

The buffer is unwritable because a key can reach nvim before view knows the
cursor has moved into the surface (below). A key that lands there moves a
cursor and writes nothing, which keeps the hard rule intact from both sides:
nvim owns the buffer text, and the buffer holds none.

### Focus

Focus is derived from the redraw, never from the bridge, and never stored.
`Model::focus()` (`crates/view-core/src/model.rs:681`) reads `Model::overlays`
today, and its doc says why: a stored focus is a second fact that has to
agree with overlay presence, and every close is a chance to leave it naming
an overlay that is gone. The enum's own doc (`model.rs:2110-2111`) repeats
it. A windowed surface is a third source of the same answer, so the
derivation gains an arm and no field:

```rust
// crates/view-core/src/model.rs, the body of Model::focus()
match self.focused_overlay() {
    Some(overlay) => Focus::Native(overlay.id),
    None => match self.engine.grids().native_pane_focus() {
        Some(surface) => Focus::Pane(surface),
        None => Focus::Engine,
    },
}

// crates/view-core/src/grid/registry.rs
impl GridRegistry {
    /// The surface of the `PaneKind::Native` pane `cursor_grid()` names,
    /// or `None` when the cursor sits in an ordinary window or grid 1.
    #[must_use]
    pub fn native_pane_focus(&self) -> Option<NativeSurface>;
}
```

`win_pos` and `grid_cursor_goto` arrive in the same redraw batch
(`drawscreen.c:784`), so `cursor_grid()` (`registry.rs:645`) is already
correct when the batch flushes and a key folded after it reads the right
answer. A bridge notification would arrive after `update()` had already
routed whatever the user typed in between.

`update/ui_event.rs`'s `UiEvent::Flush` arm (`ui_event.rs:188`) sets no
focus, because there is none to set; it marks dirty as it does today. An
open overlay owns the keyboard whatever the cursor grid is, and that is the
first arm of the derivation rather than a guard: with the windowed tree
focused, `<leader>ff` opens the picker, the cursor grid is still the tree's,
and `focus()` answers `Native(picker)` until the picker closes. The same
arm answers `Native(picker)` while the cursor sits in an ordinary window.
Closing the picker hands the answer to whichever of `Engine` and `Pane(_)`
the cursor grid names at that moment, which is what a derivation does.

`Focus` (`crates/view-core/src/model.rs:2113`) is
`#[non_exhaustive] #[derive(Debug, Clone, Copy, PartialEq, Eq)]` with
`Engine` and `Native(OverlayId)`. `Focus::Native` routes keys through
`Model::focused_overlay_mut()` (`update/mod.rs:1381`) and paste through the
focused overlay (`update/mod.rs:255`), and a windowed surface is a pane
rather than an overlay, so it takes a variant of its own:

```rust
// crates/view-core/src/model.rs, beside Focus::Native
Pane(NativeSurface),
```

Because the enum is `#[non_exhaustive]`, no crate downstream of `view-core`
needs an arm. Every site that names `Focus` is inside `view-core`:
`model.rs` (the enum and `focus()`'s construction sites at `:683-684`),
`update/mod.rs` (the paste match at `:254-255` and the key route at
`:1328`/`:1381`), `native/speculate.rs:267` (an `== Focus::Engine` test) and
`native/ai_panel/mod.rs:191`. Those four files change with it, and nothing
in `view-surface` or `update/paste.rs` names `Focus` at all.

`<Esc>` in a windowed surface sends `:wincmd p` and leaves the tile
standing. `<leader>e` from inside the windowed tree closes its window (#32);
from anywhere else it opens or focuses it. The same shape holds for
`<leader>ai` and the windowed agent panel, on top of the three states
`docs/keymaps.md` already gives it.

Two sidebars on one edge stack vertically when windowed (`tree` above
`agent`, the second opened with `split = below` inside the first's window)
and open over each other when overlay.

`size` is the same percent of the outer grid in both placements. The visible
content width is not the same: a windowed tile is measured in outer-grid
columns, which are already `ring` narrower than the terminal, and a gapped
tile spends four more on its frame and gaps. So the cycle key does not
resize the surface, and the text inside it is up to six columns narrower
when windowed and gapped. `docs/tiled-ui.md` states the number.

Windowed `palette` is a tile at the bottom edge (`anchor = "bottom"`) of
`size` percent rows, opened when the palette opens and closed when it
closes. Windowed `notifications` is a stream: every entry of the message
history in one scrollable list, newest first, each row carrying its
timestamp as `YYYY-MM-DD HH:MM:SS`, the same spelling the history overlay
gets. Focusing the stream stops the 4 s transient timeout
(`TRANSIENT_TOAST_TIMEOUT`, `crates/view-core/src/native/toast.rs:137`) for
as long as it holds focus, through the same slot-timer pause the pause key
uses (§7.1 motion rule 5), and the history keys (`j`, `k`, `<C-d>`, `<C-u>`,
`gg`, `G`, `y`, `d`) work inside it unchanged. The dispatch that answers
them is `message_history_key`
(`crates/view-core/src/update/surfaces.rs:312`), which is what the stream
routes into; `HISTORY_KEYS` (`update/surfaces.rs:284`) is `#[cfg(test)]`,
the list the documentation walk presses, and nothing in a running session
reads it.

The timestamp needs a clock view-core does not have. `update()` takes no
time, `Effect::ScheduleToastExpiry` exists precisely because the loop has no
free-running clock (`crates/view-core/src/msg.rs:1318-1324`), and the one
`SystemTime` field in the crate (`ai_registry.rs:39`) is never written. So
the runtime stamps: `crates/view/src/runtime.rs:170` is the single
production fold, and it calls `Model::set_now(SystemTime::now())` before
`update(model, msg)`. `Messages::push` (`model/messages.rs:316`) reads that
value into `MessageEntry`'s `at`. One clock read per folded message, on the
loop thread, off the paint path.

The palette also takes its default key here. The roadmap's Menu row asks for
`<leader><leader>`, and `DEFAULT_MAPS`
(`crates/view-core/src/native/mappings.rs:65`) carries no row for it. Task 5
adds `MappingSpec { feature: "palette", lhs: "<leader><leader>", verb: "open" }`,
making the array 8 rows, and flips `palette`'s `entry_keys` to `true` at
`crates/view-core/src/native/registry.rs:85`, because
`every_feature_that_declares_entry_keys_has_at_least_one`
(`mappings.rs:478`) holds the bit and the table to each other. Rebinding
goes through `[keys]` like every other key.

`cycle_surfaces` is a three-position ring over the whole set: the user's
`[ui.surfaces]` table, every surface forced `windowed`, every surface forced
`overlay`, then back to the table. It never writes the config. A surface
that is open when the ring moves is closed and reopened in its new placement
with its state kept (tree cursor, panel transcript, palette input).

`toggle_gaps` flips `[ui] gaps` live. It re-attaches the outer grid, because
the ring is two cells wide gapped and one gapless, and it re-sends every
window's inner request, because gapless requests `(0, 0)`. A gaps flip need
not move a single slot — neighbours can absorb the whole ring change — so
the idempotent guard of §1 is keyed on the look and the margin as well as
the slot (Task 1 signatures), and the re-send goes out for every window.

Both keys are `[keys]` actions, so `KEY_ACTIONS` (`resolve.rs:166`) grows
from 3 rows to 5, `ResolvedConfig.keys` is sized by it, `Action`
(`crates/view-core/src/native/keys.rs:41`) gains `ToggleGaps` and
`CycleSurfaces`, and `crates/view-native/src/config/keys.rs` gains the two
`ConfigKey` rows with their default spellings.

### Aliases

`[native] tree_width` and `[ai] panel_width` stay readable. When both the
alias and `[ui.surfaces.<s>].size` are set the surfaces table wins and a
startup notice says so; when only the alias is set it is used and a one-line
notice names the new key. There is no alias precedent in the tree (inventory
2026-09-20), so Task 5 adds
`alias_notice(old_table, old_key, new_table, new_key) -> String` beside
`discarded()` in `resolve.rs`, with the wording `[native] tree_width is now
[ui.surfaces.tree] size; both read the same value`.

`[ai]` is parsed by `view-ai` and `[ui.surfaces]` by `view-native`, and the
two crates are forbidden to each other, so `view-ai` resolves its own alias:
`AiConfig::resolve` (`crates/view-ai/src/config.rs:109`) reads
`[ui.surfaces.agent].size` from the file it already parses. Its notice joins
`AiConfig::notices() -> &[String]` (`config.rs:306`) rather than
`panel_width_notice() -> Option<&'static str>` (`config.rs:337`), because
the alias notice names two keys and is built at resolve time. The two crates
still never name each other.

Resizing a windowed surface goes through nvim rather than through the
overlay width. `sidebar_wider`/`sidebar_narrower`
(the two `ConfigKey` rows at `crates/view-native/src/config/keys.rs:107` and
`:113`, resolving to `Action::Resize(Direction)`, whose `Direction` is
`crates/view-core/src/native/keys.rs:22-27`)
step `Model::tree_width_pct` (`model.rs:246`) today, which moves an overlay
and nothing else. Under a windowed placement the same keys send
`RpcCall::SetWindowSize` (Task 4's signature block) and move `size` with it,
so the percent the config names and the window on screen stay one number.

| `SSH_CONNECTION` set | `desktop` |

held on the client. A bare tty falls through to the last row, whose marker

Windows rows read `cfg!(target_os = …)`, which is what those two have in
place of a `DISPLAY`.

person running a kitty-protocol terminal on GNOME who wants the chords
anyway writes `profile = "desktop"`.

### The modifier

The desktop chords are `Super` chords. A terminal reports `Super` only
under the kitty keyboard protocol, which view pushes as `CSI > 1 u` when
the startup probe says the terminal speaks it
(`crates/view-tui/src/terminal.rs:118`, `Model.caps.kitty_kbd` at
`crates/view-core/src/model.rs:2417`).

That bit is the probe's answer and arrives after the config is resolved
(`resolve_session_config`, `crates/view/src/main.rs:762`; the probe's own
answer lands as `Msg::CapsUpgraded`, `crates/view/src/startup.rs:825`). So
`[keys] desktop_modifier` resolves to a choice (`auto`, `super`, `alt`)
through the same layering as every other key, and the choice becomes a
modifier at takeover (`crates/view/src/native.rs:247`), where
`model.caps.kitty_kbd` is in hand and the chord registration goes out
anyway. `auto` takes `super` where the protocol is in force and `alt`
everywhere else. A `CapsUpgraded` that turns the bit on after takeover
re-issues the registration through the same path a profile flip uses.

The report row is appended by the printer at the `caps_notice` site
(`crates/view/src/main.rs:1368`), where caps are in hand, in the place the
`rows()` rustdoc names for the `[ai]` rows (`resolve.rs:488-491`), and it
names what decided the modifier:

| what happened | the row |
|---|---|
| `auto`, protocol in force | `super (kitty keyboard protocol)` |
| `auto`, no protocol | `alt (no kitty keyboard protocol)` |
| `super` written, protocol in force | `super ([keys] desktop_modifier)` |
| `super` written, no protocol | `alt ([keys] desktop_modifier, no kitty keyboard protocol)` |
| `alt` written | `alt ([keys] desktop_modifier)` |

The fourth row also raises a startup notice: "`[keys] desktop_modifier =
super` needs the kitty keyboard protocol, which this terminal did not
answer; the chords answer Alt this run".

`Alt` reaches view from every terminal, as an `ESC` prefix on the legacy
path (`alt_key`, `crates/view-tui/src/keys.rs:630`) and as a modifier bit
under the protocol. The two composer bindings ship as `<S-CR>` and
`<M-CR>` on those same grounds today
(`crates/view-core/src/native/keys.rs:67-95`). The `alt` column of the
chord table is read off the row: an `Alt` chord on a shifted key arrives as
the glyph that key types, so the column spells those chords as the glyph a
US layout types, and another layout rebinds the row it needs through
`[keys.desktop]`.

From a macOS client over ssh, `desktop_modifier = "alt"` with the
terminal's Option-as-Alt setting is the working pair: Terminal, iTerm and
kitty on macOS hold `Cmd` before the pty sees it.

`<M-CR>` is in this file twice, as `composer_newline`'s second default and
as `new_tile`'s `alt` spelling. The first answers inside the agent panel's
composer and the second is an nvim mapping in normal mode, so a press
reaches one of them.

### How a chord reaches nvim

One registration, the same one every view key already goes through.
`MappingSpec` gains a right-hand side:

```rust
/// What a mapping does when its key is pressed.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Default)]
pub enum Rhs {
    /// `<Cmd>call rpcnotify(channel, 'view_invoke', feature, verb)<CR>`,
    /// the shape every row carried before the chords.
    #[default]
    Invoke,
    /// nvim keys, set with no remapping, so the chord costs what typing
    /// those keys costs.
    Keys(&'static str),
}
```

`RegisterMappings` carries the chords as further `specs`, the chunk's own
loop takes the `Keys` arm, and every claim comes back in one answer.
`Model::record_claimed_keys` (`crates/view-core/src/model.rs:721`) replaces
what it holds. One answer per registration. `MappingSpec.lhs` becomes
`Cow<'static, str>`: a static row writes `Cow::Borrowed`, a chord row
carries the spelling a `[keys.desktop]` value gave it, and `MappingSpec`
keeps `Clone` in place of `Copy`. A `Keys` chord's `verb` is its
`[keys.desktop]` id, which is the token `is_spellable` vets
(`native/mappings.rs:275-286`) and the text the chunk writes into the
mapping's `desc`.

The 46 `[keys.desktop]` rows resolve in `resolve_with` the way every other
key does, environment over file, each with the notice a malformed value
owes (`discarded()`, `resolve.rs:737`). All 48 new rows carry
`flag: None`. `ResolvedConfig` carries the answers as
`pub desktop: [Resolved<String>; DESKTOP_CHORD_COUNT]` in
`desktop_chords()` order, and takeover reads them.

The profile is a resolved key, the modifier and the plan are built at
takeover (above), and the plan goes out in the same call the default maps
do. An `editor` session sends the default maps and no chords.

`:View keys profile desktop|editor|auto` flips it live. The chunk holds
the previous registration in `vim.g.view_registered_keys` as `lhs` to the
user's own `maparg(lhs, 'n', false, true)` dict, or `false` where the key
was free, and runs in three steps: restore every entry (`vim.fn.mapset`
for a saved dict, `vim.keymap.del` for a `false`), snapshot which keys are
taken now, then set the whole set again, the default maps and the chords
of the profile now in force. `vim.keymap.del` leaves nothing behind, so
the saved dict is what gives a user their own mapping back. The snapshot
runs after the restore, so a second registration reads the user's maps and
not view's own.
`:View keys profile` with no argument reports the profile, the modifier and
their markers as a notice, the way `:View panes` reports its own (§2).
`:View keys` is a `CommandForm` of `feature: "keys"`, the second
non-feature form after `ui` (§2), so it registers through the exemption
Task 1 teaches `Msg::FeatureInvoke`'s dispatch
(`crates/view-core/src/update/mod.rs:547`).
